# Claw Garden

Local-first memory for coding agents, written in Rust. It stores, classifies and retrieves memories and context, served by a loopback HTTP daemon and a stdio MCP bridge (Claude Code is the current client).

## Workspace

| Crate | Role |
| --- | --- |
| `crates/clawg-core` | Memory engine: SQLite storage, ONNX embeddings (ONNX Runtime), ranking, background workers, and the exclusive lock on `memory.db`. Library `clawg_core`. |
| `crates/clawg-cli` | The `clawg` binary: `serve`, `mcp`, `hook`, `setup`, `status`, `stop`, `doctor`, `path`, and more under Commands. Also a library `clawg_cli`. |
| `crates/clawg-eval` | Evaluation tools: `rag-eval` (retrieval metrics over a golden set), `golden-mine` (golden-set miner) and `conflict-eval` (the contradiction detector over labelled pairs and a flow of facts). They use `clawg-core` through its `eval` feature (`eval_api`), which production builds never link. |

Design documents live in `docs/`.

## Data profiles

`clawg` runs against one of two isolated profiles, resolved in `crates/clawg-core/src/paths.rs`:

| Profile | Data directory | Default port | MCP server name |
| --- | --- | --- | --- |
| `dev` | `~/.clawg-dev` | 27381 | `clawg-dev` |
| `prod` | `~/.clawg` | 27380 | `clawg` |

- Selection order: `--profile dev|prod`, then `CLAWG_PROFILE`, then the build type (`dev` for debug, `prod` for release).
- A debug build refuses `prod`, from both the flag and the env var. A debug binary must never open `~/.clawg`.
- Opening a store that has pending migrations first writes a `pre-migration` snapshot to `<data>/backups`; a store whose vectors were pooled by CLS (embedding contract `multilingual-e5-small`) gets a `pre-reembed` snapshot and is re-embedded by mean before memory is enabled, with the embedder status `loading` meanwhile; a store from a newer clawg, or with a diverged migration, is refused untouched.
- The daemon downloads the model into `<data>/models/` on its first start (`crates/clawg-core/src/memory/model_download.rs`), from Hugging Face or from the mirror `CLAWG_HF_BASE_URL` names: an `https://` URL, or an `http://` one on `localhost`, `127.0.0.1` or `[::1]`; any other value is an error naming the variable. Every file is checked against its pinned SHA-256 whatever the origin, hashed once and off the async runtime's threads. Each attempt waits at most 30 s to connect and 60 s between reads, with no total deadline; a file that runs out of attempts names its host and the last cause (`HTTP 503 …`, the network error), never the URL; a file over 600 MB is refused.
- The daemon lets the embedding model go after `CLAWG_EMBEDDER_IDLE_MINUTES` minutes without use (default 10, `0` keeps it loaded) and loads it again, from the same checked files, on the next request that needs a vector; requests arriving meanwhile share that load (`crates/clawg-core/src/memory/idle_embedder.rs`). That reload reads the cache alone and never downloads: when a file no longer verifies, the request answers not ready at once and one download repairs the cache in the background, which the next request loads (`unloading_when_idle`, `crates/clawg-core/src/memory/bootstrap.rs`). The same wrapper holds the model with `0` too, without letting it go: a request that finds the model's inference worker gone (an inference that panics answers its caller with the cause and ends the worker, dropping its session) drops that model, loads it again and repeats itself once; such a recovery loads at most once a minute (`RECOVERY_INTERVAL`), and the requests in between answer not ready. The embedder status stays `ready` throughout. On Linux with glibc, `clawg serve` keeps every thread on one malloc arena (set in `main` before the runtime starts), or each reload would leave memory behind in another arena.
- One process owns a profile's store at a time (exclusive lock on `memory.lock`; `memory.owner` records who holds it). The daemon also writes `daemon.json` and a bearer `token` in the data directory.
- On Unix the data directory, and every directory clawg creates in it, is private to its owner (`crates/clawg-core/src/private_dir.rs`, used wherever one is created: `serve`, the bridge's autostart, opening the store, `restore`, `sharing`, `update`, `setup` and the daemon's `logs/`, `backups/`, `workspaces/`, `models/`): a missing one is created `0700`, and an existing one with group or other bits loses them with a `warn` naming the old and the new mode. A mode that cannot be changed is logged and the directory used as it is. The files inside keep the mode they are created with. On Windows only the creation is done; the profile's ACL holds.
- `sharing.json` in the data directory holds which agents do not read which agents' memories (`crates/clawg-core/src/memory/sharing.rs`), `*` standing for every agent. Missing means every agent reads every other; an invalid file shares nothing. A row no agent saved (`agent_id` NULL, as a `global` or `project` row) is read by every agent whatever the file says, though a save is compared for contradictions only with its own agent's rows. The daemon reads it on every search and context call.

## Commands

- `clawg serve [--profile P] [--port N]`: run the daemon (`--port 0` binds an ephemeral port).
- `clawg mcp [--profile P] [--no-autostart] [--agent NAME]`: stdio MCP bridge to the daemon; starts one if none is running unless `--no-autostart`. When a call is refused (401 or connection refused) or the start gave up, it reads `daemon.json` and `token` again and repeats the call once, but never starts a daemon mid-session (`crates/clawg-cli/src/mcp/startup.rs`). The agent id is `--agent`, else the client's `clientInfo.name`, else `mcp`.
- `clawg hook session-start|user-prompt-submit --agent NAME [--profile P]`: answer the client's lifecycle hook (JSON on stdin, `hookSpecificOutput.additionalContext` on stdout; `crates/clawg-cli/src/hook.rs`). Both register the input's `session_id` with the daemon for `--agent` and that project, so the saves that follow carry it (`POST /v1/sessions`). `session-start` injects the context without a query for the project of the input's `cwd`, saying when the source was `compact`, when the model failed to load, when 20 or more memories wait for `synthesize` and when a conclusion lost a source since the last review; `user-prompt-submit` says how long the project has gone without a save once it is 30 minutes or more, counted from the later of the last save of the agent there and the creation of `transcript_path`. `--agent` must be the bridge's. It never starts a daemon: no daemon, an error or no answer within 3 s, or input that is not JSON or over 1 MiB prints nothing and exits 0; a usage error or a refused profile exits 1, never 2, which the client reads as "block".
- `clawg status [--profile P]`: print daemon state and health as JSON; exit 1 if not running.
- `clawg stop [--profile P]`: stop the daemon and wait for the process to exit.
- `clawg backup [--profile P]`: write a snapshot of `memory.db` to `<data>/backups` and print its path; goes through the daemon when one is running.
- `clawg restore <FILE> [--profile P]`: replace `memory.db` with a snapshot. The daemon must be stopped; the replaced store is snapshotted first. A file with a non-empty `-wal` beside it is refused, since only the file is copied in.
- `clawg secrets [--profile P]`: list the `memory` rows, live or deleted, and the verdict reasons of `memory_conflict` that hold a secret of a known format, by id and kind and never the secret. Read-only; works with the daemon running. `--mask-reasons --yes` instead replaces the secrets of every stored reason with their placeholders, then rebuilds the file and empties the WAL as `purge` does; the daemon must be stopped and no snapshot is taken.
- `clawg purge <ID> --yes [--profile P]`: remove one `memory` row for good (text, vector, index terms, the head of its long save kept in `memory_piece.context` when it is the first piece, free pages and WAL) and the outbox rows of its own agent's save: the one with the same text, or for a piece of a long save the ones that contain it. A live row is deleted first, so the revision of its topic it replaced comes back as a delete would bring it. It names what came back, the rows a verdict keeps replaced, the other pieces of its save, the outbox rows it removed by `operation_id`, and the backups and `workspace.md` files (AUTO section or the user's part) that still hold the text, changing none of them. A conclusion drawn from it keeps the link to its id, which `synthesize` lists as `purged`. The daemon must be stopped; no snapshot is taken.
- `clawg undelete <ID> [--profile P]`: bring back a deleted `memory` row through the running daemon, which embeds it again; refused when the same text was saved again since, when a live row of another save holds its `topic_key` (not one its own delete brought back), or the row holds a secret; it prints what it supersedes again and the rows saved meanwhile it was paired with.
- `clawg outbox retry|discard <OPERATION_ID> [--agent NAME] [--profile P]`: through the running daemon, take a `failed` save back to pending with its progress and no attempt spent and queue it (written again under another row id), or drop it after deleting the memories it inserted, which `undelete` brings back (`crates/clawg-cli/src/outbox.rs`). `--agent` is needed only when two agents used the operation id; a `pending` row is refused.
- `clawg memories list|search|show|stats [--profile P]`: read-only viewer through the running daemon; `list --deleted` lists deleted rows, most recently deleted first.
- `clawg projects add <PATH> [--profile P]`: let the daemon read and index the files of the project PATH is in, through the running daemon; without it, only the root a bridge was started in is indexed.
- `clawg sharing [hide|unhide <READER> <AUTHOR>] [--profile P]`: show or change the sharing policy. Searches reach every other agent's memories, marked `by <author>` and read-only, unless `hide` keeps AUTHOR's from READER (`*` for every agent); it works with the daemon running and never opens the store.
- `clawg doctor [--profile P]`: print as JSON which `clawg.exe` files the PATH resolves to; exit 1 if the first is not the running binary or a second copy exists. Does not open the store.
- `clawg update [--check] [--profile P]`: for a binary downloaded from a release (not a debug build, one built locally or one run from a cargo target directory), look for a newer release on GitHub and, without `--check`, install it. `--check` exits 0 up to date, 100 newer release (named on stdout), 1 any failure; it changes nothing and takes no lock. `update` downloads `SHA256SUMS` and its minisign signature first, verifies them against the embedded keys, then the binary against its hash, and runs its `--version`; none of that touches the installed binary, the daemon or `memory.db`. Then, under an exclusive lock on `<data>/update.lock`: it stops the daemon through `stop_in` (only if one was running; none is started otherwise), sets the binary aside as `<exe>.old-<yyyyMMddHHmmssfff>`, puts the new one in its place and starts the new daemon by explicit path on the port the old one had, watching it (`memory.owner` read without the try-lock, `/health`) until a daemon of the new version answers. Any failure undoes what was done in reverse (`crates/clawg-cli/src/update/plan.rs`, a plan as data run over an `Effects` trait; the real one in `effects.rs`); when the new daemon migrated the store and the old binary refuses it, the `pre-migration` snapshot that start wrote is restored in process, the migrated store kept as `pre-restore`, and when that restore fails the new binary stays and the report gives the way back by hand. Old `.old-*` and staged files are deleted at the start of the next run. Exit 0 on success, 1 on a refusal or failure.
- `clawg setup claude-code [--profile P] [--dry-run] [--remove]`: connect Claude Code (`crates/clawg-cli/src/setup.rs`, a pure `plan` over what was read, then `apply`). It registers the profile's server (`clawg`, `clawg-dev`) through `claude mcp add --scope user` with the running binary's absolute path and `mcp --profile P --agent claude-code`, reading `.claude.json` to see what is there but never writing it; adds a `SessionStart` (`startup|resume|clear|compact`) and a `UserPromptSubmit` group to the user `settings.json`, each hook in exec form (the binary's path as `command`, unchanged, and `hook <event> --agent claude-code --profile P` as `args`, run by the client without a shell, which needs Claude Code 2.1.139 or later; an older client runs the binary alone, and `clawg` without a subcommand exits 1, not 2, so it does not block the session); and puts `protocol.md` between `<!-- BEGIN CLAWG MEMORY PROTOCOL -->` and `<!-- END CLAWG MEMORY PROTOCOL -->` in the user `CLAUDE.md` (`$CLAUDE_CONFIG_DIR` instead of `~/.claude` when set, with `.claude.json` inside it). Everything is read first: an unreadable file, invalid JSON or a lone marker writes nothing. A server, or a clawg hook of the same event and profile, that differs from the plan is reported and left alone (exit 1), as is anything not clawg's; the block is rewritten, and so is a hook that is exactly the shell command line earlier versions wrote, whatever clawg path it names, which becomes the exec form in its place. Without `claude` on the PATH it prints the command, installs the rest and exits 1. Each changed file is copied to `<data>/backups/setup/` first (owner-only on Unix; only the five newest copies of each file are kept, and the report names the ones removed) and written through a temporary file with the old file's mode, synced and renamed; a symbolic link is written through, to the file it points to, and a linked `CLAUDE.md` that only held the block is emptied instead of deleted. `--remove` takes away a clawg server, the profile's clawg hooks in either form and the block (kept while the other profile's server is registered); `--dry-run` writes nothing and runs no `claude`.
- `clawg path add|remove [--dir D]`: edit the user PATH (Windows).

Daemon HTTP API (the client in `crates/clawg-cli/src/client.rs`, the bridge and the hooks included, never goes through an HTTP proxy): every route, `/health` included, answers `403 {"error":"forbidden"}` to a request whose `Host` (or URI authority) is not `127.0.0.1`, `localhost` or `[::1]`, with any port, or that carries any `Origin`, before the token is looked at (`crates/clawg-cli/src/daemon/guard.rs`), so a web page cannot reach the daemon, rebinding or not; a refusal is logged at most once a minute, without the header values. On Unix `token` and `daemon.json` are created `0600` as new files. `GET /health` (open; `embedder_resident` says whether the model is in memory now; its `ingest` block counts pending and failed saves and names each failed one by `operation_id`, with the memories it inserted in `pieces`, left out when the store does not answer within 250 ms) and, behind the bearer token, `POST/GET /v1/memories`, `POST /v1/sessions` (`agent_id`, `project_id`, `session_id` of 1 to 128 visible ASCII characters, else a 400: the host session that agent works in for that project, kept in memory, the last one registered winning; a save accepted after it is stamped with it in `source_session_id`, in the outbox event too, and carries none without one; `crates/clawg-cli/src/daemon/sessions.rs`), `POST /v1/search`, `POST /v1/context` (both also reach other agents' memories unless `sharing.json` hides them from the caller; each search hit carries its `agent_id`, its `topic_key` when it has one, and `exact` when it holds every identifier of the query; a search's `min_relative_score` cut, and the bridge's, always keeps the `exact` hits, measures the rest against the best of them and never shows a hit that scored 0 (below the cosine floor without an identifier), and the answer counts what it kept back in `withheld`; a context without a `query` (or a blank one) embeds nothing and lists, as RECENT, the caller's own newest live saves of the last seven days in the project, without one or, as a search reads them, a `user_preference` of any project, one line per save, counting no access, with `retrieval.state` `recent`; every context, with a query or without, opens after the workspace with `=== LAST SESSION ===`, the newest live `session_summary` of the project (a long one joined whole) the caller may read, its own or shared and then marked `by <author>`, whatever its age, counting no access and never repeated as a hit; a context leaves out the hits that scored 0, and its prompt fits its `budget` in bytes, default 8000 and at most 24000, `0` a 400, cutting first the RECENT or LONG-TERM hit that scored lowest (an `exact` one only when no other hit is left), then LAST SESSION, then conflict pairs, shortening a hit left alone in its block to end in ` [truncated]`, never cutting the workspace, and naming what it cut by id in a closing `=== BUDGET ===` block; its `retrieval.state` says whether memories were searched, `searched` (with the `hits` the prompt used and the `withheld` it left out), `embedder_not_ready`, `embedder_failed` or `search_failed`, and `recall_context` opens with the reason when they were not; when memories were searched and none was close enough to show, `search_memory` and `recall_context` say `no relevant memories for this query`, and `no memories found` stays for a scope with nothing in it), `PATCH/DELETE /v1/memories/{kind}/{id}` (`PATCH` takes `importance`, `memory_type` or both; `?agent=` limits them to that agent's rows), `GET /v1/memories/{kind}/{id}/save` (the save the row is a piece of, its pieces joined, and the row's `topic_key`; same `?agent=` scope), `POST /v1/memories/memory/{id}/restore` (a deleted row back with its vector and text index; same `?agent=` scope; `GET /v1/memories?deleted=true` lists deleted rows; the answer carries its `topic_key`, the rows its delete brought back and it supersedes again in `replaced`, `superseded_by_deleted` when the row that supersedes it is deleted too, and in `related` the pairs the detector wrote with the live rows saved after its `deleted_at`, the newer row `new_id` and, when escalated, `disputed`), `POST /v1/projects` (record a project root and move rows saved under its legacy ids, and start loading an unloaded model without waiting for it; `index_docs: true` also lets the daemon read the root's files and indexes them in the background, a 400 when the root is not a directory; 409 `project_root_collision` when its id belongs to another root), `POST /v1/projects/docs/search` (a project's docs and code by meaning and by term; refreshes the index first when it is over a minute old; 403 for a root that was never registered with `index_docs`), `POST /v1/backup`, `POST /v1/disputes/judge` (`keep`, `other`, `verdict` one of `supersedes`, `compatible`, `scoped` with a `reason`, or `conflicts`; optional `agent_id`, same scope), `POST /v1/disputes/resolve` (the same with `keep_both` instead of a verdict, for older bridges), `GET /v1/disputes?agent_id=` (pending and escalated pairs counted, the five oldest pending named with each side's provenance mark), `POST /v1/synthesis` (memories no conclusion covers yet, the conclusions already drawn, and in `to_review` the live ones with a source deleted, replaced or purged, each with `live` and its `lost` sources, at most 10 newest first, `to_review_total` counting them; optional `agent_id`, same scope; `POST /v1/context` answers `unreviewed` and `conclusions_to_review`, those that lost a source after the scope's last synthesis, which `recall_context` and `session-start` turn into a line from 1; `crates/clawg-core/src/memory/synthesis.rs`), `POST /v1/outbox/retry` and `POST /v1/outbox/discard` (`operation_id`, optional `agent_id`; 404 without a row, 409 for a `pending` one or an id two agents share), `POST /v1/shutdown`.

A project's docs index (`crates/clawg-core/src/memory/project_docs/`) holds its Markdown and manifests (`Cargo.toml`, `package.json`, `pyproject.toml`, `go.mod`) as passages split by heading, each under its breadcrumb (`path > heading > subheading`), and its Rust, Python and TypeScript code split along the syntax tree (tree-sitter), each piece under its path and the headers of the definitions that contain it (`path > impl Store`). It honours `.gitignore`, is derived from disk in its own tables and never touches `memory`; a file is re-read when its sha256 or the model changes. Only a root marked `index_docs` in `project` is read: the bridge asks for it for its own root alone, and `clawg projects add` for any other, so a `project_path` the model passes is a label for memories until the user adds it. When a root's id already belongs to another root, every tool that scopes to it fails rather than mix two projects (`all_projects` still works); any other registration failure only logs a warning.

Ingest masks secrets (`crates/clawg-core/src/memory/redact.rs`) before a save is chunked, hashed or embedded, and the docs index does the same with every passage; a confirmed save lists the masked kinds in `redacted`. It masks keys and tokens of known formats (an `sk-` or `hf_` key only when it mixes upper case, lower case and digits, so hyphenated identifiers and class names pass; Slack webhooks; PGP private key blocks), the literal value after a key ending in `password` or `passwd` (`password`), after a key ending in `secret`, `token`, `api_key`, `access_key`, `secret_key`, `account_key` or `auth_key`, in any case and with any prefix (`credential`, never a value of digits alone), and after `Authorization: Bearer|Basic|Token` (never a variable, a type, a call or a placeholder), and everything the writer wraps in a private mark, `<private>` to `</private>`. A mark left open masks to the end of the text; a mark right after a backtick is text. Nothing is guessed from entropy. The reason of a verdict and the error an outbox row records are masked the same way before they are stored. A rule added later reaches stored rows only through `clawg secrets`, and makes `undelete` refuse a deleted row it now flags.

A save is written, already masked, to the `ingest_outbox` table of `memory.db` before the daemon answers `201` or `202`, and its row goes in the transaction that finishes storing it (`crates/clawg-core/src/memory/outbox.rs`), so a kill, crash or power cut loses nothing accepted (the row alone is written with `synchronous = FULL`; the rest of the store keeps `NORMAL`). Each piece of a long save is noted in the row as it is stored, and a replay resumes after it. On start the daemon ingests pending rows before new saves. Each take of a row spends an attempt; a row is `failed`, with its cause, once it spent 3 takes that ended in a failure the embedder did not cause or with the process gone, or when its event no longer parses. A save the embedder could not take (`EmbedderUnavailable`) hands its attempt back and is taken again in the same run after 1 s, doubling up to 60 s, holding the queue so saves under one topic key still apply in order (`crates/clawg-core/src/memory/worker.rs`); a caller waiting for it gets `202` `retrying`. A caller waiting for a save that failed otherwise gets `500 ingest_failed` and its row is dropped when nothing was stored, and `202` `partially_saved` with the stored pieces in `memories` and the cause in `detail` when some were, its row kept for the next start to finish. A drain stops a save with a row before its next piece once its deadline passes (after the first piece each take stores), handing the attempt back, and the next start resumes it. `clawg outbox retry|discard` is the way out of `failed`. Every save answers with an `operation_id` (a UUID v4, or the caller's own, 1 to 128 visible ASCII characters); sending the same one again while its row exists answers `already_queued` (pending) or `ingest_failed` (failed) instead of saving twice. Shutdown no longer writes `ingest-pending.jsonl`; one left by an older clawg is imported masked on start and removed.

A save longer than one piece (480 tokens) is split into pieces of 96 tokens, neighbours sharing 24, so one sentence is not averaged away in a long vector; every piece after the first is embedded behind the save's opening tokens, and `memory_piece` links the pieces (`crates/clawg-core/src/memory/pieces.rs`). Saves split before at 424 tokens keep their pieces. Search fills its KNN pool with distinct saves, keeps the best piece of each and labels it `piece=K/N`.

A save may name a `topic_key` (`crates/clawg-core/src/memory/topic.rs`): lowercase segments of `[a-z0-9._-]` joined by `/`, at most 80 characters, anything else a 400 before the outbox. Its scope is the agent and the project, as for the dedup. In the transaction that finishes the save (with its outbox row, or linking its pieces), every live row of that scope outside the save becomes `superseded` by the save's first row, except a piece of a save whose first piece is live without that key, which stays live and loses the key; the save's rows take the key, the rows it inserted the best tier and the most accesses of the replaced ones, and the type and importance it does not name come from the oldest live row of the scope. The detector never pairs a save with the rows it replaces, a save that fails replaces nothing, and the answer lists the replaced rows in `replaced` and echoes `topic_key`, so a bridge can tell a daemon that ignored it. Rows keep their content: the history is the chain of `superseded` rows, listed with `by=#N` and `topic=K`. Each `superseded` row records why in `supersede_cause` (`revision` or `verdict`, V17). Deleting the current row of a key, when no other live row holds it, makes the newest save its revision replaced live again (`crates/clawg-core/src/memory/revival.rs`), marked `revived_from` the deleted row, and points the older ones at it; `DELETE` lists them in `revived`, and the rows a verdict replaced, which stay superseded, in `hidden`. Restoring the deleted row supersedes again what its delete brought back; a restored row superseded by a deleted revision comes back current under the same rule, and the maintenance pass applies it to what an older delete left.

The contradiction detector (`crates/clawg-core/src/memory/contradiction.rs`) measures closeness, not contradiction: each earlier row of the saver's within the band becomes a pair in `memory_conflict`, one per pair of saves, written in the transaction of the new row. `needs_user` escalates a pair only when it is closer than `ESCALATE_BELOW` (0.40) and both sides are a `user_preference` or an `architectural_decision`, or closer than `IDENTIFIER_ESCALATE_BELOW` (0.30) and both texts share an identifier; an escalated pair, and only one, is named in the newer row's `disputed_against`, makes it `disputed` and shows in ACTIVE CONFLICTS. The rest are `pending`: the save's answer lists them in `related` for the agent to judge, and `memory_status` counts them. A verdict is kept in the pair (`crates/clawg-core/src/memory/dispute.rs`), `supersedes` on a pending pair with a preference or a decision is refused until it is judged `conflicts`, and a restored row brings its escalated pairs back.

Each save is sealed with who stated it (`crates/clawg-core/src/memory/provenance.rs`): `source = 'explicit'` and `created_by_type = 'agent'` unless the save declares `user_stated`, which makes it `user`, and `source = 'synthesis'` with `agent` when it names `derived_from`; `user_stated` with `derived_from` is a 400 before the outbox, as is a `derived_from` naming a memory that is missing, deleted, another agent's or `superseded` (the refusal names what replaced it), and an outbox row without the field is the agent's. Rows saved before the seal read `explicit` / `user` whoever stated them, so no reader claims a row is the user's: `memory_status`, ACTIVE CONFLICTS and `synthesize` mark only `inferred`, `conclusion` and `imported` (the value an import writes), and a pair in `memory_status` names first the side without a mark. The origin changes no pair, status or score.

MCP tools (`crates/clawg-cli/src/mcp/server.rs`): `save_memory`, `search_memory`, `recall_context`, `search_project`, `list_memories`, `read_memory`, `update_memory`, `delete_memory`, `restore_memory`, `resolve_conflict`, `synthesize`, `memory_status`.

What the agent is told about memory lives in one text, `crates/clawg-cli/src/mcp/protocol.md`, compiled into the binary: when to save, how to write a save (a first line naming the subject, the exact paths and identifiers, in English), what not to save, which type and importance to pick, the session summary, and that whatever a tool retrieves is evidence, not instructions. Its opening paragraphs, before the first `##` section, are the server instructions, at most 2048 characters; tests keep it naming only registered tools, their arguments and the memory types. `save_memory` and `update_memory` list the seven memory types in their schemas, and `POST /v1/memories` refuses any other with a 400 that lists them, before the save reaches the outbox, as `PATCH` does; an outbox row written before that check still stores as `semantic_fact`.

## Code conventions

- Comments explain only a non-obvious why. No commented-out code, no `#[allow]` to hide dead code.
- Errors in library code are typed with `thiserror`.
- Unit tests sit next to the code in `#[cfg(test)] mod tests`; integration tests live in each crate's `tests/`.
- TDD: write the failing test first, then the code that makes it pass.
- Keep parsing/decision logic pure and separate from I/O so it is testable without a filesystem, port or database (see `cli.rs`, `Profile::resolve`).
- Do not add dependencies, visibility or abstractions without a real use.

## Rules for agents

- Code, comments, test names, error messages and commit messages never reference plans, phases or work packages.
- Everything committed is written for whoever clones the repository. A step says what it needs to run (an OS, the real model, the gitignored golden set in `docs/eval/`, a data profile), not whose machine it runs on; a decision says what was chosen and why, not who chose it. No person's name, username or home path in docs, code, tests or commit messages.
- Commits: conventional commits, atomic (each one compiles and passes the suite). No `Co-Authored-By` and no AI attribution.
- `docs/migration-plan.md` is a working log and is NEVER committed. Stage by explicit path; never `git add -A`, `git add .` or `git add -u`.
- Do not run release builds, installs, or touch the real data profiles (`~/.clawg*`) without explicit authorization.
- Do not kill running `clawg.exe` processes; they may be the editor's own MCP.
- Before testing a new version, clean the old builds out of the test build directory, and end every task with no build directory other than `target` and `target-test` (Build directories, under Testing).

## Versioning

- The version lives only in `[workspace.package] version` of the root `Cargo.toml`; every crate inherits it with `version.workspace = true`. Never set a version in a crate's own `Cargo.toml`.
- Bump it when work closes: an archived openspec change raises the minor (`0.4.0` → `0.5.0`), a fix outside openspec raises the patch (`0.4.0` → `0.4.1`).
- After the edit, run `cargo update --workspace`: it writes the new version into `Cargo.lock` without touching any dependency and without building. Commit both files together as `chore: bump version to X.Y.Z`; otherwise the lock trails one version behind, and CI, which builds with `--locked`, fails.
- Publishing is automatic. Merging a version bump to `main` runs CI; when CI passes for that push, `.github/workflows/release.yml` (triggered by `workflow_run`, never by a pull request) builds `clawg-cli` for `x86_64-pc-windows-msvc` and `x86_64-unknown-linux-gnu`, signs `SHA256SUMS` with minisign and creates the release `vX.Y.Z` on the commit CI ran on, with both binaries, `scripts/install.ps1`, `SHA256SUMS`, `SHA256SUMS.minisig` and a provenance attestation. A version that already has its tag publishes nothing, so a merge that does not bump the version releases nothing. Never create a tag or a release by hand, and never build a release locally to publish it.
- The release public keys are `release/minisign.pub` (primary) and `release/minisign-next.pub` (backup). The primary private key and its password are secrets of the `release` environment (`MINISIGN_SECRET_KEY`, `MINISIGN_PASSWORD`), limited to `main`; the backup private key is kept outside GitHub. Only the signing step of `release.yml` reads them, and `ci.yml` reads none.
- The version is not cosmetic: `clawg --version`, `GET /health`, the MCP `serverInfo` and `clawg doctor` report it, and `version_warning` (`crates/clawg-cli/src/memories.rs`) compares the running daemon's version with the CLI's to detect a stale daemon.

## Testing

```
cargo test --workspace
```

The bar is that the whole suite passes. Never record how many tests it has (in this file, the other agents' instruction files or `openspec/config.yaml`): the count goes stale with every change.

`crates/clawg-cli/tests/binary.rs` runs the built `clawg` itself: a hard kill with a save still pending, two daemons on one store, `status`/`stop`, `backup`/`restore`, MCP over real stdio and a daemon restart under an open bridge. Each test gets a temporary home through `CLAWG_TEST_HOME` and the fake model through `CLAWG_TEST_EMBEDDER=fake|stalled`; only a build with clawg-core's `testing` feature (its dev-dependencies) reads them, never a release build, and `tests/conventions.rs` fails when a manifest enables `testing` outside `[dev-dependencies]`. Every daemon binds `--port 0`, and each child is ended by its own handle, never by name. It takes about a second.

A `testing` build also stands in for what makes a binary a release, so `clawg update` can be driven without the network or a real release: a stamp after the end of a copied binary (`0x00`, `CLAWG-TEST-STAMP`, a JSON object up to the end of the file; `version`, `dist_target`, `migrations_up_to` (the newest migration the binary knows and applies, as if it were an older release) and `serve_fault`, `before_open` or `after_open` (where `clawg serve` fails on purpose)) replaces the version and the distribution mark the build reports (`crates/clawg-core/src/build_info.rs`), `CLAWG_TEST_RELEASE_URL` replaces the release server and `CLAWG_TEST_RELEASE_KEYS` (a JSON array with the text of a `.pub` file per key) the trusted keys. A build without `testing` reads none of them, and a binary without a stamp (the `CARGO_BIN_EXE_clawg` of the suite) is refused by `clawg update` as built locally. The tests sign what their fake release server serves with the `minisign` dev-dependency. Each scenario of `update` in `binary.rs` copies the test binary with its stamp into `<home>/bin`, starts its daemon and bridge from that copy, and ends the daemon `update` starts with `clawg stop` when the test drops it.

CI (`.github/workflows/ci.yml`) runs clippy and the suite on Linux and Windows for every pull request and every push to `main` that changes a file outside the documentation and tooling paths it ignores. A push that only changes those paths runs neither CI nor the release. Every command takes `--locked`, so a `Cargo.lock` that trails `Cargo.toml` fails there. Besides the workspace (where `--workspace` turns on clawg-core's `testing` and `eval`), it runs what the release builds: `cargo clippy --locked -p clawg-cli -- -A clippy::all -D warnings`, without `--all-targets` so no dev-dependency brings `testing` in, and `cargo test --locked -p clawg-core --lib build_info`, the `cfg(not(feature = "testing"))` side of those tests. Pull requests read the build cache and only a push to `main` writes it (`save-if`).

The compiler is fixed in `rust-toolchain.toml` (an exact `X.Y.Z` with clippy), which local builds use too; every workflow passes the same version to `dtolnay/rust-toolchain`. Raising it is a commit of its own that changes all of them. `rust-version` in the root `Cargo.toml` is the highest `rust-version` among the packages in `Cargo.lock` (1.90, from `tree-sitter-language`; a `cargo +1.90.0 check --locked --workspace --all-targets` builds), never above the pinned toolchain; `tests/conventions.rs` compares the three.

Two more workflows only report, and are not named `CI`, so `release.yml` does not wait for them: `advisories.yml` runs `cargo deny --locked check advisories` with the root `deny.toml` on the pull requests and pushes to `main` that change a manifest, the lock or `deny.toml`, and every week, so a RustSec advisory shows without blocking a pull request or a release (an ignored advisory carries its `reason`); `installer.yml` runs PSScriptAnalyzer on `scripts/` on Windows when `scripts/**` changes, with `scripts/PSScriptAnalyzerSettings.psd1`, failing on any finding (an excluded rule says why). Both download their tool at a fixed version and check it against a SHA-256 written in the workflow. `.github/dependabot.yml` updates the pinned actions once a month, against `develop`.

`.github/workflows/release.yml` runs after a green CI on a push to `main` (see Versioning) and builds only `-p clawg-cli`: `--workspace` would link clawg-eval, and with it the `eval` feature of clawg-core, into the shipped binary. Each build sets `CLAWG_DIST_TARGET` and is tried up to three times, since `ort-sys` downloads ONNX Runtime from `cdn.pyke.io` while building; it then runs `--version` and checks that the binary carries no `CLAWG_TEST_` stand-in; the Linux build also checks that it does not link OpenSSL. In every workflow, third-party actions are pinned by commit SHA with the tag in a comment, and each checkout sets `persist-credentials: false`. `tests/conventions.rs` reads the workflows and `dependabot.yml` as text (no YAML dependency) and pins their triggers, pins, build commands, downloads and the signing step, so reformatting a workflow without changing its meaning can break one of them: adjust the test in the same commit. The workflow itself only runs on GitHub; nothing in the suite executes it.

On Windows, live `clawg.exe` processes (for example the editor's MCP bridge) lock `target\debug\clawg.exe` and make the build fail. There the suite and clippy run in `target-test` instead: `cargo test --workspace --target-dir target-test`. See Build directories below for when it is cleaned.

Compiler warnings, `dead_code` and `unused` among them, are errors here (clippy's own lints are not enforced yet):

```
cargo clippy --workspace --all-targets -- -A clippy::all -D warnings
```

`tests/conventions.rs` in `clawg-cli` fails when a source hides dead code behind an `allow`.

What the model sees of the MCP server (each tool's name, description and input schema, and the instructions) is pinned in `crates/clawg-cli/src/mcp/agent_contract.json`. When a change to it is intended, run `CLAWG_BLESS=1 cargo test -p clawg-cli the_agent_contract_matches_its_file`: it rewrites the file and fails, so review the diff and run the tests again. The `MCP tools` line above is checked against the registered tools.

A ranking change is compared with the baseline by `cargo run -p clawg-eval --bin rag-eval -- --diff <before.json> <after.json>`. Every metric carries the exact paired p-value of the cases that moved (and MRR, nDCG and tokens a bootstrap interval of the mean change); the primary metrics are `recall@5` and, between two `--agent-view` runs, `search.found`. With the 46-case set a conclusion needs at least 6 cases moving one way; fewer is "not distinguishable", never "no difference". `--fail-on-regression` exits 6 when a primary metric gets worse at p < 0.05. When the golden cases carry `query_lang`, every block is also cut by the language pair of query and row (`es>en`, …), over the cases with that pair in both files: a change that touches retrieval across languages is read there, and the pair rows stay informative, outside the verdict and `--fail-on-regression`. Choose a new constant reading `by_split.calibration` and report `by_split.test`; `--lexical-only` gives the bm25-only floor to compare against.

### Build directories

Cargo never removes an old artifact from a target directory. Every version bump, branch or worktree with other sources, feature set or toolchain leaves a new set of the workspace's test binaries beside the previous ones, so a directory that is only ever reused grows past 100 GB. Most of that weight is the workspace's own crates, not its dependencies.

- Tests and clippy use one directory: `target`, or `target-test` on Windows. Never create another one (`target-apply`, `target/verify-win`, a directory outside the repository).
- Before testing a new version (another branch or openspec change, a version bump, another worktree's sources), remove the workspace's old artifacts and keep the dependencies: `cargo clean --workspace --target-dir target-test`. After `rustup update` or a dependency change in `Cargo.lock`, empty it: `cargo clean --target-dir target-test`. Within one change's TDD loop the directory is reused, not cleaned.
- On Windows, `target` is cleaned only when no `clawg.exe` built there is running; never stop one to clean it.
- A directory a one-off comparison needs (a worktree arm, a baseline build) is deleted, with its worktree, by the task that made it.
- A task ends with no build directory other than `target` and `target-test`.
