# Claw Garden

Local-first memory for coding agents, written in Rust. It stores, classifies and retrieves memories and context, served by a loopback HTTP daemon and a stdio MCP bridge (Claude Code is the current client).

## Workspace

| Crate | Role |
| --- | --- |
| `crates/clawg-core` | Memory engine: SQLite storage, ONNX embeddings (ONNX Runtime), ranking, background workers, the exclusive lock on `memory.db`, and the daemon's usage metrics (`metrics`). Library `clawg_core`. |
| `crates/clawg-cli` | The `clawg` binary: `serve`, `mcp`, `hook`, `setup`, `status`, `stop`, `doctor`, `path`, and more under Commands. Also a library `clawg_cli`. |
| `crates/clawg-eval` | Evaluation tools: `rag-eval` (retrieval metrics over a golden set), `golden-mine` (golden-set miner), `conflict-eval` (the contradiction detector over labelled pairs and a flow of facts) and `revision-eval` (what a topic key changes: chains of versions saved with and without one, and how often the unkeyed saves of an exported store are revisions) and `load-eval` (the memory peak and the time of loading the model, by arm, one load per process). They use `clawg-core` through its `eval` feature (`eval_api`), which production builds never link. |

Design documents live in `docs/`.

## Data profiles

`clawg` runs against one of two isolated profiles, resolved in `crates/clawg-core/src/paths.rs`:

| Profile | Data directory | Default port | MCP server name |
| --- | --- | --- | --- |
| `dev` | `~/.clawg-dev` | 27381 | `clawg-dev` |
| `prod` | `~/.clawg` | 27380 | `clawg` |

- Selection order: `--profile dev|prod`, then `CLAWG_PROFILE`, then the build type (`dev` for debug, `prod` for release).
- A debug build refuses `prod`, from both the flag and the env var. A debug binary must never open `~/.clawg`.
- Opening a store that has pending migrations first writes a `pre-migration` snapshot to `<data>/backups`; a store whose vectors were pooled by CLS (embedding contract `multilingual-e5-small`) gets a `pre-reembed` snapshot and is re-embedded by mean before memory is enabled, with the embedder status `loading` meanwhile; a store from a newer clawg, or with a diverged migration, is refused untouched.
- The daemon downloads the model into `<data>/models/` on its first start (`crates/clawg-core/src/memory/model_download.rs`), from Hugging Face or from the mirror `CLAWG_HF_BASE_URL` names: an `https://` URL, or an `http://` one on `localhost`, `127.0.0.1` or `[::1]`; any other value is an error naming the variable. Every file is checked against its pinned SHA-256 whatever the origin, hashed once and off the async runtime's threads, and `model.onnx` is hashed on the read-only view (`OnnxFile`, a `memmap2` mapping) that the load then receives, so no copy of it sits in memory: on Windows the file is open without sharing writes or deletion from the hash until `commit_from_memory` returns, and on Unix the `0700` data directory and the rename of a `.partial` are the guard. A download runs `model.onnx` into `.partial` and renames it under the write side of the `CacheLock` that every load holds the read side of, so a repair waits for a load to let go of the file; the run that downloads it hashes it as it writes `.partial`, keeps none of its bytes (`download_one` answers none for it), renames it and loads it from the cache like a reload (`fetch`), so only that run hashes it twice. Each attempt waits at most 30 s to connect and 60 s between reads, with no total deadline; a file that runs out of attempts names its host and the last cause (`HTTP 503 …`, the network error), never the URL; a file over 600 MB is refused. A file another program holds open (Windows errors 5, 32 or 33, as an antivirus scanning it gives) is read again over about 2 s (`OPEN_RETRY_WAITS_MS`) and, if it stays held, is neither missing nor downloaded over: the check answers `DownloadError::Busy`, which the start retries.
- The daemon lets the embedding model go after `CLAWG_EMBEDDER_IDLE_MINUTES` minutes without use (default 10, `0` keeps it loaded) and loads it again, from the same checked files, on the next request that needs a vector; requests arriving meanwhile share that load (`crates/clawg-core/src/memory/idle_embedder.rs`). Each such load logs who asked for it (a wake, a call that embeds, a recovery) and the private memory before and after, and on Windows the private peak the load reached (`private peak rose to …`) or that the peak stayed where an earlier load set it, which adds nothing to `metrics.db`; the model a wake loaded logs how long until a call first used it, and an unload says when none did. That reload reads the cache alone and never downloads, and the model it hands to the load is the read-only view its hash was taken on (`OnnxFile`), which holds the file and the read side of the `CacheLock` until the session is built or fails, after which a repair may rename over it: when a file no longer verifies, the request answers not ready at once and one download repairs the cache in the background, which the next request loads, except when a file is held by another program (`Busy`), which answers not ready with no download (`needs_repair`) (`unloading_when_idle`, `crates/clawg-core/src/memory/bootstrap.rs`). The same wrapper holds the model with `0` too, without letting it go: a request that finds the model's inference worker gone (an inference that panics answers its caller with the cause and ends the worker, dropping its session) drops that model, loads it again and repeats itself once; such a recovery loads at most once a minute (`RECOVERY_INTERVAL`), and the requests in between answer not ready. The embedder status stays `ready` throughout. On Linux with glibc, `clawg serve` keeps every thread on one malloc arena (set in `main` before the runtime starts), or each reload would leave memory behind in another arena.
- One process owns a profile's store at a time (exclusive lock on `memory.lock`; `memory.owner` records who holds it). The daemon also writes `daemon.json` and a bearer `token` in the data directory.
- The daemon listens on `<data>/clawg.sock` (`crates/clawg-cli/src/daemon/socket/`, on Unix and on Windows): `mod.rs` holds what both share (`SUN_PATH_LEN`, `SocketError`, `check_socket_path`, `serves_without_socket`, `remove_stale_socket`, `bind_socket`, `Listener`), `unix.rs` the peer check and `windows.rs` the native AF_UNIX listener (`AfUnixListener`, built with `socket2`, since `std::os::windows::net` is unstable, and accepted on a plain thread, `clawg-accept`, that the listener's `Drop` wakes) and the client's `Connector`. On Unix the listener drops, before reading a byte, every connection of another uid (`admits_peer`); on Windows there is no peer check, and the guard is the data directory's DACL, which the socket file inherits when it is created: an account without `FILE_WRITE_DATA` on the file cannot connect (`WSAEACCES`, 10013). With the store lock taken the daemon removes the socket a killed one left, and an orderly exit removes it with `daemon.json` and `token`. A socket path that does not fit `sun_path` (108 bytes on Linux and Windows, 104 elsewhere, the path being shorter than that) stops the start naming the path, unless `--port` was given, and then the daemon serves over TCP alone; on Windows a path that is not valid Unicode (`SocketError::NotUnicode`) is treated the same way. A Windows system without AF_UNIX (`WSAEAFNOSUPPORT`, `lacks_af_unix`, `SocketError::Unsupported`) logs a `warn` and serves over TCP alone, with or without `--port`; any other socket failure stops the start. TCP stays on beside the socket for clients older than the socket: `--port N` binds `127.0.0.1:N` and a failed bind is fatal; without it the daemon also tries the profile's port, and with the socket up a failed bind (another user's daemon on it, another program) is a `warn` and the daemon goes on over the socket, while without a socket the profile's port is required and a failed bind is fatal (`tcp_plan`, `crates/clawg-cli/src/daemon/serve.rs`). `daemon.json` carries `port` whenever TCP is on and `unix_socket: true` when the socket is; the client (`from_data_dir`, `endpoint`) dials the socket it derives from the data directory whenever one is published, on both systems, at `http://localhost`, and never falls back to the port (through reqwest's `unix_socket` on Unix, through hyper-util's legacy client over the `Connector` on Windows).
- On Unix the data directory, and every directory clawg creates in it, is private to its owner (`crates/clawg-core/src/private_dir.rs`, used wherever one is created: `serve`, the bridge's autostart, opening the store, `restore`, `sharing`, `update`, `setup` and the daemon's `logs/`, `backups/`, `workspaces/`, `models/`): a missing one is created `0700`, and an existing one with group or other bits loses them with a `warn` naming the old and the new mode. A mode that cannot be changed is logged and the directory used as it is. The files inside keep the mode they are created with. On Windows only the creation is done; the profile's ACL holds.
- The daemon keeps its usage metrics in `<data>/metrics.db` (`crates/clawg-core/src/metrics/`), with a connection of its own, never in `memory.db`, so no snapshot, `restore`, `purge`, `export`, `import` or `doctor` touches it. `Recorder` (`MemoryRuntime::metrics`, the store's own, `MemoryStore::metrics`, so every clone of the store and a test runtime of its own measure into one) holds the minute in progress and the whole run: `http.duration` (µs) by `method`, `route` (the template axum matched, else `unmatched`), `status` class and `transport` (`unix`, `tcp`), timed by a middleware outside the guard and the token so refusals count too, `http.request_bytes` from `Content-Length`, the gauge `http.in_flight`, and once a minute `process.rss_bytes`, `process.rss_peak_bytes`, `process.private_bytes`, `process.private_peak_bytes` (Windows, `PeakPagefileUsage`), `process.cpu_ratio`, `process.threads` and `process.open_files` (Linux), `process.handles` (Windows), `embedder.resident` and `rt.alive_tasks`, `rt.global_queue_depth`, `rt.worker_busy_ratio` (`crates/clawg-cli/src/daemon/process.rs`); what a system does not give is left out, never 0. A probe of the store (`crates/clawg-cli/src/daemon/store_probe.rs`) queues a call without SQL on the store's one connection at start and every `PROBE_INTERVAL` (10 s) and records `db.probe_wait` (µs, the wait until it starts on the connection's thread, `MemoryStore::probe_wait`, `crates/clawg-core/src/memory/conn_probe.rs`), and with the first probe and every sixth the gauges `db.cache_hit`, `db.cache_miss`, `db.cache_write`, `db.cache_spill` (counted since the reading before, which `sqlite3_db_status` restarts), `db.cache_used_bytes`, `db.stmt_used_bytes`, `db.file_bytes` by `file` (`db`, `wal`, `backups`, the files directly in `backups/`; one not there is left out), `outbox.pending`, `outbox.failed` and, with a row pending, `outbox.oldest_pending_s`; it is aborted once the servers stop, before the drain. The pipeline measures itself into the same recorder: every search `search.duration` (µs) by `arm` (`knn_memory`, `knn_episodic`, `knn_skill`, `lexical`, `identifiers`, `total`, each arm that ran) and `search.knn_retry` by `table` (`memory`, `episodic`, `skill`) when a window was searched again (`crates/clawg-core/src/memory/search.rs`); `POST /v1/search` the gauges `search.hits` and `search.withheld`; `POST /v1/context` `context.retrieval_state` by `state`, `context.prompt_bytes` and `context.cut` by `block` (`recent`, `long_term`, `last_session`, `conflicts`, `PromptBlock`, each block the budget took something out of); every take of a save `ingest.stage` (µs) by `stage` (`split`, `gate`, `embed`, `store`, `link`, the stages `ingest_pieces` runs, `split_event`, `gate_pieces`, `embed_pieces`, `store_pieces`, and the finish), `ingest.outcome` by `outcome` (`stored`, `retrying`, `partially_saved`, `failed`; a paused one none) and, stored, `ingest.pieces` and `ingest.end_to_end` (µs, from its outbox row's `created_at`), and the worker `ingest.queue_depth` as it takes each save (`crates/clawg-core/src/memory/worker.rs`); the model's session every batch `embedder.batch` (texts) and `embedder.batch_tokens` (what it runs over, padding included) by `role` (`query`, `passage`) and `embedder.wait` (µs, until its thread takes it), and every load `embedder.load` (µs) by `phase` (`verify`, a read of the cache with its hashes; `session`, the build of the embedder) (`crates/clawg-core/src/memory/embedder.rs`, `bootstrap.rs`); every refresh of a docs index `docs.refresh.duration` and `docs.refresh.files` by `state` (`indexed`, `unchanged`, `removed`, `failed`), and a docs search that waited for one `docs.search.inline_wait` (µs). A count is a gauge of 1, its samples the count. No label comes from a URL, a query, a body, a text, a path or an id. Histograms have fixed buckets per unit (`histogram.rs`), so minutes add up into any day, hour or version. The writer (`crates/clawg-cli/src/daemon/metrics.rs`) records the run (`run`: version, `dist_target`, profile, OS, CPUs, model, idle minutes, UTC offset) with `stopped_at_ms` null, writes each minute at the turn of the wall-clock minute in a blocking task, and on an orderly shutdown, after the drain, the last minute, the shutdown's event and `stopped_at_ms` within `METRICS_CLOSE` (1 s); a killed run keeps it null. Minutes older than 14 days fold into their hour, hours older than 400 days go (`prune`, at start and hourly). The rare things a run does are events (`crates/clawg-core/src/metrics/event.rs`): a kind of a closed set and a detail of numbers and `&'static str` labels, queued by `Recorder::event`, written with each minute into `event` (`metrics.db` schema 2, which a file of schema 1 gets when it is opened to write, keeping its rows; an older binary refuses the newer file untouched and writes no metrics until the next start) and dropped with the hours: `model_load` (`cause` `start`, `wake`, `call` or `recovery`, `outcome`, `ms`), `model_unload`, `embedder_recovery` (`idle_embedder.rs`, through `LoadWatch`), `model_download` (`result`, `bytes`, `ms`; a verified cache records none), `maintenance` (its time and counts), `backup` (`reason`, `ms`, `bytes`), `import` (`source`, `dry_run`, `ms`, counts), `outbox_failed` (`cause` `failure`, `gave_up` or `unparsable`) and `shutdown` (`http_ms`, `drain_ms`, `within_bounds`). The file is created `0600` on Unix; one SQLite does not recognise is kept as `metrics.db.corrupt-<ms>` and started again; a failure to open or write is one `warn` and no writing until the next start, never a failed request. `CLAWG_METRICS=off` writes nothing (the recorder and `GET /v1/metrics` go on).
- A project is a row of `project` (V27), the reference every table keys its rows by: an id that never changes, a name, how it was born (`migrated`, `root`, `adopted`, `import`) and whether the user reviewed it. A write of `memory` under an id `project` does not know adopts it in the same write (`born = 'adopted'`, two triggers; `crates/clawg-core/src/memory/registry.rs`). A folder, a row of `project_path` (the `project` table of before V27), is one way to reach a project: the root of a path (the nearest ancestor with a `.git`, a worktree's main repository, a submodule itself, or the folder outside git; `crates/clawg-core/src/memory/identity.rs`) with its root id, `index_docs`, the project it leads to and its fingerprints, its remote and its first commit (`git rev-list --max-parents=0 --first-parent HEAD` on the git directory the root names, without the caller's `GIT_*`, stopped after 1 s, and read only when no folder of the path recorded the stamp of that git directory: its creation time and, on Unix, its device and inode). The daemon gives a root its ids (`register_project`, `crates/clawg-core/src/memory/project.rs`), reading the disk on a blocking thread between passes of the transaction that writes (`Ground`, `Disk`). A path may hold several folders, one per repository there: a root settles on the first folder whose fingerprints are its checkout's (the remote decides when both sides know one, else the first commit), else on the oldest that neither contradicts, and one that contradicts every folder of its path gets a new folder (`fit`, `settle`), whose id is the first of `candidate_id(root, 0..64)` no other folder holds (0 being `derive_project_id`), so two roots whose 16-bit hash collides each get their own; the path's legacy ids join only a new path or its oldest folder. Its project id, under which its memories are read and written, is the one `project_remote` (V24) gives the key of its `origin` remote (`origin_key`: the URL of `[remote "origin"]` in the `config` of its git directory, normalized to `host/path` in lower case without scheme, user, password, port or `.git`; none for a path, `file://` or no `origin`), else the project of a checkout that moved to it, else the one its folder records, else a new project with its folder's id (`born = 'root'`). A move is a new path whose first commit was recorded, with no remote that contradicts it, only in folders of one project whose recorded checkouts are gone; when one is still there (a copy), two projects could be it, or a remote changed in place over the same first commit, the root stays apart and a suggestion is left in `project_suggestion`, once per pair whatever its order, logged, shown by `clawg projects list` and answered by `clawg projects merge` (`merged`) or `clawg projects keep-apart` (`apart`, which records the pair with reason `user` when none was pending, so no registration suggests it later). A new path that opens a new project also leaves a suggestion `folder_name` with each live project whose name has the key of the folder's name (`name_key`: lower case, letters and digits only, `crates/clawg-core/src/memory/registry.rs`) and whose recorded checkouts are all gone, looked at in the same pass as a move (`named_after_in`, `project.rs`): a folder without a VCS that moved. The pending suggestions of a project come back in `POST /v1/context` (`suggestions`), which `recall_context` turns into one line each and `session-start` into one line naming up to two, until someone answers them, the agent through `answer_suggestion`. So the clones of one remote share their memories, a fork is another project, a checkout without `origin` keeps its project when it is moved, and each folder keeps the docs index of its own checkout (keyed by its root id). A subfolder of a repository can be declared a project of its own (`project_subfolder`, V30; `crates/clawg-core/src/memory/subfolder.rs`): a row says that in the project of a repository, what is worked on inside a subpath (relative to the top of the checkout, the directory with the `.git`, so a worktree measures from itself; components joined by `/`) goes to another project; it keys on the repository's project, not on a remote, so every clone, a moved checkout and the store on another machine reach it, and both of its ids are read through `canonical`, so a merge rewrites none. A registration with `assigned` and `path` (the client's raw path, absolute) reads the path's subpath on the thread that reads the checkout (`Ground::subpath`, `subpath_of`, `crates/clawg-core/src/memory/identity.rs`; a path under another root, outside git or not absolute is logged and left out), settles the root as before (its legacy ids and its folder's id join the repository's project, `root_id` stays the folder's) and then answers in `project_id` the project the deepest declaration holding the subpath leads to, by whole components (the repository's own before a tombstone's, then the oldest; `deepest`, `declared_in`), without reading the subproject's declarations; a deleted subproject answers itself. `project_path` keeps holding roots alone, and the docs index of a subproject is its repository's. A project may have no folder: `resolve_project` (`registry.rs`, `POST /v1/projects/resolve`) reads a reference as an id (a tombstone's leads to its live project, a deleted one is itself and a save brings it back), else as the name of one live project in any case (two are `ambiguous`), else answers the projects whose name has its key, deleted ones marked, as `similar`; only when asked to create, with nothing similar or with `new_project`, it makes a project without a folder, `slug-4hex` (`new_project_id`), `born = 'agent'` unreviewed or `born = 'user'` reviewed. Registering a root whose project id is not its root id joins into the project the rows of its root id and of its legacy ids: `memory` through the move engine (`merge_in`, `crates/clawg-core/src/memory/relocate.rs`: every unit moves, clashes included, logged in `memory_move`, and then the project keeps the save of the newest live row of each `topic_key` and the oldest live row of each `content_hash` a moved row touches, the others `superseded` by it with cause `revision`, logged in `memory_move_supersede`, which `projects move --undo N` gives back first), the other two tables with `project_rekey`; a registration that moves rows first writes a `pre-rekey` snapshot and logs the move's number. Only a caller that sends `assigned: true` gets assigned ids; one that does not (a bridge from before) keeps the old rule: `derive_project_id(root)`, never follows a move, and gets 409 `project_root_collision` when that id is not the folder its fingerprints settle on or its path is contradicted (the daemon reads them for it too, and binds no remote). The bridge, the hooks and `projects add|move` use the ids the daemon answers, and all but `projects add` send the path they work in as `path` (the bridge its working directory, or the `project_path` or `to_project_path` of a tool, registering each root and path once per process, `ids_for`); `export --project` and `memories --here` read them from the store without writing, with the raw path too (`project_id_of`, `crates/clawg-core/src/memory/portability/export.rs`), and an import plans them alike, its disk reads off the connection's thread (`ReadAhead`), and places each project of the file (the `project` lines of one id) by the first of: a `--map-root` naming one of its folders (the project a registration gives NEW with its raw path), a remote of it `project_remote` binds here, its id when that is a project here it does not contradict (through `canonical`, so a tombstone's leads to its live project; a deleted one is itself), its name when one live project here has it in any case and neither side has fingerprints, the path of one of its folders recorded or present here and not contradicted, else a new project, with the file's id and name when both are free (else `new_project_id`), `born = 'import'` (`place`, `By`, `crates/clawg-core/src/memory/portability/projects.rs`); a line no row goes to creates nothing, but for the subproject of a declaration it writes. It records a folder present here as a registration would unless its checkout contradicts its project of the file, one of another machine with the file's remote and first commit and no stamp, and binds the file's remotes nobody binds; with a write it leaves the suggestions a registration of each folder it records would (`root_commit`, `remote_changed`, `folder_name`), `similar_name` with the live projects whose name has the key of one it placed and `merged_at_source` when the source merged two projects that are apart here, which a dry run reports without writing; it writes the declarations of the file between the projects their two sides went to, keeping one here under the same key; a row it inserts deleted leaves a deleted project deleted (its `deleted_at` and `reviewed` put back in the same transaction), a live one brings it back and the report says so; it never merges, splits or renames a project here. A project merged into another (`clawg projects merge`, V28, `crates/clawg-core/src/memory/merge.rs`) stays a row of `project` with `merged_into`, a tombstone, since open bridges keep its id for their whole session and old exports carry it: `canonical` leads past it to the live project (one hop, since a merge repoints the tombstones that led to its source; at most `MAX_MERGE_HOPS`, a cycle or a chain that ends in no project answering the id itself), at every daemon entry that reads under a project (`live_project`, `crates/clawg-cli/src/daemon/api.rs`) and inside the transaction of every writer (the worker as a save starts, `follow_merge`; the target of a move or a `PATCH`, `target_in`; the origin of a move's undo; a registration, its read-only planning and an import); a test reads `router()` and fails on a route `PROJECT_INPUTS` (`crates/clawg-cli/tests/api.rs`) does not classify by the project it takes. What manages projects refuses a tombstone instead, 409 `project_merged` naming the live one: renaming it, keeping it apart, merging into it, a move `from_project` it; and undoing the move of a merge alone is 409 `part_of_merge`. A project can be deleted (`project.deleted_at`, V29; `crates/clawg-core/src/memory/project_delete.rs`): its row stays, since its deleted rows stay under its id and `undelete` restores into it, and it is not listed while its name is free (its id is not). An empty one (no row of `memory`, `episodic_trajectory` or `procedural_skill` with `deleted_at` NULL, `superseded` ones counting as live) is deleted at once. One with live rows is answered a report with `refused: "not_empty"` (a 200: the report carries what the CLI prints) that names the projects to empty it into, the `duplicates` of its facts read in the same transaction plus its pending suggestions. Deleting it with its rows takes two steps: a report whose code (`code_of`: the first 8 hex digits of the SHA-256 of its id, the root ids of its folders, its remotes and the id, `status`, `deleted_at` and `update_count` of every row of the three tables, never a text or a `last_modified_at`) the second step sends back, compared in a pass that writes nothing (a code that is not the set's answers the new report with `refused: "code_changed"`, writing nothing), then a `pre-delete` snapshot, then a second comparison and one transaction that marks every live row deleted at once, so no older version of a topic comes back, drops their vectors, releases the rows outside that disputed them, journals the whole set (`project_delete`, `project_delete_row` with the `deleted_at` each row had, `project_delete_folder`), turns off `index_docs` and empties the docs index of its folders (`drop_root_index_in`). Both steps wait for the saves of the project in the outbox, up to `SAVES_WAIT`, but the report does not. A live row written under a deleted project's id brings it back, unreviewed, whoever writes it (`memory_project_ai`, `memory_project_au` and `memory_project_restored`, V29: a save of a bridge opened before the delete, a replay of the outbox, an import, a move and its undo, `undelete`); registering one of its folders, searching, asking for a context or registering a session does not, and what the delete deleted, its folders' `index_docs` and its open delete stay as they were. `undo_delete_core` restores, in X, the rows the delete deleted that are as it left them, with their vectors computed first (batches of 32) and the `status`, `update_count` and `last_modified_at` they had, turns `index_docs` back on and writes a `pre-undo` snapshot; it keeps deleted, naming why in `kept`, the rows `undelete` would refuse (`live_twin`, `topic_taken`, `holds_secret`), those that changed (`changed`) and those tied to a piece of their save that stays (`tied`), and it needs the model only when it has rows to restore. What manages projects refuses a deleted one, 409 `project_deleted` whose `detail` names its open delete and its `--undo` (`deleted_message`): renaming it, keeping it apart, merging it or into it, undoing a merge into it, a move or a `PATCH` `to_project` it; a move `from_project` it is accepted.
- `sharing.json` in the data directory holds which agents do not read which agents' memories (`crates/clawg-core/src/memory/sharing.rs`), `*` standing for every agent. Missing means every agent reads every other; an invalid file shares nothing. A row no agent saved (`agent_id` NULL, as a `global` or `project` row) is read by every agent whatever the file says. What an agent reaches (`Reader`: its id and its `Reach`, read by `reader_in`) is the one rule for reading and for changing: `agent_id` says who saved a row, never who may read it whole, change, delete, restore or judge it, and the rules that compare a save with what is stored (dedup, the detector, `topic_key`, `synthesize`) apply to its project within what the saver reaches, whoever saved the rows. The daemon reads it on every call that names an agent, and the worker on every save (`MemoryStore::reader_for`). `hide '*' '*'` leaves every agent its own rows and the ones no agent saved. The workspace, RECENT, the registered session and the hook's reminder stay each agent's own.
- `preferences.json` in the data directory holds the user's preferences (`crates/clawg-core/src/preferences.rs`): `{"version": 1, "language": "es"|"en"}`, `deny_unknown_fields`, written through a temporary file and a rename, never in `memory.db`, a snapshot or an export. Without it, or with one that cannot be read (`language_in` logs it and reads it as none), clawg behaves as before preferences, and only `doctor` names a broken file. The language is the one memories are saved and searched in and the agent answers the user in: the bridge reads it once at start (`ClawgMcp::with_language`), so a session keeps the language it was opened in; `session-start` and every command that prints for the user read it when they run (`language`, `crates/clawg-cli/src/main.rs`). The commands speak it, one `match` on `Lang` per sentence: each `message` of `doctor`, and what `update`, `setup`, `secrets`, `purge`, `export`, `import`, `restore`, `undelete`, `outbox`, `projects`, `sharing`, `metrics report`, `memories`, `stop` and `clawg preferences` print. Identifiers stay as they are (`check_id`, `reason_code`, `evidence`, `safe_next_step`, JSON keys, states, memory types, commands, exit codes), as does the technical cause of a failure, shown as it came inside the sentence that frames it (a typed error's `Display`, an I/O, SQLite or HTTP error, the cause of a failed `update` step), `clap`'s help, the logs, `clawg serve` and `clawg path`; without a preference every sentence is the English one of before.

## Commands

- `clawg serve [--profile P] [--port N]`: run the daemon on the profile's socket and on TCP as above (`--port 0` binds an ephemeral port) until Ctrl-C, SIGTERM (Unix; Windows console events are not handled) or `POST /v1/shutdown`, each an orderly shutdown that exits 0. Every phase of a shutdown has a bound: the requests in flight `HTTP_GRACE` (3 s, then cut), the drain `DRAIN_DEADLINE` (10 s), the save in flight, access flush and checkpoint `AFTER_DRAIN` (7 s, then left to the outbox and the WAL), the last minute of metrics `METRICS_CLOSE` (1 s) and the blocking tasks the process waits for, a model load among them, `RUNTIME_TEARDOWN` (2 s). A shutdown that finished within its bounds then closes `memory.db` and waits for the close (`MemoryRuntime::close`), so SQLite removes `-wal` and `-shm` before the process exits; left to the last handle's drop, the exit could cut the close halfway and leave an empty `-wal`. Its first log line names its version, and its `dist_target` when it has one (`starting_line`). A daemon clawg starts (a bridge's autostart, `update`) writes stdout and stderr to `<data>/logs/serve.log`, which is rotated when it is opened, never while a daemon writes to it: past `SERVE_LOG_LIMIT` (10 MiB) `serve.log.1` becomes `serve.log.2` and `serve.log` becomes `serve.log.1`, so three files are kept (`crates/clawg-cli/src/serve_log.rs`); a rotation that fails is written to the log, and the daemon starts anyway. One started by hand logs where it is told. `RUST_LOG=info,clawg_core::memory::search=debug` adds each search's `retrieval=` line without the rest of `debug`.
- `clawg mcp [--profile P] [--no-autostart] [--agent NAME]`: stdio MCP bridge to the daemon; starts one if none is running unless `--no-autostart`. When a call is refused (401 or connection refused) or the start gave up, it reads `daemon.json` and `token` again and repeats the call once, but never starts a daemon mid-session (`crates/clawg-cli/src/mcp/startup.rs`). The agent id is `--agent`, else the client's `clientInfo.name`, else `mcp`.
- `clawg hook session-start|user-prompt-submit --agent NAME [--profile P]`: answer the client's lifecycle hook (JSON on stdin, `hookSpecificOutput.additionalContext` on stdout; `crates/clawg-cli/src/hook.rs`). Both register the root of the input's `cwd`, with `cwd` as `path` (`POST /v1/projects`, without `index_docs`), and read under the project id the daemon gives (a declared subfolder's when `cwd` is in one) (the id derived from the root when the registration fails, nothing on a 409), and register the input's `session_id` with the daemon for `--agent` and that project, so the saves that follow carry it (`POST /v1/sessions`). `session-start` injects the context without a query for the project of the input's `cwd`, saying when the source was `compact`, when the model failed to load, when 20 or more memories wait for `synthesize`, when a conclusion lost a source since the last review and when the project has pending suggestions (`suggestion_note`); `user-prompt-submit` says how long the project has gone without a save once it is 30 minutes or more, counted from the later of the last save of the agent there and the creation of `transcript_path`. `--agent` must be the bridge's. With a language preference, `session-start` opens with a line naming the user's language, to answer in it unless they write in another and to save and search in it (`language_line`), and prints that line alone when the rest gives nothing; both events read the preference at every event and speak it, and `session-start` asks for its context in it (`lang`). It never starts a daemon: no daemon, an error or no answer within 3 s, or input that is not JSON or over 1 MiB prints nothing (or the language line alone) and exits 0; a usage error or a refused profile exits 1, never 2, which the client reads as "block".
- `clawg preferences [set language es|en | unset language] [--profile P]`: show or change `preferences.json` without the daemon or the store (`crates/clawg-cli/src/preferences.rs`); a change reaches the Claude Code sessions opened after it, and `clawg setup claude-code` rewrites the protocol block. It speaks the language it leaves set, one `match` on `Lang` per sentence. An invalid file is never overwritten: `set` and `unset` exit 1 naming the cause.
- `clawg status [--profile P]`: print daemon state and health as JSON; exit 1 if not running.
- `clawg stop [--profile P]`: stop the daemon and wait for the process to exit, at most `STOP_TIMEOUT` (30 s), which a test keeps 5 s above the sum of the shutdown's phases (`crates/clawg-cli/src/stop.rs`).
- `clawg backup [--profile P]`: write a snapshot of `memory.db` to `<data>/backups` and print its path; goes through the daemon when one is running.
- `clawg restore <FILE> [--profile P]`: replace `memory.db` with a snapshot. The daemon must be stopped; the replaced store is snapshotted first. A file with a non-empty `-wal` beside it is refused, since only the file is copied in.
- `clawg export --out FILE [--project PATH] [--agent A] [--include-deleted] [--format jsonl|markdown] [--profile P]`: write the `memory` rows to FILE in the `clawg-memories` format version 1 (`crates/clawg-core/src/memory/portability/format.rs`): JSON Lines, a header with the format, its own version (not the schema's), the clawg version and the source model, then `project` (one line per project: `id`, `root_path` of its oldest folder, absent without one, `name`, `folders` with each `remote` and `root_commit` recorded, `remotes`, `merged_into` for a tombstone and `subfolders` it declares, an empty field left out; a line for each project of an exported row, each tombstone leading to one, each repository declaring a subfolder as one and each subproject one declares; a store before V27 writes one line per folder as before; never `deleted_at`, `born`, `reviewed`, `index_docs`), `memory` (every column but `content_hash`, ids of the source store, `lang` among them, which an import reads again from the text, and `origin_project`, `null` for a store older than V23), `derivation`, `piece` and `conflict` lines (each pair with `topic_key_warned`, false for a store older than V19 or a line without it), a link only with the row that holds it and a pair only with both sides; a reader ignores fields it does not know. Read-only and without the lock, like `secrets`, so it works with the daemon running; a store of an older schema is read with the columns it has, a newer or diverged one is refused. `--project` resolves the root as a bridge does and reads its project id from the store, the one a declared subfolder leads PATH to when it is in one (a store before V30 has none); without `--include-deleted` deleted rows stay out. FILE must not exist and is created `0600` on Unix; the output counts what it wrote (the projects among it, and those without a folder), warns that the text is as stored (`clawg secrets` lists secrets) and names the saves still in the outbox, which do not travel, nor do `episodic_trajectory` and `procedural_skill`. `--format markdown` writes a view by project and type that `import` does not read.
- `clawg import [--from clawg|engram] FILE [--dry-run] [--agent A] [--map-root OLD=NEW]... [--project-map NAME=PATH|NAME=project:REF]... [--profile P]`: send an export to the running daemon (`POST /v1/import`; never starts one), which writes a `pre-import` snapshot and inserts each row as it was (dates, accesses, tier, importance, state, `source`, `origin_project`, links translated to the new ids), masked and hashed again, indexed unless deleted, re-embedded unless deleted (behind its piece's head), without running the detector (`crates/clawg-core/src/memory/portability/import.rs`). It embeds the rows with the most tokens first, counted by the daemon's tokenizer in groups on a blocking thread, ties in the file's order, in calls of `EMBED_BATCH` (32) texts (`longest_first`, `embedding_order`), so a run of the embedder pads its texts to little more than their own length; each vector is kept by its row's id, so the order changes no vector, row, id or report. `--map-root` only goes with `--from clawg` (the default) and `--project-map` only with another tool, a usage error otherwise (`Cli::parse_args`). Rows of a project of the file go where the data profile's project paragraph says an import places it (the map, a remote, the id, the name, a path, a new project; the CLI sends each map's root and raw path, absolute and canonical, as an object, so a path in a declared subfolder leads to its project and a daemon from before refuses the body; an id a registration gave another root meanwhile keeps that project's rows out); a row whose project has no line keeps its id, the import creating that project when `project` lacks it; `--agent` replaces every row's agent but the `project`/`global` ones. A row with the same agent, project, masked hash and `created_at` is already here and is not inserted (its links are only filled where empty, and a save gets its pieces only when none of its rows has one), so a second import adds nothing; a row of a clawg file not present in its project is present too when a row of any project here, deleted or not, has its agent, masked hash, `created_at` and `created_by_ref` (`PRESENT_ELSEWHERE_SQL`, over `idx_memory_created_at`, V31), so importing again after a `projects move` adds nothing, counted in `present_elsewhere` by the project it is in; a live row whose text is live in its project here, whoever saved it, merges into that row; a live row whose `topic_key` a live row of its project here holds is stored `superseded` by it (`revision`). An unknown format or version is a 400 that writes nothing; an invalid line is reported with its number and the rest imported; a link whose other end is neither in the file nor here is dropped and reported. `--dry-run` reports the same without writing, embedding or snapshotting. The file is at most `MAX_IMPORT_BYTES` (256 MiB). With `--from engram` FILE is what `engram export --all FILE` writes, to a file outside the repository since it holds every note as stored (without `--all` newer versions export only the project of the directory they run in, and the file does not say so; a partial or empty export imports, and `--dry-run` shows its notes by project of the source). The daemon reads it with the adapter (`portability/engram.rs`, versions `0.1.0` and `0.2.0`, into the model of `foreign.rs`) before asking for the model, and `translate.rs` makes each note (an observation, a prompt, the summary of a session) the rows a save of its text stores: title and content masked whole and split by the daemon's tokenizer, with the head of the save, under the agent `migrated` (or `--agent`; it names the author and nothing else), `source = 'import'`, the note's origin in `created_by_ref` (`engram:<sync_id>`) and its project of the source in `origin_project` (V23, indexed, with `created_by_ref` indexed for the rows of `source = 'import'`), typed (`decision` and `architecture` as `architectural_decision`, `preference` as `user_preference`, a prompt as `chat_message`, a summary as `session_summary`, any other as `semantic_fact`), dated by its text (`updated_at`, a later or unreadable date clamped to the import's), with `duplicate_count` as its accesses, importance 9 when pinned, deleted when the source deleted it, its key rewritten into one clawg takes and qualified by its project of the source when two of those share it in one project here, the notes of one project of the source with one masked text stored once, and its relations as `memory_conflict` pairs (`supersedes` over a preference or a decision the user did not mark is escalated; a relation with an end outside the export is counted). `--project-map NAME=PATH` stores the notes of project NAME in the project a registration gives PATH's root with PATH as its raw path (resolved as a bridge does, a directory, refused before the file is read), and `--project-map NAME=project:REF` (split at the last `=project:`) in the project REF names, an id or the name of one live project, which the daemon resolves before reading the file (404, 409 `project_ambiguous`, 409 `project_deleted`) and checks again in the transaction that writes; a note of a project not named, of none or `personal` is stored in no project, and `clawg projects move --origin-project NAME` places it later. A second import finds each note by its origin wherever it is now: with a row of its date (or without a date of its own), deleted here or deleted at the source it is present and changes nothing; with other dates it is a rewrite, stored in the project and under the key of the latest version here, a newer one replacing the live rows it does not share in the transaction that stores it, an older one stored under them. The pass that decides where each row goes, all a dry run does, loads what it reads of the store in calls of `LOAD_BATCH` (256) index seeks and decides on a blocking thread, writing nothing, so other calls go on meanwhile; rows are then written in transactions of whole notes. The report counts inserted rows by language (`by_lang`, for a clawg file too), names each project of the file with where it went, the step that decided it and whether it created or brought it back (`projects`), the suggestions it left (`suggestions`) and the declarations written or not (`subfolders`), and, in `foreign`, says by note what became of each and counts what has no place in clawg, by field; with new projects or suggestions the output ends with `clawg projects list`. Every write of an import is journaled in its transaction (V26, `crates/clawg-core/src/memory/portability/import.rs`, `Journal`): `memory_import` numbers each import that writes anything (`MAX + 1`, taken by its first write; a dry run or an import that adds nothing has none) with its start, its end (NULL when the process died before the links), its source and its snapshot; `memory_import_row` each row it inserted with the `update_count`, `deleted_at` and `supersede_cause` it left; `memory_import_supersede` each row a newer version of its note replaced, with the state it had; and `memory_import_extra`, only where the write added something, the links it filled in rows it did not insert, every pair, the derivations and pieces of rows it did not insert, and the roots and remotes it recorded; and `memory_import_registry` (V31) the projects it created, the deleted ones it brought back with their `deleted_at`, the suggestions it left and the declarations it wrote. The report names the number in `import_id` and the output the command that undoes it; the imports this process is writing hold their number in `MemoryStore::importing`. Each step of an import logs an `info` line as it ends (`crates/clawg-core/src/memory/portability/timing.rs`): `read` in the handler, `plan`, `prepare` (a clawg file) or `translate` (another tool's), `load`, `decide` (where a dry run ends), `embed` (counting the rows' tokens included), `snapshot`, `write` and `links`, with its seconds and what it went through (rows, embedding batches and rows/s, calls) and, in the daemon, the private memory of the process as it ended, and for the steps on the connection the time inside SQLite apart from the wait in its queue and the call that held it longest; a successful import closes with `import: done in …` and every step, to set against `http.duration{route=/v1/import}`. Names and numbers only, and neither the report nor what is written changes.
- `clawg import --undo N [--dry-run] [--profile P]`: take import N back through the running daemon (`POST /v1/import/undo`; never starts one; `crates/clawg-core/src/memory/portability/undo.rs`), keeping what was saved after it. A row the import inserted is removed for good (the row, its vector, its piece links, its derivations and its pairs; the text index trigger takes its terms out), not marked deleted, so the same file imports again; it stays, named with why in `kept`, when its `update_count` or `deleted_at` moved (`edited`, `deleted`, `restored`), when a verdict replaced it or a pair of it is not as the import wrote it (`judged`), when a row that stays names it by `superseded_by`, `revived_from`, `disputed_against` or as the source of a conclusion, but for a link the import itself wrote in a row that was here (`referenced`), or when it is a piece of a save with a row that stays (`tied`), until nothing more is kept (`decide`, pure). Its project, tier, accesses, `last_modified_at` and a later revision by key are no sign. What the import changed in other rows comes back only where it is still as it left it: a replaced row returns to its state when its replacement goes, a filled link to NULL, an added pair (unjudged), derivation or piece goes unless a kept row holds it, a recorded root or remote goes when no row of any kind uses it and the root has neither `index_docs` nor indexed files; in the last transaction, a declaration it wrote goes while it still leads where it wrote it, a suggestion it left while unanswered, a project it brought back is deleted again with its `deleted_at` while live, unreviewed, without live rows and its delete still open, and a project it created goes when nothing names it (no row of the three tables in any state, folder, remote, declaration, tombstone, suggestion, merge or delete journal or `synthesis_review`) and it is still unreviewed; what stays is named in `registry.kept` (`in_use`, `answered`, `reviewed`, `changed`). An import from before V31 keeps what it added to the registry. The store is read in calls of `LOAD_BATCH` seeks and written in transactions of `WRITE_BATCH` rows, each reading again the columns of its rows, so an edit that came in between keeps its row; a `pre-undo` snapshot comes first when there is anything to undo. What was taken back leaves the journal and what stayed is weighed again by the next undo, so a second one changes nothing. An unknown N is a 404, an import still being written a 409, and an import cut short is undone as any. `--undo` takes no file, `--from`, `--agent`, `--map-root` or `--project-map`; `--dry-run` reports the same without writing. Imports from before V26 have no journal and only their snapshot.
- `clawg secrets [--profile P]`: list the `memory` rows, live or deleted, and the verdict reasons of `memory_conflict` that hold a secret of a known format, by id and kind and never the secret. Read-only; works with the daemon running. `--mask-reasons --yes` instead replaces the secrets of every stored reason with their placeholders, then rebuilds the file and empties the WAL as `purge` does; the daemon must be stopped and no snapshot is taken.
- `clawg purge <ID> --yes [--profile P]`: remove one `memory` row for good (text, vector, index terms, the head of its long save kept in `memory_piece.context` when it is the first piece, free pages and WAL) and the outbox rows of its own agent's save: the one with the same text, or for a piece of a long save the ones that contain it. A live row is deleted first, so the revision of its topic it replaced comes back as a delete would bring it. It names what came back, the rows a verdict keeps replaced, the other pieces of its save, the outbox rows it removed by `operation_id`, and the backups and `workspace.md` files (AUTO section or the user's part) that still hold the text, changing none of them. A conclusion drawn from it keeps the link to its id, which `synthesize` lists as `purged`. The daemon must be stopped; no snapshot is taken.
- `clawg purge --project-delete N --yes [--profile P]`: remove for good what delete N left (`purge_delete`, `crates/clawg-core/src/memory/secrets.rs`), under the rules of `clawg purge <ID>` (the daemon stopped, `--yes` for both forms or it refuses before opening anything, no snapshot, nothing written before every check passes; an unknown, an undone and a purged delete are refused, `PurgeError::{UnknownDelete, DeleteUndone, DeletePurged}`). In one transaction it removes every row of `project_delete_row` that is still deleted, wherever it is now, in the three tables (the row, its vector and, for `memory`, what `purge` removes of a deleted row: `remove_in`), names the ones live again, which stay, empties again the docs index under the folders of `project_delete_folder` still at `index_docs = 0`, and sets `purged_at`; the project stays as it is. After the commit it merges both text indexes (`memory_fts` and `project_doc_fts`), runs `VACUUM` and empties the WAL, once. The report (`purge_delete_report`) counts the rows removed by table and names the outbox rows removed, the rows left live, the snapshots that still hold any of the rows (one pass, `pre-delete` among them), the project's own `workspace.md` files and the other ones that hold a removed text, changing none.
- `clawg undelete <ID> [--profile P]`: bring back a deleted `memory` row through the running daemon, which embeds it again; refused when the same text was saved again since, when a live row of another save holds its `topic_key` (not one its own delete brought back), or the row holds a secret; it prints what it supersedes again and the rows saved meanwhile it was paired with.
- `clawg outbox retry|discard <OPERATION_ID> [--agent NAME] [--profile P]`: through the running daemon, take a `failed` save back to pending with its progress and no attempt spent and queue it (written again under another row id), or drop it after deleting the memories it inserted, which `undelete` brings back (`crates/clawg-cli/src/outbox.rs`). `--agent` is needed only when two agents used the operation id; a `pending` row is refused.
- `clawg metrics report (--metric M [--label K=V]... [--by day|hour|minute|version] | --events) [--since Nd|Nh] [--profile P]`: read `metrics.db` read-only, without the daemon or the store's lock, and print as JSON the metric summed by local day, hour of the local day (`00` to `23`), local minute (`YYYY-MM-DD HH:MM`, from no earlier than the first whole hour of the 14 days kept by minute, `since_for`) or version (default; versions in the order they first ran), from `--since` (default `30d`), keeping the series that hold every `--label` (`crates/clawg-cli/src/metrics.rs`, grouping in `crates/clawg-core/src/metrics/report.rs`): `count`, `mean`, `min`, `max`, `p50`, `p95`, `p99` for a histogram, `samples`, `mean`, `min`, `max` for a gauge, each group with its `runs` and `not_stopped`, and `runs` (`total`, `not_stopped`: killed, crashed or still running) over every run started since. The local time of a row is its run's offset. `--events` prints instead, by run (its version, start and stop), the events from `--since` on, oldest first, and takes no metric, label or grouping. Without the file, or without the metric (the error lists the names), exit 1.
- `clawg memories list|search|show|stats [--profile P]`: read-only viewer through the running daemon; `list --deleted` lists deleted rows, most recently deleted first; `list` and `search` take `--no-project` for the rows saved in no project, and `--here` reads the project of the working directory from the store; `list --origin-project NAME` lists the rows another tool's project NAME gave.
- `clawg projects list [--profile P]`: list every project through the running daemon (`GET /v1/projects`; never starts one; `crates/clawg-cli/src/projects.rs`), by name: how many memories it holds, how it was born when nobody reviewed it, its folders (those no longer there marked), its remotes, the subfolders declared as it with their paths here (those not there marked; such a project is not printed as without a folder) and, under a repository, each of its declarations with the project it leads to, the projects merged into it with the command that undoes each merge, its pending suggestions with the other project and why, and a project without a folder as such; neither a tombstone nor a deleted project is listed, with a suggestion pending the listing ends with the two commands that answer it, and then it ends with the open deletes (`render_listing`), each with its `clawg projects delete --undo N` and, when it left deleted rows, its `clawg purge --project-delete N --yes`, saying so when a save brought the project back into use.
- `clawg projects rename <ID> <NAME> [--profile P]`: give a project a name, without the spaces around it, and mark it reviewed, through the running daemon (`PATCH /v1/projects/{id}`); its id, and what was saved under it, stays. A refusal (no such project, an empty name, one over 80 characters or with control characters, the name or the id of another project in any case) names the id, with the daemon's cause as it came.
- `clawg projects create <NAME> [--new] [--profile P]`: create a project without a folder through the running daemon (`POST /v1/projects/resolve` with `born: user`; never starts one): a name a live project has prints that project, one whose key other projects' names have prints them (deleted ones with their `--undo`) and `--new` creates one apart (exit 1 without it); `render_created`, `crates/clawg-cli/src/projects.rs`.
- `clawg projects locate <PROJECT> <PATH> [--subfolder] [--profile P]`: make the folder PATH is in lead to PROJECT, by id or by name, through the running daemon (`POST /v1/projects/locate`): the root is registered as a bridge registers it, and the project it gets, when another and with that folder alone, is merged into PROJECT as `projects merge` does, which `--undo` takes back; a project with other folders is 409 `folder_shared` naming the merge it would take. With `--subfolder`, PATH itself, a subfolder of a repository, is declared as PROJECT (`declare_subfolder`, `crates/clawg-core/src/memory/subfolder.rs`), sent absolute and not raised to its root: the top of a checkout or a path outside one is a 400; naming the repository's own project removes the declaration (`removed`, with the project it led to in `previous`); one that leads to PROJECT already writes nothing; one that led to a project nothing else reaches (no folder, no remote, no other declaration) merges that project into PROJECT, and otherwise it is 409 `folder_shared`; a tombstone or a deleted PROJECT is 409 `project_merged` or `project_deleted`. It moves no memory: the output names `clawg projects move --from-project P --to-project X --text WORDS --dry-run` for what was saved there before, says that a session opened before keeps the repository's project until it restarts, and after a removal names `clawg projects merge X --into P --dry-run` (`render_declared`, `crates/clawg-cli/src/projects.rs`).
- `clawg projects merge <SOURCE> --into <TARGET> [--dry-run] [--profile P]` and `clawg projects merge --undo N [--dry-run] [--profile P]`: merge one project into another, or take merge N back, through the running daemon (`POST /v1/projects/merge`; never starts one; `merge_core` and `undo_merge_core`, `crates/clawg-core/src/memory/merge.rs`). A merge waits up to `SAVES_WAIT` (5 s) for the saves of either project still in the outbox (the worker reads a save's project more than once), then refuses with 409 `saves_pending`; after a `pre-merge` snapshot, in one transaction that decides again what a pass writing nothing found, every `memory` row of SOURCE, deleted ones too, goes to TARGET with the part of its unit that is there (`merge_in` with `Span::Carry`: the part of a unit in another project stays there, named in `split`; a registration's join keeps such a unit whole, `Span::Keep`), reconciled as a registration's join and logged under one `memory_move`; its trajectories and skills, its `synthesis_review` rows (the older review kept where TARGET has one, so no reminder is lost), its folders, its remotes and the tombstones that led to it follow; the suggestions whose sides became one are answered `merged`; SOURCE becomes a tombstone and TARGET reviewed, and each change is journaled with what it was (`project_merge`, `project_merge_change`). Then each agent's `workspace.md` of SOURCE is copied where TARGET has none (`adopt_legacy`), SOURCE's own never changing. SOURCE already merged into TARGET is a repair: what is still under it moves. another tool's export is split by the model's tokenizer, so without it, a dry run too, it is a 503 `tokenizer_not_ready`; answers the import report), `POST /v1/disputes/judge` (`keep`, `other`, `verdict` one of `supersedes`, `compatible`, `scoped` with a `reason`, or `conflicts`; `user_answered` with the user's answer in `reason`, else a 400; optional `agent_id`, as `?agent=`, both rows in its reach), `POST /v1/disputes/resolve` (the same with `keep_both` instead of a verdict, for older bridges), `GET /v1/disputes?agent_id=&project_id=` (pending and escalated pairs both of whose rows the agent reaches, whose newer row the project reaches as a search reads it, counted, the five oldest pending named with each side's provenance mark), `POST /v1/synthesis` (memories of the scope no conclusion of any author covers yet, the conclusions already drawn, and in `to_review` the live ones with a source deleted, replaced or purged, each with `live` and its `lost` sources, at most 10 newest first, `to_review_total` counting them; optional `agent_id`, as `?agent=`; the review is the project's, `synthesis_review.agent_id` `''`, so one agent's turns the reminder off for all; `POST /v1/context` answers `unreviewed` and `conclusions_to_review`, those that lost a source after the scope's last synthesis, which `recall_context` and `session-start` turn into a line from 1; `crates/clawg-core/src/memory/synthesis.rs`), `POST /v1/outbox/retry` and `POST /v1/outbox/discard` (`operation_id`, optional `agent_id`; 404 without a row, 409 for a `pending` one or an id two agents share), `POST /v1/shutdown`.

A project's docs index (`crates/clawg-core/src/memory/project_docs/`) holds its Markdown and manifests (`Cargo.toml`, `package.json`, `pyproject.toml`, `go.mod`) as passages split by heading, each under its breadcrumb (`path > heading > subheading`), and its Rust, Python and TypeScript code split along the syntax tree (tree-sitter), each piece under its path and the headers of the definitions that contain it (`path > impl Store`). It honours `.gitignore`, is derived from disk in its own tables and never touches `memory`; a file is re-read when its sha256 or the model changes. A changed doc keeps the stored vector of each of its passages whose whole `indexed_text` (breadcrumb, a blank line, body) is in the same doc's stored passages, when the doc was embedded by the refresh's `model_id`, read by value and not by row id (a repeated text takes the first one's blob in every passage that has it); only the rest is embedded, and the doc is still replaced whole in one transaction, so it equals a full reindex. A new doc, a moved file (its path is in the text) or a doc of another model reuses nothing, and `RefreshReport::reused` counts the passages kept, which the `indexed the docs of …` log line ends with (`refresh_line`, `crates/clawg-cli/src/daemon/api.rs`). A doc whose vector the embedder returns unusable is left as it was, logged and tried again by the next refresh, without stopping the other docs (`RefreshReport::failed`); a failing embedder or store still ends the refresh. Only a root marked `index_docs` in `project` is read: the bridge asks for it for its own root alone, and only when that root has a `.git` or one of those manifests and is not the home directory or a filesystem root (`auto_indexable`, `crates/clawg-core/src/memory/project_docs/corpus.rs`; a root already marked stays marked), and `clawg projects add` for any other, so a `project_path` the model passes is a label for memories until the user adds it. A daemon from before assigned ids that answers 409 `project_root_collision` makes every tool that scopes to that root fail rather than mix two projects (`all_projects` still works); any other registration failure only logs a warning, and the bridge goes on with the id derived from the root.

Ingest masks secrets (`crates/clawg-core/src/memory/redact.rs`) before a save is chunked, hashed or embedded, and the docs index does the same with every passage; a confirmed save lists the masked kinds in `redacted`. It masks keys and tokens of known formats (an `sk-` or `hf_` key only when it mixes upper case, lower case and digits, so hyphenated identifiers and class names pass; Slack webhooks; PGP private key blocks), the literal value after a key ending in `password` or `passwd` (`password`), after a key ending in `secret`, `token`, `api_key`, `access_key`, `secret_key`, `account_key` or `auth_key`, in any case and with any prefix (`credential`, never a value of digits alone), and after `Authorization: Bearer|Basic|Token` (never a variable, a type, a call or a placeholder), and everything the writer wraps in a private mark, `<private>` to `</private>`. A mark left open masks to the end of the text; a mark right after a backtick is text. Nothing is guessed from entropy. The reason of a verdict and the error an outbox row records are masked the same way before they are stored. A rule added later reaches stored rows only through `clawg secrets`, and makes `undelete` refuse a deleted row it now flags.

A save is written, already masked, to the `ingest_outbox` table of `memory.db` before the daemon answers `201` or `202`, and its row goes in the transaction that finishes storing it (`crates/clawg-core/src/memory/outbox.rs`), so a kill, crash or power cut loses nothing accepted (the row alone is written with `synchronous = FULL`; the rest of the store keeps `NORMAL`). Each piece of a long save is noted in the row as it is stored, and a replay resumes after it. On start the daemon ingests pending rows before new saves. Each take of a row spends an attempt; a row is `failed`, with its cause, once it spent 3 takes that ended in a failure the embedder did not cause or with the process gone, or when its event no longer parses. A save the embedder could not take (`EmbedderUnavailable`) hands its attempt back and is taken again in the same run after 1 s, doubling up to 60 s, holding the queue so saves under one topic key still apply in order (`crates/clawg-core/src/memory/worker.rs`); a caller waiting for it gets `202` `retrying`. A caller waiting for a save that failed otherwise gets `500 ingest_failed` and its row is dropped when nothing was stored, and `202` `partially_saved` with the stored pieces in `memories` and the cause in `detail` when some were, its row kept for the next start to finish. A drain stops a save with a row before its next piece once its deadline passes (after the first piece each take stores), handing the attempt back, and the next start resumes it. `clawg outbox retry|discard` is the way out of `failed`. Every save answers with an `operation_id` (a UUID v4, or the caller's own, 1 to 128 visible ASCII characters); sending the same one again while its row exists answers `already_queued` (pending) or `ingest_failed` (failed) instead of saving twice. Shutdown no longer writes `ingest-pending.jsonl`; one left by an older clawg is imported masked on start and removed.

A save longer than one piece (480 tokens) is split into pieces of 96 tokens, neighbours sharing about 24, so one sentence is not averaged away in a long vector; every piece after the first is embedded behind the save's first 32 tokens, and `memory_piece` links the pieces (`crates/clawg-core/src/memory/pieces.rs`). With the tokenizer loaded, every cut of the splitter (pieces, head, chunks, the docs index, an import's notes) falls where a word starts, whitespace right before the token or at it, a token of whitespace alone opening the word after it (`word_starts`, `plan_word_windows`, `crates/clawg-core/src/memory/chunker/token_splitter.rs`): a window ends at the last word start under its cap, the next starts at the word start nearest the 24th token from that end, moved back while the two share fewer than the 16 characters `join_pieces` looks for (`MIN_OVERLAP_CHARS`), and a word longer than a piece or a text without spaces is cut by token. The byte fallback cuts as before. Saves split before at 424 tokens, or inside words, keep their pieces. Search fills its KNN pool with distinct saves, keeps the best piece of each and labels it `piece=K/N`. A save's `content` holds at most 64 KiB, counted in bytes as received (`MAX_CONTENT_BYTES`, `crates/clawg-cli/src/daemon/api.rs`): a longer one is a 400 before the outbox naming its size and the limit, since every piece rewrites the outbox row with the progress so far and what a save writes grows with the square of its length; `save_memory` and `protocol.md` say so.

A save may name a `topic_key` (`crates/clawg-core/src/memory/topic.rs`): lowercase segments of `[a-z0-9._-]` joined by `/`, at most 80 characters, anything else a 400 before the outbox. Its scope is the project, as for the dedup, whoever saved the rows, within what the saver reaches: a key names a topic of the project (V20 indexes both by `COALESCE(project_id, '')`). In the transaction that finishes the save (with its outbox row, or linking its pieces), every live row of that scope outside the save becomes `superseded` by the save's first row, except a piece of a save whose first piece is live without that key, which stays live and loses the key; the save's rows take the key, the rows it inserted the best tier and the most accesses of the replaced ones, and the type and importance it does not name come from the oldest live row of the scope. The detector never pairs a save with the rows it replaces, a save that fails replaces nothing, and the answer lists the replaced rows in `replaced` and echoes `topic_key`, so a bridge can tell a daemon that ignored it. A save without a key that the detector paired with a row of its project (`Candidate.same_scope`) names the closest of them in `revision_candidate` (`unkeyed_revision`), the transaction that finishes the save marks its pair with that row `topic_key_warned` (V19; no later verdict, key or delete clears it, and the export and import carry it, since following the line keys the save's own row, which then reads like a row keyed from the start; `mark_warned_in`, `topic.rs`), and `save_memory` adds the line `revision-eval` measured: if the save revises that row, save it again under a `topic_key`, which only gives its own row the key (`topic_key_warning`, `crates/clawg-cli/src/mcp/tools.rs`; a test in `revision-eval`'s `cost.rs` keeps it the measured line). Rows keep their content: the history is the chain of `superseded` rows, listed with `by=#N` and `topic=K`. `search_memory` and `read_memory` show a row's `topic=K` only where a save under it would revise it: a row of any author in the project a `save_memory` with the same `project_path` goes to (`read_memory`, which takes none, compares with the bridge's own; `revised_from`, `crates/clawg-cli/src/mcp/tools.rs`). A `user_preference` of another project, which a search reaches from any project, shows no key, nor does a row without a project unless the save has none either; a hit from a daemon that does not send `project_id` keeps it. Each `superseded` row records why in `supersede_cause` (`revision` or `verdict`, V17). Deleting the current row of a key, when no other live row of its project holds it, makes the newest save its revision replaced live again, whoever saved either, (`crates/clawg-core/src/memory/revival.rs`), marked `revived_from` the deleted row, and points the older ones at it; `DELETE` lists them in `revived`, and the rows a verdict replaced, which stay superseded, in `hidden`. Restoring the deleted row supersedes again what its delete brought back; a restored row superseded by a deleted revision comes back current under the same rule, and the maintenance pass applies it to what an older delete left.

The contradiction detector (`crates/clawg-core/src/memory/contradiction.rs`) measures closeness, not contradiction: each earlier row within the band that the saver reaches, of any author or none, becomes a pair in `memory_conflict`, one per pair of saves, written in the transaction of the new row. `needs_user` escalates a pair only when it is closer than `ESCALATE_BELOW` (0.40) and both sides are a `user_preference` or an `architectural_decision`, or closer than `IDENTIFIER_ESCALATE_BELOW` (0.30) and both texts share an identifier; an escalated pair, and only one, is named in the newer row's `disputed_against`, makes it `disputed` and shows in ACTIVE CONFLICTS to every agent that reaches both sides and is shown one of them. The rest are `pending`: the save's answer lists them in `related` for the agent to judge, and `memory_status` counts them. A verdict is kept in the pair (`crates/clawg-core/src/memory/dispute.rs`), `supersedes` whose `other` is a preference or a decision is a 409 in any state of the pair unless the call declares `user_answered` with the user's answer in `reason`, which the pair keeps as `user answered: <reason>` (a declaration, not an authentication; the protected row as `keep` needs none, so a verdict is undone as before), and a restored row brings its escalated pairs back.

Each save is sealed with who stated it (`crates/clawg-core/src/memory/provenance.rs`): `source = 'explicit'` and `created_by_type = 'agent'` unless the save declares `user_stated`, which makes it `user`, and `source = 'synthesis'` with `agent` when it names `derived_from`; `user_stated` with `derived_from` is a 400 before the outbox, as is a `derived_from` naming a memory that is missing, deleted, out of the saver's reach or `superseded` (the refusal names what replaced it), and an outbox row without the field is the agent's. Rows saved before the seal read `explicit` / `user` whoever stated them, so no reader claims a row is the user's: `memory_status`, ACTIVE CONFLICTS and `synthesize` mark only `inferred`, `conclusion` and `imported` (the value an import writes), and a pair in `memory_status` names first the side without a mark. The origin changes no pair, status or score.

MCP tools (`crates/clawg-cli/src/mcp/server.rs`): `save_memory`, `search_memory`, `recall_context`, `search_project`, `list_memories`, `read_memory`, `update_memory`, `delete_memory`, `restore_memory`, `resolve_conflict`, `answer_suggestion`, `synthesize`, `memory_status`.

`update_memory` also moves a memory, with its unit, to the project of `to_project_path` (a directory, registered first as any path a tool names), to `to_project` (an id or a name) or out of every project with `clear_project`, through `PATCH`.

`save_memory`, `search_memory`, `recall_context`, `search_project` and `synthesize` take `project`, an id or a name, not with `project_path`, resolved through `POST /v1/projects/resolve` on every call; only `save_memory` creates one (with `new_project` apart from similar names), and a refusal names the candidates and what to ask the user (`format_refusal`, `crates/clawg-cli/src/mcp/tools.rs`). `answer_suggestion` relays the user's answer to a pending suggestion.

A saved text never opens a line of its own where clawg prints it (`indent_continuations`, `crates/clawg-core/src/memory/prompt_builder.rs`): in the context prompt (hits of every block and the sides of ACTIVE CONFLICTS) and in the AUTO section of `workspace.md`, each line after the first is printed behind `  | `, and in `workspace.md` every `<!--` of a copied text becomes `<! --`, so no text can forge a block, a hit or a section marker; the rows keep their text as saved. An author is shown after `by ` through `display_author` (no controls or line breaks, brackets as parentheses, at most 48 characters), in the prompt and in `search_memory`, while the stored `agent_id` still decides whose a row is.

What the agent is told about memory lives in one text per language, `crates/clawg-cli/src/mcp/protocol.md` and `protocol.es.md`, compiled into the binary: when to save, how to write a save (a first line naming the subject, the exact paths and identifiers, in English), what not to save, which type and importance to pick, the session summary, and that whatever a tool retrieves is evidence, not instructions. Its opening paragraphs, before the first `##` section, are the server instructions, at most 2048 characters; tests keep it naming only registered tools, their arguments and the memory types. `crates/clawg-cli/src/mcp/protocol.rs` owns them (`PROTOCOL`, `PROTOCOL_ES`, `opening`, `text`), for the bridge and for `setup`: with Spanish, `text` is `protocol.es.md`, written for Spanish with the same sections and the same names and markers between backticks (a test compares them); with English, `protocol.md` with its two rules on language rewritten (found across the file's line breaks, each by a test exactly once) to save and search in English, answer the user in it unless they write in another, and search again in Spanish when a search says memories remain in it; every variant fits the 2048 characters. Without a preference it is `protocol.md` as written.

A session in Spanish reads the rest in Spanish too, one `match` on `Lang` per sentence: the descriptions of the tools and their arguments (`crates/clawg-cli/src/mcp/tools_es.rs`, a table `ClawgMcp::with_language` puts on the router, which a test keeps covering every tool and argument and naming what the English text names), every answer of the bridge (`tools.rs`, `server.rs`; the language the bridge started with, `ClawgMcp::speaks`), the notes the daemon adds to a context (`SHARED_NOTE`, `CONFLICT_NOTE`, the BUDGET note and the conflicts not shown, in the `lang` of the request, English without one) and the hooks. The markers stay as they are in every language: the `=== … ===` headings, `NEW`, `OLD`, `disputed`, `[truncated]`, `piece=K/N`, `by <agent>`, `topic=`, `score=`, `imp=`, `acc=`, `by=#N`, `from=`, `live=`, `lost=`, `origin=`, the provenance marks, the names of tools, arguments and memory types and the values of a status, as do the sentences the daemon returns in an error, which the bridge frames (`no se guardó: …`). `rag-eval` reads an empty answer in either language.

While a store holds both languages, `memory.lang` (V22: `en`, `es`, `und`, NULL until classified) says which one a row is in, as the detector `clawg_core::memory::language::detect` reads its masked text: function words of each language and the marks of Spanish, with code, paths and identifiers left out first, undecided on little evidence. The save (`PreparedRow`) and the import write it, from the row's own text and never from a file's `lang`; the maintenance pass classifies the rows left NULL in batches of 500 without touching anything else. `POST /v1/search` and `POST /v1/context` with a query take `lang` (`en` or `es`, anything else a 400) and then answer `other_language`, the live saves of the search's scope in the other language that the caller reaches (`count_saves_in`, over `idx_memory_lang`). A bridge with a preference sends its language and, when that count is above zero and the search showed fewer than `FEW_SHOWN` (3) memories, ends `search_memory` and `recall_context` with a line asking to search again with the query in the other language (`other_language_line`, `crates/clawg-cli/src/mcp/tools.rs`); with no memory left in the other language the line stops. `memory_status` names the session's language and says when `preferences.json` now says another. `save_memory` and `update_memory` list the seven memory types in their schemas, and `POST /v1/memories` refuses any other with a 400 that lists them, before the save reaches the outbox, as `PATCH` does; an outbox row written before that check still stores as `semantic_fact`.

## Code conventions

- Comments explain only a non-obvious why. No commented-out code, no `#[allow]` to hide dead code.
- Errors in library code are typed with `thiserror`.
- Unit tests sit next to the code in `#[cfg(test)] mod tests`; integration tests live in each crate's `tests/`.
- TDD: write the failing test first, then the code that makes it pass.
- Keep parsing/decision logic pure and separate from I/O so it is testable without a filesystem, port or database (see `cli.rs`, `Profile::resolve`).
- Do not add dependencies, visibility or abstractions without a real use.

## Rules for agents

- Code, comments, test names, error messages and commit messages never reference plans, phases or work packages.
- Everything committed is written for whoever clones the repository. A step says what it needs to run (an OS, the real model, the gitignored golden set in `docs/eval/`, a data profile), not whose machine it runs on; a decision says what was chosen and why, not who chose it. No person's name, username or home path in docs, code, tests or commit messages.
- Commits: conventional commits, atomic (each one compiles and passes the suite). No `Co-Authored-By` and no AI attribution.
- `docs/migration-plan.md` is a working log and is NEVER committed. Stage by explicit path; never `git add -A`, `git add .` or `git add -u`.
- Do not run release builds, installs, or touch the real data profiles (`~/.clawg*`) without explicit authorization.
- Do not kill running `clawg.exe` processes; they may be the editor's own MCP.
- Before testing a new version, clean the old builds out of the test build directory, and end every task with no build directory other than `target` and `target-test` (Build directories, under Testing).

## Versioning

- The version lives only in `[workspace.package] version` of the root `Cargo.toml`; every crate inherits it with `version.workspace = true`. Never set a version in a crate's own `Cargo.toml`.
- Bump it when work closes: an archived openspec change raises the minor (`0.4.0` → `0.5.0`), a fix outside openspec raises the patch (`0.4.0` → `0.4.1`).
- After the edit, run `cargo update --workspace`: it writes the new version into `Cargo.lock` without touching any dependency and without building. Commit both files together as `chore: bump version to X.Y.Z`; otherwise the lock trails one version behind, and CI, which builds with `--locked`, fails.
- Publishing is automatic. Merging a version bump to `main` runs CI; when CI passes for that push, `.github/workflows/release.yml` (triggered by `workflow_run`, never by a pull request) builds `clawg-cli` for `x86_64-pc-windows-msvc` and `x86_64-unknown-linux-gnu`, signs `SHA256SUMS` with minisign and creates the release `vX.Y.Z` on the commit CI ran on, with both binaries, `scripts/install.ps1`, `SHA256SUMS`, `SHA256SUMS.minisig` and a provenance attestation. A version that already has its tag publishes nothing, so a merge that does not bump the version releases nothing. Never create a tag or a release by hand, and never build a release locally to publish it.
- The release public keys are `release/minisign.pub` (primary) and `release/minisign-next.pub` (backup). The primary private key and its password are secrets of the `release` environment (`MINISIGN_SECRET_KEY`, `MINISIGN_PASSWORD`), limited to `main`; the backup private key is kept outside GitHub. Only the signing step of `release.yml` reads them, and `ci.yml` reads none.
- The version is not cosmetic: `clawg --version`, `GET /health`, the MCP `serverInfo` and `clawg doctor` report it, and `version_warning` (`crates/clawg-cli/src/memories.rs`) compares the running daemon's version with the CLI's to detect a stale daemon.

## Testing

```
cargo test --workspace
```

The bar is that the whole suite passes. Never record how many tests it has (in this file, the other agents' instruction files or `openspec/config.yaml`): the count goes stale with every change.

A test leaves nothing in the system temp dir, passed or failed. Dropping a store only signals its connection's thread, and on Windows a file still open cannot be deleted, so a directory removed right after loses the race in silence. In clawg-core a test takes its directory from `crate::test_dir::test_dir()`, which waits for the store's files and fails the test when a store still holds them: close a runtime (`MemoryRuntime::close`) or an ingest (`EvalIngest::finish`, then close) the test started. `rag-eval`'s tests use `TempPath` (`test_temp.rs`), and a run of `rag-eval` removes the store it seeds unless `--keep-store` keeps it. `CLAWG_KEEP_TEST_FILES` keeps the test paths and names each one on stderr, for a test whose files need a closer look.

`crates/clawg-cli/tests/binary.rs` runs the built `clawg` itself: a hard kill with a save still pending, two daemons on one store, `status`/`stop`, `backup`/`restore`, MCP over real stdio, a daemon restart under an open bridge, the socket (status, stop, bridge, hooks, an orphan left by a kill, a path over the limit, a taken profile port, an explicit `--port` that is taken, a shutdown that ends the listener), the metrics a daemon records over both transports and `metrics report` reads after `clawg stop` or a kill, the series of its pipeline and its events, the bridge's autostart, clients and updaters older than the socket, an update of a daemon that serves TCP alone, `doctor` beside a live daemon and an import of another tool's export; these run on Unix and on Windows, while the directory mode, the export's `0600`, SIGTERM, `write_executable`'s `chmod`, the `setup` scenarios with a shell `claude` and `admits_peer` are Unix only. Each test gets a temporary home through `CLAWG_TEST_HOME` and the fake model through `CLAWG_TEST_EMBEDDER=fake|stalled|blocked` (`fake` also gives the process a tokenizer of one token per word, `chunker::word_tokenizer`, as a model load gives the model's; `stalled` never finishes the download, `blocked` never returns from the load); only a build with clawg-core's `testing` feature (its dev-dependencies) reads them, never a release build, and `tests/conventions.rs` fails when a manifest enables `testing` outside `[dev-dependencies]`. Every daemon a test starts binds `--port 0`; one started without `--port` (by a bridge, by `update`, or a test of the socket) is kept off the profile's port by `CLAWG_TEST_DEFAULT_PORT=off`, which a `testing` build reads in place of that port (`off` or a port number). Each child is ended by its own handle, never by name. It takes about a second.

`crates/clawg-cli/tests/transport_bar.rs` (`#![cfg(windows)]`, its test `#[ignore]`, so CI never runs it) starts one `testing` daemon with `--port 0` that serves both transports and measures AF_UNIX against TCP in five scenarios: sequential, a new client per request, 8 concurrent tasks, a burst of 32 in 20 rounds and a list of about 8 KB. It fails when any AF_UNIX mean is over 1.10 times the TCP mean, or when the AF_UNIX burst has a failure: `cargo test -p clawg-cli --release --test transport_bar --target-dir target-test -- --ignored --nocapture`.

A `testing` build also stands in for what makes a binary a release, so `clawg update` can be driven without the network or a real release: a stamp after the end of a copied binary (`0x00`, `CLAWG-TEST-STAMP`, a JSON object up to the end of the file; `version`, `dist_target`, `migrations_up_to` (the newest migration the binary knows and applies, as if it were an older release) and `serve_fault`, `before_open` or `after_open` (where `clawg serve` fails on purpose), and `transport: "tcp"` (no socket on either system, the profile's port fatal, a client that ignores a published socket and an `update` that passes the old daemon's port on, as a clawg older than the socket)) replaces the version and the distribution mark the build reports (`crates/clawg-core/src/build_info.rs`), `CLAWG_TEST_RELEASE_URL` replaces the release server and `CLAWG_TEST_RELEASE_KEYS` (a JSON array with the text of a `.pub` file per key) the trusted keys. A build without `testing` reads none of them, and a binary without a stamp (the `CARGO_BIN_EXE_clawg` of the suite) is refused by `clawg update` as built locally. The tests sign what their fake release server serves with the `minisign` dev-dependency. Each scenario of `update` in `binary.rs` copies the test binary with its stamp into `<home>/bin`, starts its daemon and bridge from that copy, and ends the daemon `update` starts with `clawg stop` when the test drops it.

CI (`.github/workflows/ci.yml`) runs clippy and the suite on Linux and Windows for every pull request that changes a file outside the documentation and tooling paths it ignores. A push to `main` with such a change runs only `merged`, a job that builds nothing: the pull request it merges already ran the suite on that content, and `release.yml` waits for a successful run of the push, which a run of skipped jobs alone is not. A push that only changes the ignored paths runs neither CI nor the release. Every command takes `--locked`, so a `Cargo.lock` that trails `Cargo.toml` fails there. Besides the workspace (where `--workspace` turns on clawg-core's `testing` and `eval`), it runs what the release builds: `cargo clippy --locked -p clawg-cli -- -A clippy::all -D warnings`, without `--all-targets` so no dev-dependency brings `testing` in, and, on Linux alone since `build_info` has no platform code, `cargo test --locked -p clawg-core --lib build_info`, the `cfg(not(feature = "testing"))` side of those tests. Pull requests only read the build cache (`save-if: false`); `cache.yml` writes it from `main`.

The compiler is fixed in `rust-toolchain.toml` (an exact `X.Y.Z` with clippy), which local builds use too; every workflow passes the same version to `dtolnay/rust-toolchain`. Raising it is a commit of its own that changes all of them. `rust-version` in the root `Cargo.toml` is the highest `rust-version` among the packages in `Cargo.lock` (1.90, from `tree-sitter-language`; a `cargo +1.90.0 check --locked --workspace --all-targets` builds), never above the pinned toolchain; `tests/conventions.rs` compares the three.

Three more workflows are not named `CI`, so `release.yml` does not wait for them. `cache.yml` (`Cache`) builds on `main`, on Linux and Windows, what CI's `test` job tests, without running it, and writes the cache pull requests read: its job is also named `test`, with the same environment, because rust-cache keys a cache by job id, runner, `CARGO_`/`RUST` environment and lock, never by workflow. It runs when a push to `main` changes a manifest, the lock, the toolchain, `ci.yml` or `cache.yml`, twice a week so GitHub does not evict an unused cache after seven days, and on demand. The other two only report: `advisories.yml` runs `cargo deny --locked check advisories` with the root `deny.toml` on the pull requests and pushes to `main` that change a manifest, the lock or `deny.toml`, and every week, so a RustSec advisory shows without blocking a pull request or a release (an ignored advisory carries its `reason`); `installer.yml` runs PSScriptAnalyzer on `scripts/` on Windows when `scripts/**` changes, with `scripts/PSScriptAnalyzerSettings.psd1`, failing on any finding (an excluded rule says why). Those two download their tool at a fixed version and check it against a SHA-256 written in the workflow. `.github/dependabot.yml` updates the pinned actions once a month, against `develop`.

`.github/workflows/release.yml` runs after a green CI on a push to `main` (see Versioning) and builds only `-p clawg-cli`: `--workspace` would link clawg-eval, and with it the `eval` feature of clawg-core, into the shipped binary. Each build sets `CLAWG_DIST_TARGET` and is tried up to three times, since `ort-sys` downloads ONNX Runtime from `cdn.pyke.io` while building; it then runs `--version` and checks that the binary carries no `CLAWG_TEST_` stand-in; the Linux build also checks that it does not link OpenSSL. In every workflow, third-party actions are pinned by commit SHA with the tag in a comment, and each checkout sets `persist-credentials: false`. `tests/conventions.rs` reads the workflows and `dependabot.yml` as text (no YAML dependency) and pins their triggers, pins, build commands, downloads and the signing step, so reformatting a workflow without changing its meaning can break one of them: adjust the test in the same commit. The workflow itself only runs on GitHub; nothing in the suite executes it.

On Windows, live `clawg.exe` processes (for example the editor's MCP bridge) lock `target\debug\clawg.exe` and make the build fail. There the suite and clippy run in `target-test` instead: `cargo test --workspace --target-dir target-test`. See Build directories below for when it is cleaned.

Compiler warnings, `dead_code` and `unused` among them, are errors here (clippy's own lints are not enforced yet):

```
cargo clippy --workspace --all-targets -- -A clippy::all -D warnings
```

`tests/conventions.rs` in `clawg-cli` fails when a source hides dead code behind an `allow`.

What the model sees of the MCP server (each tool's name, description and input schema, and the instructions) is pinned in `crates/clawg-cli/src/mcp/agent_contract.json`. When a change to it is intended, run `CLAWG_BLESS=1 cargo test -p clawg-cli the_agent_contract_matches_its_file`: it rewrites the file and fails, so review the diff and run the tests again. It pins the server without a language preference, and `agent_contract.es.json` the server in Spanish (`CLAWG_BLESS=1 cargo test -p clawg-cli the_spanish_agent_contract_matches_its_file`); the English variant a preference gives is held by the tests of `protocol.rs` and `server.rs` (each fits 2048 characters and names only what exists). The `MCP tools` line above is checked against the registered tools.

`rag-eval --lang-detect [--golden FILE]` prints, without a model or a store, how `detect` labels the corpus rows that carry a `lang`: by label, in total and for the rows of eight words or more, the share right, crossed and undecided, counts only.

A ranking change is compared with the baseline by `cargo run -p clawg-eval --bin rag-eval -- --diff <before.json> <after.json>`. Every metric carries the exact paired p-value of the cases that moved (and MRR, nDCG and tokens a bootstrap interval of the mean change); the primary metrics are `recall@5` and, between two `--agent-view` runs, `search.found`. With the 46-case set a conclusion needs at least 6 cases moving one way; fewer is "not distinguishable", never "no difference". `--fail-on-regression` exits 6 when a primary metric gets worse at p < 0.05. When the golden cases carry `query_lang`, every block is also cut by the language pair of query and row (`es>en`, …), over the cases with that pair in both files: a change that touches retrieval across languages is read there, and the pair rows stay informative, outside the verdict and `--fail-on-regression`. Choose a new constant reading `by_split.calibration` and report `by_split.test`; `--lexical-only` gives the bm25-only floor to compare against.

`rag-eval --background SNAPSHOT (--fake | --real)` measures at the scale of a real store: SNAPSHOT is a file `clawg backup` wrote, read as a file and never opened, and copied into a `rag-eval-*` directory of the system temp dir that is removed when the run ends, failed or not (`eval_api::copy_background`). A snapshot with commits in a `-wal` beside it, damaged, without clawg's history, of a newer or diverged schema, without an embedding contract or of another one (a store pooled by CLS is named, to be opened once by the daemon and backed up again) is refused with exit 1 before anything writes; an older schema is migrated in the copy. The golden corpus is seeded on top (`--agent-view` saves it through the ingest), every search reaches every agent's rows, as the daemon does without `sharing.json`, and a hit outside the corpus keeps its place in `ranked_refs` as `bg`. A case may cite its save by origin, `expected_origins` (the `created_by_ref` an import wrote, `engram:<sync_id>`, resolved among the live rows of `source = 'import'`, a hit on any piece counting), and name its `project` (an id, or the name of one live project, read in each snapshot as the tools' `project` argument reads it); either without `--background`, an origin with no live row, an unknown, ambiguous or deleted project, or a cited save with rows outside the case's project is exit 2 before anything is measured (`resolve_cases`). The results add `background` (the path, sha256, contract, schema from and to, `searched_at_ms`, the live rows by type, agent, language, source and project, where each `origin_project` was placed, and `golden_twins`), each case's `expected_type`, `top5_types`, `decay_age_days`, `best_cosine`, `score_gap_1_10`, `passes`, `pool_survival` and `short_pool` with its cause (`scope` or `crowded`), and `retrieval.scale`: the top-3 places by type of the cases that do not expect a `session_summary` against the share of rows, the spread of `best_cosine` and the gap with and without an answer by pair and partition, and the short pools left out of both. None of it holds a stored text, a row id or a key, and the tag gains `bg-<first 8 hex of the sha256>`. `--diff` names each side's background and warns when both searched one more than a day apart, since decay reads the clock when it searches; the sweep flags are accepted, while `--docs`, `--lang-detect`, `--fts-tokenizer`, `--follow-up`, `--audit` and `--lexical-only` are not. The snapshots, the cases and the results stay in `docs/eval/` or the temp dir, outside git.

`revision-eval chains (--fake | --real [--tag T])` saves the chain set of `crates/clawg-eval/data/revision-chains.json` through the ingest worker in five stores under the system temp dir: every version without a key; every version under its key; the same without the old versions' vectors (`keyed_bare`); the same with the old versions in no index (`keyed_unindexed`); and the last version alone, saved in the round the keyed store saves it. It reports where the detector leaves each old version, where each version shows in `search_memory` and `recall_context`, and what showing the key costs in tokens. M2 compares the keyed store with `keyed_unindexed`, which differs only in the old versions, and keeps the comparison with the last-version store as a reference (`m2_control`). `revision-eval store --export FILE [--seed N] (--fake | --real)` replays an export, which must sit in a `revision-eval-*` directory directly under the system temp dir, through the worker and writes there the pairs to label; `store --labels FILE [--tag T]` scores the labelled file and removes that directory, which it keeps while a label is missing or invalid or the result file already exists, so no labelling is lost. `--real` reads the dev profile's model (exit 3 without it) and writes a dated file to `docs/eval/results/` that never replaces an existing one, and `--fake` only prints; a `store` result holds counts and rates, never a stored text, a row id or a key. `revision-eval warned --export FILE --since SNAPSHOT [--seed N] (--fake | --real)` measures the topic-key warning on an export made by `clawg export --include-deleted` without `--project` or `--agent` (anything else is refused with exit 2, as is a `--since` that is not the snapshot below): `--since` is the `pre-migration` snapshot (`memory-<UTC>-pre-migration.db`, or its path) that the opening which migrated the store to V19 wrote, since a save before it never had its pair marked, and the window is the saves made from then on. It leaves in the same kind of `revision-eval-*` directory `labels.jsonl`, with the pairs marked by `topic_key_warned` mixed with 100 saves of the window the warning did not fire on (all of them when there are fewer), each with `a`, `b` and `c` to fill, and `warned.json`, with no text; `warned --labels FILE [--tag T]` scores the passes (`c` only where `a` and `b` differ): Cohen's kappa, the precision of the marked pairs against `p_min = 2π / (1 + π)` with π the prevalence of revisions, a `decision` (`keeps`, `adjust_or_remove`, or, with fewer than `N_MAX` = 200 marked pairs, `gather_more` instead of `keeps_by_default`), the precision by distance and by store size, and what the agent did with the warning. It writes `docs/eval/results/{date}-real-revision-eval-warned[-T].json` under the same rules, with counts, rates, intervals and cuts only.

`load-eval gate [--model-dir D] [--loads 10] [--tag T]` measures what loading the embedding model costs in memory and time, by the way `model.onnx` reaches the session: `vec` (read into a `Vec`, hashed, `commit_from_memory`), `file` (hashed in 1 MiB blocks through a handle that stays open, `commit_from_file`) and `view` (production's read-only view); `load_once` in `eval_api` is the only code that builds the first two, `fetch_model` only downloads the model into the directory they read, and no release build links either. Every load runs in a process of its own (`load-eval child --arm A --model-dir D`) over one warm-up round, discarded, and `--loads` counted rounds, each with the three arms in rotated order (`schedule`). On Windows the parent creates a job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, assigns the child to it and only then writes `go` to its stdin; the child loads, reads `clawg_cli::daemon::process::sample()` and prints one JSON line with its timing (`verify_ms`, `session_ms`) and counters, and the parent reads the job's `PeakProcessMemoryUsed`, the peak commit the gate decides on. On Linux each load is a process too and the peak is `VmHWM`, but the run only reports. It needs Windows to decide, a release build and the real model, which `gate` downloads (about 470 MB; `CLAWG_HF_BASE_URL` names a mirror) into a `load-eval-<uuid>` directory of the system temp dir that is removed when it ends, failed or not; `--model-dir` only accepts such a directory, so a data profile is never read. `verdict` (pure) holds an arm to the `vec` arm of the same run: the median peak commit drops at least 300 MiB, its worst load stays under the best `vec` load, and the median verify-plus-session time rises no more than max(150 ms, 15 %). It decides `View` when `view` passes (alone or with `file`), `File` when only `file` does and `Revert` when neither does; where the peak is not a commit it decides nothing. The result goes to stdout and to `docs/eval/results/{date}-real-load-eval[-T].json`, never over a file that is already there and outside git: `cargo run -p clawg-eval --release --target-dir target-test --bin load-eval -- gate`.

### Build directories

Cargo never removes an old artifact from a target directory. Every version bump, branch or worktree with other sources, feature set or toolchain leaves a new set of the workspace's test binaries beside the previous ones, so a directory that is only ever reused grows past 100 GB. Most of that weight is the workspace's own crates, not its dependencies.

- Tests and clippy use one directory: `target`, or `target-test` on Windows. Never create another one (`target-apply`, `target/verify-win`, a directory outside the repository).
- Before testing a new version (another branch or openspec change, a version bump, another worktree's sources), remove the workspace's old artifacts and keep the dependencies: `cargo clean --workspace --target-dir target-test`. After `rustup update` or a dependency change in `Cargo.lock`, empty it: `cargo clean --target-dir target-test`. Within one change's TDD loop the directory is reused, not cleaned.
- On Windows, `target` is cleaned only when no `clawg.exe` built there is running; never stop one to clean it.
- A directory a one-off comparison needs (a worktree arm, a baseline build) is deleted, with its worktree, by the task that made it.
- A task ends with no build directory other than `target` and `target-test`.
