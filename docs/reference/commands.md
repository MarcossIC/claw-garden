# Commands

Every `clawg` command. "As above" and "the data profile's project paragraph" refer to [data-profiles.md](data-profiles.md); the daemon's routes are in [daemon.md](daemon.md).

- `clawg serve [--profile P] [--port N]`: run the daemon on the profile's socket and on TCP as above (`--port 0` binds an ephemeral port) until Ctrl-C, SIGTERM (Unix; Windows console events are not handled) or `POST /v1/shutdown`, each an orderly shutdown that exits 0. Every phase of a shutdown has a bound: the requests in flight and the import job that runs `HTTP_GRACE` (3 s, then cut: the signal closes the job registry, so no job is accepted, and asks the running one to stop at the safe point of its step, which a batch in embedding or between write batches reaches at once; a job still running when the grace ends has its task aborted and is left `interrupted` and `abandoned`, with a `warn` naming its step, before the probe is aborted and the drain begins, and what it had already sent the connection runs ahead of the close), the drain `DRAIN_DEADLINE` (10 s), the save in flight, access flush and checkpoint `AFTER_DRAIN` (7 s, then left to the outbox and the WAL), the last minute of metrics `METRICS_CLOSE` (1 s) and the blocking tasks the process waits for, a model load among them, `RUNTIME_TEARDOWN` (2 s). A shutdown that finished within its bounds then closes `memory.db` and waits for the close (`MemoryRuntime::close`), so SQLite removes `-wal` and `-shm` before the process exits; left to the last handle's drop, the exit could cut the close halfway and leave an empty `-wal`. Its first log line names its version, and its `dist_target` when it has one (`starting_line`). A daemon clawg starts (a bridge's autostart, `update`) writes stdout and stderr to `<data>/logs/serve.log`, which is rotated when it is opened, never while a daemon writes to it: past `SERVE_LOG_LIMIT` (10 MiB) `serve.log.1` becomes `serve.log.2` and `serve.log` becomes `serve.log.1`, so three files are kept (`crates/clawg-cli/src/serve_log.rs`); a rotation that fails is written to the log, and the daemon starts anyway. One started by hand logs where it is told. `RUST_LOG=info,clawg_core::memory::search=debug` adds each search's `retrieval=` line without the rest of `debug`.
- `clawg mcp [--profile P] [--no-autostart] [--agent NAME]`: stdio MCP bridge to the daemon; starts one if none is running unless `--no-autostart`. When a call is refused (401 or connection refused) or the start gave up, it reads `daemon.json` and `token` again and repeats the call once, but never starts a daemon mid-session (`crates/clawg-cli/src/mcp/startup.rs`). The agent id is `--agent`, else the client's `clientInfo.name`, else `mcp`.
- `clawg hook session-start|user-prompt-submit --agent NAME [--profile P]`: answer the client's lifecycle hook (JSON on stdin, `hookSpecificOutput.additionalContext` on stdout; `crates/clawg-cli/src/hook.rs`). Both register the root of the input's `cwd`, with `cwd` as `path` (`POST /v1/projects`, without `index_docs`), and read under the project id the daemon gives (a declared subfolder's when `cwd` is in one) (the id derived from the root when the registration fails, nothing on a 409), and register the input's `session_id` with the daemon for `--agent` and that project, so the saves that follow carry it (`POST /v1/sessions`). `session-start` injects the context without a query for the project of the input's `cwd`, saying when the source was `compact`, when the model failed to load, when 20 or more memories wait for `synthesize`, when a conclusion lost a source since the last review and when the project has pending suggestions (`suggestion_note`); `user-prompt-submit` says how long the project has gone without a save once it is 30 minutes or more, counted from the later of the last save of the agent there and the creation of `transcript_path`. `--agent` must be the bridge's. With a language preference, `session-start` opens with a line naming the user's language, to answer in it unless they write in another and to save and search in it (`language_line`), and prints that line alone when the rest gives nothing; both events read the preference at every event and speak it, and `session-start` asks for its context in it (`lang`). It never starts a daemon: no daemon, an error or no answer within 3 s, or input that is not JSON or over 1 MiB prints nothing (or the language line alone) and exits 0; a usage error or a refused profile exits 1, never 2, which the client reads as "block".
- `clawg preferences [set language es|en | unset language] [--profile P]`: show or change `preferences.json` without the daemon or the store (`crates/clawg-cli/src/preferences.rs`); a change reaches the Claude Code sessions opened after it, and `clawg setup claude-code` rewrites the protocol block. It speaks the language it leaves set, one `match` on `Lang` per sentence. An invalid file is never overwritten: `set` and `unset` exit 1 naming the cause.
- `clawg status [--profile P]`: print daemon state and health as JSON; exit 1 if not running.
- `clawg stop [--profile P]`: stop the daemon and wait for the process to exit, at most `STOP_TIMEOUT` (30 s), which a test keeps 5 s above the sum of the shutdown's phases (`crates/clawg-cli/src/stop.rs`).
- `clawg backup [--profile P]`: write a snapshot of `memory.db` to `<data>/backups` and print its path; goes through the daemon when one is running.
- `clawg restore <FILE> [--profile P]`: replace `memory.db` with a snapshot. The daemon must be stopped; the replaced store is snapshotted first. A file with a non-empty `-wal` beside it is refused, since only the file is copied in.
- `clawg export --out FILE [--project PATH] [--agent A] [--include-deleted] [--format jsonl|markdown] [--profile P]`: write the `memory` rows to FILE in the `clawg-memories` format version 1 (`crates/clawg-core/src/memory/portability/format.rs`): JSON Lines, a header with the format, its own version (not the schema's), the clawg version and the source model, then `project` (one line per project: `id`, `root_path` of its oldest folder, absent without one, `name`, `folders` with each `remote` and `root_commit` recorded, `remotes`, `merged_into` for a tombstone and `subfolders` it declares, an empty field left out; a line for each project of an exported row, each tombstone leading to one, each repository declaring a subfolder as one and each subproject one declares; a store before V27 writes one line per folder as before; never `deleted_at`, `born`, `reviewed`, `index_docs`), `memory` (every column but `content_hash`, ids of the source store, `lang` among them, which an import reads again from the text, and `origin_project`, `null` for a store older than V23), `derivation`, `piece` and `conflict` lines (each pair with `topic_key_warned`, false for a store older than V19 or a line without it), a link only with the row that holds it and a pair only with both sides; a reader ignores fields it does not know. Read-only and without the lock, like `secrets`, so it works with the daemon running; a store of an older schema is read with the columns it has, a newer or diverged one is refused. `--project` resolves the root as a bridge does and reads its project id from the store, the one a declared subfolder leads PATH to when it is in one (a store before V30 has none); without `--include-deleted` deleted rows stay out. FILE must not exist and is created `0600` on Unix; the output counts what it wrote (the projects among it, and those without a folder), warns that the text is as stored (`clawg secrets` lists secrets) and names the saves still in the outbox, which do not travel, nor do `episodic_trajectory` and `procedural_skill`. `--format markdown` writes a view by project and type that `import` does not read.
- `clawg import [--from clawg|engram] FILE [--dry-run] [--follow] [--agent A] [--map-root OLD=NEW]... [--project-map NAME=PATH|NAME=project:REF]... [--profile P]`: ask the running daemon (`POST /v1/imports`; never starts one) to import an export and follow the job it runs (`crates/clawg-cli/src/import.rs`), which writes a `pre-import` snapshot and inserts each row as it was (dates, accesses, tier, importance, state, `source`, `origin_project`, links translated to the new ids), masked and hashed again, indexed unless deleted, re-embedded unless deleted (behind its piece's head), without running the detector (`crates/clawg-core/src/memory/portability/import.rs`). It embeds the rows with the most tokens first, counted by the daemon's tokenizer in groups on a blocking thread, ties in the file's order, in calls of `EMBED_BATCH` (32) texts (`longest_first`, `embedding_order`), so a run of the embedder pads its texts to little more than their own length; each vector is kept by its row's id, so the order changes no vector, row, id or report. `--map-root` only goes with `--from clawg` (the default) and `--project-map` only with another tool, a usage error otherwise (`Cli::parse_args`). Rows of a project of the file go where the data profile's project paragraph says an import places it (the map, a remote, the id, the name, a path, a new project; the CLI sends each map's root and raw path, absolute and canonical, as an object, so a path in a declared subfolder leads to its project and a daemon from before refuses the body; an id a registration gave another root meanwhile keeps that project's rows out); a row whose project has no line keeps its id, the import creating that project when `project` lacks it; `--agent` replaces every row's agent but the `project`/`global` ones. A row with the same agent, project, masked hash and `created_at` is already here and is not inserted (its links are only filled where empty, and a save gets its pieces only when none of its rows has one), so a second import adds nothing; a row of a clawg file not present in its project is present too when a row of any project here, deleted or not, has its agent, masked hash, `created_at` and `created_by_ref` (`PRESENT_ELSEWHERE_SQL`, over `idx_memory_created_at`, V31), so importing again after a `projects move` adds nothing, counted in `present_elsewhere` by the project it is in; a live row whose text is live in its project here, whoever saved it, merges into that row; a live row whose `topic_key` a live row of its project here holds is stored `superseded` by it (`revision`). An unknown format or version is a 400 that writes nothing; an invalid line is reported with its number and the rest imported; a link whose other end is neither in the file nor here is dropped and reported. `--dry-run` reports the same without writing, embedding or snapshotting. The file is at most `MAX_IMPORT_BYTES` (256 MiB). With `--from engram` FILE is what `engram export --all FILE` writes, to a file outside the repository since it holds every note as stored (without `--all` newer versions export only the project of the directory they run in, and the file does not say so; a partial or empty export imports, and `--dry-run` shows its notes by project of the source). The daemon reads it with the adapter (`portability/engram.rs`, versions `0.1.0` and `0.2.0`, into the model of `foreign.rs`) before asking for the model, and `translate.rs` makes each note (an observation, a prompt, the summary of a session) the rows a save of its text stores: title and content masked whole and split by the daemon's tokenizer, with the head of the save, under the agent `migrated` (or `--agent`; it names the author and nothing else), `source = 'import'`, the note's origin in `created_by_ref` (`engram:<sync_id>`) and its project of the source in `origin_project` (V23, indexed, with `created_by_ref` indexed for the rows of `source = 'import'`), typed (`decision` and `architecture` as `architectural_decision`, `preference` as `user_preference`, a prompt as `chat_message`, a summary as `session_summary`, any other as `semantic_fact`), dated by its text (`updated_at`, a later or unreadable date clamped to the import's), with `duplicate_count` as its accesses, importance 9 when pinned, deleted when the source deleted it, its key rewritten into one clawg takes and qualified by its project of the source when two of those share it in one project here, the notes of one project of the source with one masked text stored once, and its relations as `memory_conflict` pairs (`supersedes` over a preference or a decision the user did not mark is escalated; a relation with an end outside the export is counted). `--project-map NAME=PATH` stores the notes of project NAME in the project a registration gives PATH's root with PATH as its raw path (resolved as a bridge does, a directory, refused before the file is read), and `--project-map NAME=project:REF` (split at the last `=project:`) in the project REF names, an id or the name of one live project, which the daemon resolves before reading the file (404, 409 `project_ambiguous`, 409 `project_deleted`) and checks again in the transaction that writes; a note of a project not named, of none or `personal` is stored in no project, and `clawg projects move --origin-project NAME` places it later. A second import finds each note by its origin wherever it is now: with a row of its date (or without a date of its own), deleted here or deleted at the source it is present and changes nothing; with other dates it is a rewrite, stored in the project and under the key of the latest version here, a newer one replacing the live rows it does not share in the transaction that stores it, an older one stored under them. The pass that decides where each row goes, all a dry run does, loads what it reads of the store in calls of `LOAD_BATCH` (256) index seeks and decides on a blocking thread, writing nothing, so other calls go on meanwhile; rows are then written in transactions of whole notes. The report counts inserted rows by language (`by_lang`, for a clawg file too), names each project of the file with where it went, the step that decided it and whether it created or brought it back (`projects`), the suggestions it left (`suggestions`) and the declarations written or not (`subfolders`), and, in `foreign`, says by note what became of each and counts what has no place in clawg, by field; with new projects or suggestions the output ends with `clawg projects list`. Every write of an import is journaled in its transaction (V26, `crates/clawg-core/src/memory/portability/import.rs`, `Journal`): `memory_import` numbers each import that writes anything (`MAX + 1`, taken by its first write; a dry run or an import that adds nothing has none) with its start, its end (NULL when the process died before the links), its source and its snapshot; `memory_import_row` each row it inserted with the `update_count`, `deleted_at` and `supersede_cause` it left; `memory_import_supersede` each row a newer version of its note replaced, with the state it had; and `memory_import_extra`, only where the write added something, the links it filled in rows it did not insert, every pair, the derivations and pieces of rows it did not insert, and the roots and remotes it recorded; and `memory_import_registry` (V31) the projects it created, the deleted ones it brought back with their `deleted_at`, the suggestions it left and the declarations it wrote. The report names the number in `import_id` and the output the command that undoes it; the imports this process is writing hold their number in `MemoryStore::importing`. Each step of an import logs an `info` line as it ends (`crates/clawg-core/src/memory/portability/timing.rs`): `read` in the handler, `plan`, `prepare` (a clawg file) or `translate` (another tool's), `load`, `decide` (where a dry run ends), `embed` (counting the rows' tokens included), `snapshot`, `write` and `links`, with its seconds and what it went through (rows, embedding batches and rows/s, calls) and, in the daemon, the private memory of the process as it ended, and for the steps on the connection the time inside SQLite apart from the wait in its queue and the call that held it longest; a successful import closes with `import: done in …` and every step, to set against `http.duration{route=/v1/import}`. Names and numbers only, and neither the report nor what is written changes. The command sends the absolute path of FILE (`std::path::absolute`) and never reads it: the daemon does, so a file it cannot read or a file over the limit comes back as its 400 with the cause as it came (a relative FILE is made absolute first, so the `path must be absolute` 400 is for other clients), and `--dry-run` goes as a job too. It follows the job with `GET /v1/imports/{id}` every `POLL_EVERY` (1 s), a poll with no deadline of its own (only `/health` sets a timeout in the client), and prints on stdout the report that `POST /v1/import` printed (`render`), so killing `clawg import` leaves the job running. The phases (`planning`, `preparing`, `translating`, `loading`, `deciding`, `embedding`, `snapshot`, `writing`, `linking`, then the final one) and their counters go to stderr, redrawn in place on a terminal, one line per phase seen with `--follow` when stderr is not one and nothing without either (`shows_progress`); `--follow` does not go with `--undo`. Ctrl-C (`interrupts`) sends `DELETE /v1/imports/{id}` and goes on waiting for the final state, then prints what was written with its `clawg import --undo N`; a second one leaves without waiting, naming the job. What it decides is `Follow::on` over an `Event`, apart from the I/O. Every final state but `done` exits 1: `cancelled` and `interrupted` print the report and how far the job got when it wrote a batch, else the step it stopped in and that nothing was written (the `pre-import` snapshot stays in `backups` after `snapshot`); `failed` is `clawg: the import failed: {error}: {detail}`; a `done` that a `DELETE` met says on stderr that the job was in its last step. When the daemon cannot be asked in a way that says it is gone (a refused connection or a timeout, a rejected token, or a 404 for the job because another client's job took its place as the last finished: `ClientError::means_daemon_gone`), `gone` says by the last phase seen what was written, with the last `import_id` and its `--undo`. Any other error of a poll or of the `DELETE` (a reset connection, a 5xx) is `Event::Unanswered` and passes: the poll is asked again at the next tick and a `DELETE` that did not land is sent again after a tick (a second Ctrl-C still leaves), and a view resets the count; `MAX_UNANSWERED` (5) in a row fail the command with a sentence that names the job, the last phase seen, the count and the cause as it came, says the import may still be running and that `clawg status` shows it (its `import` block), and claims neither that the daemon went away nor that nothing was written (`not_answering`). A `409 import_running` names the job that holds the slot. A daemon without the route (`route_missing`: a `404` whose body is not an object with a text `error`, which axum's own lacks) exits 1 without sending the file, saying that the daemon is older, with the `version_warning` sentence and the version `/health` gives, or an earlier build of this version, and that `clawg stop` makes the next start use this one. Each sentence is in the language preference, one `match` on `Lang`; phases, commands and the technical cause stay as they came.
- `clawg import --undo N [--dry-run] [--profile P]`: take import N back through the running daemon (`POST /v1/import/undo`; never starts one; `crates/clawg-core/src/memory/portability/undo.rs`), keeping what was saved after it. A row the import inserted is removed for good (the row, its vector, its piece links, its derivations and its pairs; the text index trigger takes its terms out), not marked deleted, so the same file imports again; it stays, named with why in `kept`, when its `update_count` or `deleted_at` moved (`edited`, `deleted`, `restored`), when a verdict replaced it or a pair of it is not as the import wrote it (`judged`), when a row that stays names it by `superseded_by`, `revived_from`, `disputed_against` or as the source of a conclusion, but for a link the import itself wrote in a row that was here (`referenced`), or when it is a piece of a save with a row that stays (`tied`), until nothing more is kept (`decide`, pure). Its project, tier, accesses, `last_modified_at` and a later revision by key are no sign. What the import changed in other rows comes back only where it is still as it left it: a replaced row returns to its state when its replacement goes, a filled link to NULL, an added pair (unjudged), derivation or piece goes unless a kept row holds it, a recorded root or remote goes when no row of any kind uses it and the root has neither `index_docs` nor indexed files; in the last transaction, a declaration it wrote goes while it still leads where it wrote it, a suggestion it left while unanswered, a project it brought back is deleted again with its `deleted_at` while live, unreviewed, without live rows and its delete still open, and a project it created goes when nothing names it (no row of the three tables in any state, folder, remote, declaration, tombstone, suggestion, merge or delete journal or `synthesis_review`) and it is still unreviewed; what stays is named in `registry.kept` (`in_use`, `answered`, `reviewed`, `changed`). An import from before V31 keeps what it added to the registry. The store is read in calls of `LOAD_BATCH` seeks and written in transactions of `WRITE_BATCH` rows, each reading again the columns of its rows, so an edit that came in between keeps its row; a `pre-undo` snapshot comes first when there is anything to undo. What was taken back leaves the journal and what stayed is weighed again by the next undo, so a second one changes nothing. An unknown N is a 404, an import still being written a 409, and an import cut short is undone as any. `--undo` takes no file, `--from`, `--agent`, `--map-root` or `--project-map`; `--dry-run` reports the same without writing. Imports from before V26 have no journal and only their snapshot.
- `clawg secrets [--profile P]`: list the `memory` rows, live or deleted, and the verdict reasons of `memory_conflict` that hold a secret of a known format, by id and kind and never the secret. Read-only; works with the daemon running. `--mask-reasons --yes` instead replaces the secrets of every stored reason with their placeholders, then rebuilds the file and empties the WAL as `purge` does; the daemon must be stopped and no snapshot is taken.
- `clawg purge <ID> --yes [--profile P]`: remove one `memory` row for good (text, vector, index terms, the head of its long save kept in `memory_piece.context` when it is the first piece, free pages and WAL) and the outbox rows of its own agent's save: the one with the same text, or for a piece of a long save the ones that contain it. A live row is deleted first, so the revision of its topic it replaced comes back as a delete would bring it. It names what came back, the rows a verdict keeps replaced, the other pieces of its save, the outbox rows it removed by `operation_id`, and the backups and `workspace.md` files (AUTO section or the user's part) that still hold the text, changing none of them. A conclusion drawn from it keeps the link to its id, which `synthesize` lists as `purged`. The daemon must be stopped; no snapshot is taken.
- `clawg purge --project-delete N --yes [--profile P]`: remove for good what delete N left (`purge_delete`, `crates/clawg-core/src/memory/secrets.rs`), under the rules of `clawg purge <ID>` (the daemon stopped, `--yes` for both forms or it refuses before opening anything, no snapshot, nothing written before every check passes; an unknown, an undone and a purged delete are refused, `PurgeError::{UnknownDelete, DeleteUndone, DeletePurged}`). In one transaction it removes every row of `project_delete_row` that is still deleted, wherever it is now, in the three tables (the row, its vector and, for `memory`, what `purge` removes of a deleted row: `remove_in`), names the ones live again, which stay, empties again the docs index under the folders of `project_delete_folder` still at `index_docs = 0`, and sets `purged_at`; the project stays as it is. After the commit it merges both text indexes (`memory_fts` and `project_doc_fts`), runs `VACUUM` and empties the WAL, once. The report (`purge_delete_report`) counts the rows removed by table and names the outbox rows removed, the rows left live, the snapshots that still hold any of the rows (one pass, `pre-delete` among them), the project's own `workspace.md` files and the other ones that hold a removed text, changing none.
- `clawg undelete <ID> [--profile P]`: bring back a deleted `memory` row through the running daemon, which embeds it again; refused when the same text was saved again since, when a live row of another save holds its `topic_key` (not one its own delete brought back), or the row holds a secret; it prints what it supersedes again and the rows saved meanwhile it was paired with.
- `clawg outbox retry|discard <OPERATION_ID> [--agent NAME] [--profile P]`: through the running daemon, take a `failed` save back to pending with its progress and no attempt spent and queue it (written again under another row id), or drop it after deleting the memories it inserted, which `undelete` brings back (`crates/clawg-cli/src/outbox.rs`). `--agent` is needed only when two agents used the operation id; a `pending` row is refused.
- `clawg metrics report (--metric M [--label K=V]... [--by day|hour|minute|version] | --events) [--since Nd|Nh] [--profile P]`: read `metrics.db` read-only, without the daemon or the store's lock, and print as JSON the metric summed by local day, hour of the local day (`00` to `23`), local minute (`YYYY-MM-DD HH:MM`, from no earlier than the first whole hour of the 14 days kept by minute, `since_for`) or version (default; versions in the order they first ran), from `--since` (default `30d`), keeping the series that hold every `--label` (`crates/clawg-cli/src/metrics.rs`, grouping in `crates/clawg-core/src/metrics/report.rs`): `count`, `mean`, `min`, `max`, `p50`, `p95`, `p99` for a histogram, `samples`, `mean`, `min`, `max` for a gauge, each group with its `runs` and `not_stopped`, and `runs` (`total`, `not_stopped`: killed, crashed or still running) over every run started since. The local time of a row is its run's offset. `--events` prints instead, by run (its version, start and stop), the events from `--since` on, oldest first, and takes no metric, label or grouping. Without the file, or without the metric (the error lists the names), exit 1.
- `clawg memories list|search|show|stats [--profile P]`: read-only viewer through the running daemon; `list --deleted` lists deleted rows, most recently deleted first; `list` and `search` take `--no-project` for the rows saved in no project, and `--here` reads the project of the working directory from the store; `list --origin-project NAME` lists the rows another tool's project NAME gave.
- `clawg projects list [--profile P]`: list every project through the running daemon (`GET /v1/projects`; never starts one; `crates/clawg-cli/src/projects.rs`), by name: how many memories it holds, how it was born when nobody reviewed it, its folders (those no longer there marked), its remotes, the subfolders declared as it with their paths here (those not there marked; such a project is not printed as without a folder) and, under a repository, each of its declarations with the project it leads to, the projects merged into it with the command that undoes each merge, its pending suggestions with the other project and why, and a project without a folder as such; neither a tombstone nor a deleted project is listed, with a suggestion pending the listing ends with the two commands that answer it, and then it ends with the open deletes (`render_listing`), each with its `clawg projects delete --undo N` and, when it left deleted rows, its `clawg purge --project-delete N --yes`, saying so when a save brought the project back into use.
- `clawg projects rename <ID> <NAME> [--profile P]`: give a project a name, without the spaces around it, and mark it reviewed, through the running daemon (`PATCH /v1/projects/{id}`); its id, and what was saved under it, stays. A refusal (no such project, an empty name, one over 80 characters or with control characters, the name or the id of another project in any case) names the id, with the daemon's cause as it came.
- `clawg projects create <NAME> [--new] [--profile P]`: create a project without a folder through the running daemon (`POST /v1/projects/resolve` with `born: user`; never starts one): a name a live project has prints that project, one whose key other projects' names have prints them (deleted ones with their `--undo`) and `--new` creates one apart (exit 1 without it); `render_created`, `crates/clawg-cli/src/projects.rs`.
- `clawg projects locate <PROJECT> <PATH> [--subfolder] [--profile P]`: make the folder PATH is in lead to PROJECT, by id or by name, through the running daemon (`POST /v1/projects/locate`): the root is registered as a bridge registers it, and the project it gets, when another and with that folder alone, is merged into PROJECT as `projects merge` does, which `--undo` takes back; a project with other folders is 409 `folder_shared` naming the merge it would take. With `--subfolder`, PATH itself, a subfolder of a repository, is declared as PROJECT (`declare_subfolder`, `crates/clawg-core/src/memory/subfolder.rs`), sent absolute and not raised to its root: the top of a checkout or a path outside one is a 400; naming the repository's own project removes the declaration (`removed`, with the project it led to in `previous`); one that leads to PROJECT already writes nothing; one that led to a project nothing else reaches (no folder, no remote, no other declaration) merges that project into PROJECT, and otherwise it is 409 `folder_shared`; a tombstone or a deleted PROJECT is 409 `project_merged` or `project_deleted`. It moves no memory: the output names `clawg projects move --from-project P --to-project X --text WORDS --dry-run` for what was saved there before, says that a session opened before keeps the repository's project until it restarts, and after a removal names `clawg projects merge X --into P --dry-run` (`render_declared`, `crates/clawg-cli/src/projects.rs`).
- `clawg projects merge <SOURCE> --into <TARGET> [--dry-run] [--profile P]` and `clawg projects merge --undo N [--dry-run] [--profile P]`: merge one project into another, or take merge N back, through the running daemon (`POST /v1/projects/merge`; never starts one; `merge_core` and `undo_merge_core`, `crates/clawg-core/src/memory/merge.rs`). A merge waits up to `SAVES_WAIT` (5 s) for the saves of either project still in the outbox (the worker reads a save's project more than once), then refuses with 409 `saves_pending`; after a `pre-merge` snapshot, in one transaction that decides again what a pass writing nothing found, every `memory` row of SOURCE, deleted ones too, goes to TARGET with the part of its unit that is there (`merge_in` with `Span::Carry`: the part of a unit in another project stays there, named in `split`; a registration's join keeps such a unit whole, `Span::Keep`), reconciled as a registration's join and logged under one `memory_move`; its trajectories and skills, its `synthesis_review` rows (the older review kept where TARGET has one, so no reminder is lost), its folders, its remotes and the tombstones that led to it follow; the suggestions whose sides became one are answered `merged`; SOURCE becomes a tombstone and TARGET reviewed, and each change is journaled with what it was (`project_merge`, `project_merge_change`). Then each agent's `workspace.md` of SOURCE is copied where TARGET has none (`adopt_legacy`), SOURCE's own never changing. SOURCE already merged into TARGET is a repair: what is still under it moves. Merging into a tombstone, or a tombstone into another project, is 409 `project_merged`. `--undo N`, after a `pre-undo` snapshot, brings SOURCE back with what the merge moved and still points at TARGET, rows of `memory` as a move of their own (`undo_move_in`), and removes each `workspace.md` copy whose user's part is still SOURCE's (`drop_adopted`); what was saved in TARGET since stays, a row moved elsewhere is named in `kept`, a merge whose TARGET was merged since is 409 `merged_later`, and one undone already 409 `merge_undone`. The output names what moved, what was replaced, the units kept split, the folders, remotes and tombstones, the `workspace.md` copies, the snapshot and the merge's number.
- `clawg projects keep-apart <A> <B> [--profile P]`: answer that two projects are not one through the running daemon (`POST /v1/projects/keep-apart`; `keep_apart`, `crates/clawg-core/src/memory/registry.rs`): every pending suggestion between them, read through the merges since, is answered `apart`, or the pair is recorded with reason `user`, and both are marked reviewed.
- `clawg projects delete <ID> [--profile P]`, `clawg projects delete <ID> --with-memories [--confirm CODE] [--profile P]` and `clawg projects delete --undo N [--dry-run] [--profile P]`: delete a project, report what deleting it with its memories takes, or take delete N back, through the running daemon (`POST /v1/projects/delete`; never starts one; `delete`, `render_delete`, `delete_refused`, `crates/clawg-cli/src/projects.rs`). `<ID>` and `--undo` exclude each other and one is required; `--confirm` needs `--with-memories`; `--undo` takes neither, and `--dry-run` goes only with it (`DeleteOpts`). An empty project is deleted and the output gives the delete's number and `clawg projects delete --undo N`, and `clawg purge --project-delete N --yes` when it left deleted rows (exit 0). A project with live rows prints its live rows by table and the ways to empty it, `clawg projects merge X --into C --dry-run` for each candidate with its name and reason, `clawg projects move --from-project X --to-project <ID>` and `--with-memories` (exit 1). `--with-memories` prints the report (counts by table, type, author and status, the preferences and decisions, the pairs, the conclusions that go to review, the `workspace.md` files, the folders, the remotes, the subfolders declared as it, which stay declared, the saves waiting and each `failed` one with its `clawg outbox discard OPERATION_ID --agent AGENT`, and the candidates) and ends with the exact `clawg projects delete X --with-memories --confirm CODE` (exit 0); a code that is no longer the set's says so and prints the new report (exit 1). A confirmed delete prints how many rows it deleted, the snapshot, `--undo N` and the purge. An `--undo` prints how many rows came back and each one that stayed, with its reason, and with `--dry-run` what it would do (exit 0). A refusal (400, 404 or 409) prints the daemon's cause as it came and exits 1, `saves_pending` adding that it can be tried again. The commands it prints do not carry `--profile`.
- `clawg projects add <PATH> [--profile P]`: let the daemon read and index the files of the project PATH is in, through the running daemon; without it, only the root a bridge was started in is indexed.
- `clawg projects move [--id N]... [--from-project ID | --from-none | --here] [--agent A] [--type T] [--source S] [--session ID] [--text WORDS] [--origin-project NAME] [--include-deleted] (--to PATH | --to-project ID | --to-none | --undo N) [--dry-run] [--profile P]`: move `memory` rows to another project, or out of every project, through the running daemon (`POST /v1/memories/move`; never starts one; `crates/clawg-cli/src/projects.rs`). At least one selection filter; `--origin-project` selects the rows whose `origin_project` is NAME, as written in the tool they were imported from; without `--include-deleted` only rows not deleted are selected. `--to PATH` registers the root of PATH first (without `index_docs`, with PATH as `path`, so a declared subfolder leads to its project, as `--here` does with the working directory) and must be a directory; `--to-project` must be a project, by id or by the name of one live project. Each row moves with its unit (`crates/clawg-core/src/memory/relocate.rs`): the pieces of every save it is a piece of, the rows it replaced as a revision and the one that replaced it so, and what its delete revived or the delete that revived it, deleted and superseded rows included; the rows nobody named are listed as pulled in. A move changes `project_id`, and `scope` for a row no agent saved (`project` with a project, `global` without), and nothing else: no vector, no text index, no `last_modified_at`, no detector, no embedder. A unit is left where it is, named with why, when a live row of the target has the text (`content_hash`) or the `topic_key` of a live row of the unit, when an earlier unit of the same move takes that text or key there (the first, by id, moves), or when its rows are in more than one project. The report names what moved, what was already there, the open pairs left across two projects and the preferences and decisions that moved. A real move first writes a `pre-move` snapshot when there is something to move, logs every row in `memory_move` (V21: move, row, project and `scope` of origin and target) and prints its number; `--undo N` moves back, under the same rules and as a move of its own, the rows of move N still where it left them, to their origin whether it is registered or not, or to the project it was merged into since; the move of a merge is undone only with its merge (409 `part_of_merge`), and `--from-project` a tombstone is 409 `project_merged`, each printed with the daemon's cause. Re-importing a clawg export after a move inserts the moved rows again: the export's project no longer matches.
- `clawg sharing [hide|unhide <READER> <AUTHOR>] [--profile P]`: show or change the sharing policy. Every agent reads and changes every other agent's memories, marked `by <author>`, unless `hide` keeps AUTHOR's from READER (`*` for every agent), which then neither reads nor changes them; it works with the daemon running and never opens the store.
- `clawg doctor [--profile P]`: print as JSON what is wrong with the install, the data directory and the store (`crates/clawg-cli/src/doctor/`): the fields of before (which `clawg.exe` files the PATH resolves to: `installs`, `winner`, `shadowed`, `duplicates`) and `data_dir`, `checks` and `summary`. Each check gives at least one finding, `ok` when it found nothing, each with `check_id`, `severity` (`ok`, `info`, `warn`, `error`), `reason_code`, `message` (in the preferred language, the rest of the finding the same in both), `evidence` (ids, counts, paths and names, never a row's text, a verdict reason or a `topic_key`), `safe_next_step` (a command or null) and `requires_confirmation` (the step changes stored data). It checks the PATH, the data directory's mode (Unix), whether the socket path fits, who holds the store, the schema, the embedding contract against the one `clawg serve` verifies (without loading a model), the age of the newest snapshot by its name (`warn` past 30 days, or with none for a store with rows), the spill files an older clawg left, `sharing.json`, `preferences.json` when it exists (`preferences`) and, with a language preference, whether the protocol block of the user `CLAUDE.md` is the one `setup` would write for it (`protocol_block`: `stale`, `not_installed`, `unreadable`), failed and waiting outbox rows, the agents and their rows (`warn` for live rows under the fallback `mcp`, which every agent reads but the client's own workspace and RECENT leave out), the ids of the folders in `project_path` against their root (one `candidate_id` of it), the projects with more than one bound remote, each root named with its `origin_key` now (`project_remotes`), from V27 two live projects that may be one, by name in any case or by folders of one first commit no pair of remotes tells apart, skipping a pair someone answered (`project_duplicates`, the step the dry run of merging the newer into the older; a deleted project is none, nor is a pair that reaches one through a tombstone), an id with rows `project` does not have (`project_orphans`), rows under a tombstone and a tombstone whose chain ends in no live project (`project_merges`), from V29 a deleted project with live rows in any of the three tables (`project_deletes`, `warn` `live_under_deleted`, naming the project, its latest open delete and the live rows by table, no step; a store before V29 gives no finding of it), from V30 a declared subfolder whose repository or project is not in `project` (`project_subfolders`, `warn` `broken_subfolder`, no step; a tombstone or a deleted project on a side is none), six rules of `memory` no schema imposes (one live save per topic key of a project, `superseded_by` and `revived_from` naming a row, no two live rows with one `content_hash` in a project, both naming their authors in `agents`, no save keeping the opening of a purged first piece, a `disputed` row with a live rival) and Claude Code's registration of the profile's server in the `.claude.json` `setup` reads. The store is read without its lock and without writing (`clawg_core::memory::inspect`, through `open_for_probe`), beside a running daemon or not; a newer or diverged store is read no further than its history. Writes nothing, repairs nothing. Exit 1 only with an `error` finding (a shadowed or duplicated PATH among them), 0 otherwise.
- `clawg update [--check] [--profile P]`: for a binary downloaded from a release (not a debug build, one built locally or one run from a cargo target directory), look for a newer release on GitHub and, without `--check`, install it. `--check` exits 0 up to date, 100 newer release (named on stdout), 1 any failure; it changes nothing and takes no lock. `update` downloads `SHA256SUMS` and its minisign signature first, verifies them against the embedded keys, then the binary against its hash, and runs its `--version`; none of that touches the installed binary, the daemon or `memory.db`. Then, under an exclusive lock on `<data>/update.lock`: it stops the daemon through `stop_in` (only if one was running; none is started otherwise), sets the binary aside as `<exe>.old-<yyyyMMddHHmmssfff>`, puts the new one in its place and starts the new daemon by explicit path, according to the old daemon's `daemon.json` and not to the system (`serve_port`, `crates/clawg-cli/src/update/effects.rs`; `Running.socket`, `update/plan.rs`; `running_daemon`, `update/mod.rs`): without `--port` when the old one published its socket (as an autostart does, so a port is kept only where someone asks for it again), on the port the old one had when it served TCP alone (its socket path did not fit, or it was a clawg older than the socket, or the updater is stamped `tcp`), watching it (`memory.owner` read without the try-lock, `/health`) until a daemon of the new version answers. Any failure undoes what was done in reverse (`crates/clawg-cli/src/update/plan.rs`, a plan as data run over an `Effects` trait; the real one in `effects.rs`); a stop that ran out of time after the daemon accepted it counts as done, so the undo waits up to `STOP_TIMEOUT` more for that pid to end before it starts the old daemon, and starts none, saying so, while it lives, and starts the old one by the same rule; when the new daemon migrated the store and the old binary refuses it, the `pre-migration` snapshot that start wrote is restored in process, the migrated store kept as `pre-restore`, and when that restore fails the new binary stays and the report gives the way back by hand. Old `.old-*` and staged files are deleted at the start of the next run. Exit 0 on success, 1 on a refusal or failure.
- `clawg setup claude-code [--profile P] [--dry-run] [--remove]`: connect Claude Code (`crates/clawg-cli/src/setup.rs`, a pure `plan` over what was read, then `apply`). It registers the profile's server (`clawg`, `clawg-dev`) through `claude mcp add --scope user` with the running binary's absolute path and `mcp --profile P --agent claude-code`, reading `.claude.json` to see what is there but never writing it; adds a `SessionStart` (`startup|resume|clear|compact`) and a `UserPromptSubmit` group to the user `settings.json`, each hook in exec form (the binary's path as `command`, unchanged, and `hook <event> --agent claude-code --profile P` as `args`, run by the client without a shell, which needs Claude Code 2.1.139 or later; an older client runs the binary alone, and `clawg` without a subcommand exits 1, not 2, so it does not block the session); and puts `protocol.md`, with the rules of the profile's language preference when there is one (`protocol::text`), between `<!-- BEGIN CLAWG MEMORY PROTOCOL -->` and `<!-- END CLAWG MEMORY PROTOCOL -->` in the user `CLAUDE.md` (`$CLAUDE_CONFIG_DIR` instead of `~/.claude` when set, with `.claude.json` inside it). Everything is read first: an unreadable file, invalid JSON or a lone marker writes nothing. A server, or a clawg hook of the same event and profile, that differs from the plan is reported and left alone (exit 1), as is anything not clawg's; the block is rewritten, and so is a hook that is exactly the shell command line earlier versions wrote, whatever clawg path it names, which becomes the exec form in its place. Without `claude` on the PATH it prints the command, installs the rest and exits 1. Each changed file is copied to `<data>/backups/setup/` first (owner-only on Unix; only the five newest copies of each file are kept, and the report names the ones removed) and written through a temporary file with the old file's mode, synced and renamed; a symbolic link is written through, to the file it points to, and a linked `CLAUDE.md` that only held the block is emptied instead of deleted. `--remove` takes away a clawg server, the profile's clawg hooks in either form and the block (kept while the other profile's server is registered); `--dry-run` writes nothing and runs no `claude`.
