# Testing

```
cargo test --workspace
```

The bar is that the whole suite passes. Never record how many tests it has (in `.claude/CLAUDE.md`, the other agents' instruction files, these documents or `openspec/config.yaml`): the count goes stale with every change.

A test leaves nothing in the system temp dir, passed or failed. Dropping a store only signals its connection's thread, and on Windows a file still open cannot be deleted, so a directory removed right after loses the race in silence. In clawg-core a test takes its directory from `crate::test_dir::test_dir()`, which waits for the store's files and fails the test when a store still holds them: close a runtime (`MemoryRuntime::close`) or an ingest (`EvalIngest::finish`, then close) the test started. An integration test cannot reach `test_dir`: it takes a `tempfile` directory, which gives up on a file still open without failing, so it closes the runtime it opens on disk before it ends, as `an_integration_test_closes_the_store_it_opens_on_disk` in `tests/conventions.rs` checks. `rag-eval`'s tests use `TempPath` (`test_temp.rs`), and a run of `rag-eval` removes the store it seeds unless `--keep-store` keeps it. `CLAWG_KEEP_TEST_FILES` keeps the test paths and names each one on stderr, for a test whose files need a closer look.

`crates/clawg-cli/tests/binary.rs` runs the built `clawg` itself: a hard kill with a save still pending, two daemons on one store, `status`/`stop`, `backup`/`restore`, MCP over real stdio, a daemon restart under an open bridge, the socket (status, stop, bridge, hooks, an orphan left by a kill, a path over the limit, a taken profile port, an explicit `--port` that is taken, a shutdown that ends the listener), the metrics a daemon records over both transports and `metrics report` reads after `clawg stop` or a kill, the series of its pipeline and its events, the bridge's autostart, clients and updaters older than the socket, an update of a daemon that serves TCP alone, `doctor` beside a live daemon and an import of another tool's export; these run on Unix and on Windows, while the directory mode, the export's `0600`, SIGTERM, `write_executable`'s `chmod`, the `setup` scenarios with a shell `claude` and `admits_peer` are Unix only. Each test gets a temporary home through `CLAWG_TEST_HOME` and the fake model through `CLAWG_TEST_EMBEDDER=fake|stalled|blocked` (`fake` also gives the process a tokenizer of one token per word, `chunker::word_tokenizer`, as a model load gives the model's; `stalled` never finishes the download, `blocked` never returns from the load); only a build with clawg-core's `testing` feature (its dev-dependencies) reads them, never a release build, and `tests/conventions.rs` fails when a manifest enables `testing` outside `[dev-dependencies]`. Every daemon a test starts binds `--port 0`; one started without `--port` (by a bridge, by `update`, or a test of the socket) is kept off the profile's port by `CLAWG_TEST_DEFAULT_PORT=off`, which a `testing` build reads in place of that port (`off` or a port number). Each child is ended by its own handle, never by name. It takes about a second.

`crates/clawg-cli/tests/transport_bar.rs` (`#![cfg(windows)]`, its test `#[ignore]`, so CI never runs it) starts one `testing` daemon with `--port 0` that serves both transports and measures AF_UNIX against TCP in five scenarios: sequential, a new client per request, 8 concurrent tasks, a burst of 32 in 20 rounds and a list of about 8 KB. It fails when any AF_UNIX mean is over 1.10 times the TCP mean, or when the AF_UNIX burst has a failure: `cargo test -p clawg-cli --release --test transport_bar --target-dir target-test -- --ignored --nocapture`.

`crates/clawg-cli/tests/perf_bench.rs` is a performance bench of the daemon that repeats the same way on the next version, on every system; its test `bench` is `#[ignore]` and the tests of its pure parts run with the suite. It starts one `testing` daemon with `--port 0` in a temporary home and seeds its store through `POST /v1/import` with an export built from a seed (four agents, three projects and rows without one, a tenth `superseded`, a twentieth deleted, frequent words and rare identifiers). After 5 s idle it sends an open-loop load, each request leaving at the instant its rate gives it and timed from that instant, so a stall is charged to every request that waited behind it: alone, `search`, `context`, `session_start` (the context without a query the hook asks for) and saves of 1, 10 and 100 pieces; then `search`, `context`, `session_start` and `save_1` together while a save of 100 pieces, a backup or the first docs refresh of 400 Markdown files runs (a save or a backup again until 10 s have passed) (`{stream}_during_{background}`). The rates are below what a debug build serves with 10 000 rows. It writes `docs/eval/results/{date}-{fake|real}-perf-bench-{rows}[-{tag}].json`, never over a file already there, with the version, build, embedder and machine, every scenario's raw samples and their p50, p95, p99 and max, the daemon process's CPU idle and under load and its memory peak (read by its pid: `/proc` on Linux, `GetProcessTimes` and `GetProcessMemoryInfo` on Windows, `null` elsewhere), and the run's histograms of `GET /v1/metrics` with the minute's `embedder.*` gauges. `CLAWG_BENCH_ROWS` (default 10 000), `CLAWG_BENCH_SEED` (74) and `CLAWG_BENCH_TAG` shape a run; `CLAWG_BENCH_MODEL_DIR`, a data directory whose `models/` is copied into the temporary home, gives the daemon the real model instead of the fake one, which needs authorization since that directory is usually a profile's: `cargo test -p clawg-cli --test perf_bench -- --ignored --nocapture` (add `--release` for an optimized daemon, and `--target-dir target-test` on Windows).

A `testing` build also stands in for what makes a binary a release, so `clawg update` can be driven without the network or a real release: a stamp after the end of a copied binary (`0x00`, `CLAWG-TEST-STAMP`, a JSON object up to the end of the file; `version`, `dist_target`, `migrations_up_to` (the newest migration the binary knows and applies, as if it were an older release) and `serve_fault`, `before_open` or `after_open` (where `clawg serve` fails on purpose), and `transport: "tcp"` (no socket on either system, the profile's port fatal, a client that ignores a published socket and an `update` that passes the old daemon's port on, as a clawg older than the socket)) replaces the version and the distribution mark the build reports (`crates/clawg-core/src/build_info.rs`), `CLAWG_TEST_RELEASE_URL` replaces the release server and `CLAWG_TEST_RELEASE_KEYS` (a JSON array with the text of a `.pub` file per key) the trusted keys. A build without `testing` reads none of them, and a binary without a stamp (the `CARGO_BIN_EXE_clawg` of the suite) is refused by `clawg update` as built locally. The tests sign what their fake release server serves with the `minisign` dev-dependency. Each scenario of `update` in `binary.rs` copies the test binary with its stamp into `<home>/bin`, starts its daemon and bridge from that copy, and ends the daemon `update` starts with `clawg stop` when the test drops it.

## CI and release workflows

CI (`.github/workflows/ci.yml`) runs clippy and the suite on Linux and Windows for every pull request that changes a file outside the documentation and tooling paths it ignores. A push to `main` with such a change runs only `merged`, a job that builds nothing: the pull request it merges already ran the suite on that content, and `release.yml` waits for a successful run of the push, which a run of skipped jobs alone is not. A push that only changes the ignored paths runs neither CI nor the release. Every command takes `--locked`, so a `Cargo.lock` that trails `Cargo.toml` fails there. Besides the workspace (where `--workspace` turns on clawg-core's `testing` and `eval`), it runs what the release builds: `cargo clippy --locked -p clawg-cli -- -D warnings`, without `--all-targets` so no dev-dependency brings `testing` in, and, on Linux alone since `build_info` has no platform code, `cargo test --locked -p clawg-core --lib build_info`, the `cfg(not(feature = "testing"))` side of those tests. Pull requests only read the build cache (`save-if: false`); `cache.yml` writes it from `main`.

The compiler is fixed in `rust-toolchain.toml` (an exact `X.Y.Z` with clippy), which local builds use too; every workflow passes the same version to `dtolnay/rust-toolchain`. Raising it is a commit of its own that changes all of them. `rust-version` in the root `Cargo.toml` is the highest `rust-version` among the packages in `Cargo.lock` (1.90, from `tree-sitter-language`; a `cargo +1.90.0 check --locked --workspace --all-targets` builds), never above the pinned toolchain; `tests/conventions.rs` compares the three.

Three more workflows are not named `CI`, so `release.yml` does not wait for them. `cache.yml` (`Cache`) builds on `main`, on Linux and Windows, what CI's `test` job tests, without running it, and writes the cache pull requests read: its job is also named `test`, with the same environment, because rust-cache keys a cache by job id, runner, `CARGO_`/`RUST` environment and lock, never by workflow. It runs when a push to `main` changes a manifest, the lock, the toolchain, `ci.yml` or `cache.yml`, twice a week so GitHub does not evict an unused cache after seven days, and on demand. The other two only report: `advisories.yml` runs `cargo deny --locked check advisories` with the root `deny.toml` on the pull requests and pushes to `main` that change a manifest, the lock or `deny.toml`, and every week, so a RustSec advisory shows without blocking a pull request or a release (an ignored advisory carries its `reason`); `installer.yml` runs PSScriptAnalyzer on `scripts/` on Windows when `scripts/**` changes, with `scripts/PSScriptAnalyzerSettings.psd1`, failing on any finding (an excluded rule says why). Those two download their tool at a fixed version and check it against a SHA-256 written in the workflow. `.github/dependabot.yml` updates the pinned actions once a month, against `develop`.

`.github/workflows/release.yml` runs after a green CI on a push to `main` (see [release.md](release.md)) and builds only `-p clawg-cli`: `--workspace` would link clawg-eval, and with it the `eval` feature of clawg-core, into the shipped binary. Each build sets `CLAWG_DIST_TARGET` and is tried up to three times, since `ort-sys` downloads ONNX Runtime from `cdn.pyke.io` while building; it then runs `--version` and checks that the binary carries no `CLAWG_TEST_` stand-in; the Linux build also checks that it does not link OpenSSL. In every workflow, third-party actions are pinned by commit SHA with the tag in a comment, and each checkout sets `persist-credentials: false`. `tests/conventions.rs` reads the workflows and `dependabot.yml` as text (no YAML dependency) and pins their triggers, pins, build commands, downloads and the signing step, so reformatting a workflow without changing its meaning can break one of them: adjust the test in the same commit. The workflow itself only runs on GitHub; nothing in the suite executes it.

## Local checks

On Windows, live `clawg.exe` processes (for example the editor's MCP bridge) lock `target\debug\clawg.exe` and make the build fail. There the suite and clippy run in `target-test` instead: `cargo test --workspace --target-dir target-test`. See Build directories below for when it is cleaned.

Compiler warnings, `dead_code` and `unused` among them, and clippy's lints are errors here:

```
cargo clippy --workspace --all-targets -- -D warnings
```

`tests/conventions.rs` in `clawg-cli` fails when a source hides dead code behind an `allow`.

The same file fixes the layout of `crates/clawg-core/src/memory`. It is ten folders (`domain`, `store`, `embedding`, `retrieval`, `revision`, `project_docs`, `projects`, `ingest`, `upkeep`, `portability`), and the table `MEMORY_FOLDERS` lists, for each, the folders its production code may name: only ones written above it, so no two folders depend on each other. `a_memory_folder_names_only_the_folders_its_row_allows` fails with `file:line` when a source names a folder its row does not list, when a row lists a folder nothing names, when a module lies outside the folders, or when a source of the crate reaches a module without naming its folder (`crate::memory::store::db`, not `crate::memory::db`). The other crates keep naming the modules the root of `memory` re-exports (`clawg_core::memory::db`), and `every_public_memory_module_is_named_outside_core` fails for one none of them names. The modules that depend on each other in a circle are the groups of `MEMORY_CYCLES`, each inside one folder and with its reason; `the_memory_modules_cycle_only_where_listed` prints every group it finds when the code and the list differ:

```
cargo test -p clawg-cli --test conventions the_memory_modules_cycle_only_where_listed
```

Which clippy lints run is `[workspace.lints.clippy]` in the root `Cargo.toml`: the default group, `large_futures` (a future over 16 KiB, which a move copies whole onto the stack), and `allow_attributes` with `allow_attributes_without_reason`. Every package takes the table with `[lints] workspace = true`, which Cargo does not apply on its own, and a package that takes it cannot add lints of its own. `tests/conventions.rs` checks that each member takes it, that it allows nothing, and that no workflow passes clippy a lint level (`-A`, `-W`, `--cap-lints`). A finding that is not fixed is annotated where it applies with `#[expect(clippy::<lint>, reason = "<why>")]`, the reason saying why the lint does not hold there or which refactor of its own it waits for; once the lint stops firing, the unfulfilled expectation fails the command until the attribute goes.

What the model sees of the MCP server (each tool's name, description and input schema, and the instructions) is pinned in `crates/clawg-cli/src/mcp/agent_contract.json`. When a change to it is intended, run `CLAWG_BLESS=1 cargo test -p clawg-cli the_agent_contract_matches_its_file`: it rewrites the file and fails, so review the diff and run the tests again. It pins the server without a language preference, and `agent_contract.es.json` the server in Spanish (`CLAWG_BLESS=1 cargo test -p clawg-cli the_spanish_agent_contract_matches_its_file`); the English variant a preference gives is held by the tests of `protocol.rs` and `server.rs` (each fits 2048 characters and names only what exists).

## Evaluation tools

`rag-eval --lang-detect [--golden FILE]` prints, without a model or a store, how `detect` labels the corpus rows that carry a `lang`: by label, in total and for the rows of eight words or more, the share right, crossed and undecided, counts only.

A ranking change is compared with the baseline by `cargo run -p clawg-eval --bin rag-eval -- --diff <before.json> <after.json>`. Every metric carries the exact paired p-value of the cases that moved (and MRR, nDCG and tokens a bootstrap interval of the mean change); the primary metrics are `recall@5` and, between two `--agent-view` runs, `search.found`. With the 46-case set a conclusion needs at least 6 cases moving one way and none the other; every case that moves the other way raises that, and the verdict says how many more on the leading side it needs (3 better and 10 worse need 2 more worse). Fewer is "not distinguishable", never "no difference". `--fail-on-regression` exits 6 when a primary metric gets worse at p < 0.05. When the golden cases carry `query_lang`, every block is also cut by the language pair of query and row (`es>en`, …), over the cases with that pair in both files: a change that touches retrieval across languages is read there, and the pair rows stay informative, outside the verdict and `--fail-on-regression`. Choose a new constant reading `by_split.calibration` and report `by_split.test`; `--lexical-only` gives the bm25-only floor to compare against.

`rag-eval --background SNAPSHOT (--fake | --real)` measures at the scale of a real store: SNAPSHOT is a file `clawg backup` wrote, read as a file and never opened, and copied into a `rag-eval-*` directory of the system temp dir that is removed when the run ends, failed or not (`eval_api::copy_background`). A snapshot with commits in a `-wal` beside it, damaged, without clawg's history, of a newer or diverged schema, without an embedding contract or of another one (a store pooled by CLS is named, to be opened once by the daemon and backed up again) is refused with exit 1 before anything writes; an older schema is migrated in the copy. The golden corpus is seeded on top (`--agent-view` saves it through the ingest), every search reaches every agent's rows, as the daemon does without `sharing.json`, and a hit outside the corpus keeps its place in `ranked_refs` as `bg`. A case may cite its save by origin, `expected_origins` (the `created_by_ref` an import wrote, `engram:<sync_id>`, resolved among the live rows of `source = 'import'`, a hit on any piece counting), and name its `project` (an id, or the name of one live project, read in each snapshot as the tools' `project` argument reads it); either without `--background`, an origin with no live row, an unknown, ambiguous or deleted project, or a cited save with rows outside the case's project is exit 2 before anything is measured (`resolve_cases`). The results add `background` (the path, sha256, contract, schema from and to, `searched_at_ms`, the live rows by type, agent, language, source and project, where each `origin_project` was placed, and `golden_twins`), each case's `expected_type`, `top5_types`, `decay_age_days`, `best_cosine`, `score_gap_1_10`, `passes`, `pool_survival` and `short_pool` with its cause (`scope` or `crowded`), and `retrieval.scale`: the top-3 places by type of the cases that do not expect a `session_summary` against the share of rows, the spread of `best_cosine` and the gap with and without an answer by pair and partition, and the short pools left out of both. None of it holds a stored text, a row id or a key, and the tag gains `bg-<first 8 hex of the sha256>`. `--diff` names each side's background and warns when both searched one more than a day apart, since decay reads the clock when it searches; the sweep flags are accepted, while `--docs`, `--lang-detect`, `--fts-tokenizer`, `--follow-up`, `--audit` and `--lexical-only` are not. The snapshots, the cases and the results stay in `docs/eval/` or the temp dir, outside git.

`revision-eval chains (--fake | --real [--tag T])` saves the chain set of `crates/clawg-eval/data/revision-chains.json` through the ingest worker in five stores under the system temp dir: every version without a key; every version under its key; the same without the old versions' vectors (`keyed_bare`); the same with the old versions in no index (`keyed_unindexed`); and the last version alone, saved in the round the keyed store saves it. It reports where the detector leaves each old version, where each version shows in `search_memory` and `recall_context`, and what showing the key costs in tokens. M2 compares the keyed store with `keyed_unindexed`, which differs only in the old versions, and keeps the comparison with the last-version store as a reference (`m2_control`). `revision-eval store --export FILE [--seed N] (--fake | --real)` replays an export, which must sit in a `revision-eval-*` directory directly under the system temp dir, through the worker and writes there the pairs to label; `store --labels FILE [--tag T]` scores the labelled file and removes that directory, which it keeps while a label is missing or invalid or the result file already exists, so no labelling is lost. `--real` reads the dev profile's model (exit 3 without it) and writes a dated file to `docs/eval/results/` that never replaces an existing one, and `--fake` only prints; a `store` result holds counts and rates, never a stored text, a row id or a key. `revision-eval warned --export FILE --since SNAPSHOT [--seed N] (--fake | --real)` measures the topic-key warning on an export made by `clawg export --include-deleted` without `--project` or `--agent` (anything else is refused with exit 2, as is a `--since` that is not the snapshot below): `--since` is the `pre-migration` snapshot (`memory-<UTC>-pre-migration.db`, or its path) that the opening which migrated the store to V19 wrote, since a save before it never had its pair marked, and the window is the saves made from then on. It leaves in the same kind of `revision-eval-*` directory `labels.jsonl`, with the pairs marked by `topic_key_warned` mixed with 100 saves of the window the warning did not fire on (all of them when there are fewer), each with `a`, `b` and `c` to fill, and `warned.json`, with no text; `warned --labels FILE [--tag T]` scores the passes (`c` only where `a` and `b` differ): Cohen's kappa, the precision of the marked pairs against `p_min = 2π / (1 + π)` with π the prevalence of revisions, a `decision` (`keeps`, `adjust_or_remove`, or, with fewer than `N_MAX` = 200 marked pairs, `gather_more` instead of `keeps_by_default`), the precision by distance and by store size, and what the agent did with the warning. It writes `docs/eval/results/{date}-real-revision-eval-warned[-T].json` under the same rules, with counts, rates, intervals and cuts only.

`perf-bench diff FIRST SECOND [--fail-on-regression]` compares two result files of the daemon bench, scenario by scenario: the p50 and p95 of each side, the relative change of both with a 95 % bootstrap interval (4 000 draws, each run drawn again on its own, a fixed seed) and the two-sided Mann-Whitney p-value, which is read but decides nothing. A scenario is `slower` when its p95 rose over 20 % and the interval leaves out no change, or when the second run has failures the first did not; `faster` the other way; with fewer than 40 samples a side it decides nothing, since below that the p95 leaves one sample above it. It warns when the runs differ in build, embedder, machine, rows or seed, and names a scenario only one of them has. Exit 0, 1 for a file it cannot read, 2 for bad arguments, 6 for a `slower` scenario with `--fail-on-regression`: `cargo run -p clawg-eval --bin perf-bench -- diff A.json B.json`.

`load-eval gate [--model-dir D] [--loads 10] [--tag T]` measures what loading the embedding model costs in memory and time, by the way `model.onnx` reaches the session: `vec` (read into a `Vec`, hashed, `commit_from_memory`), `file` (hashed in 1 MiB blocks through a handle that stays open, `commit_from_file`) and `view` (production's read-only view); `load_once` in `eval_api` is the only code that builds the first two, `fetch_model` only downloads the model into the directory they read, and no release build links either. Every load runs in a process of its own (`load-eval child --arm A --model-dir D`) over one warm-up round, discarded, and `--loads` counted rounds, each with the three arms in rotated order (`schedule`). On Windows the parent creates a job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, assigns the child to it and only then writes `go` to its stdin; the child loads, reads `clawg_cli::daemon::process::sample()` and prints one JSON line with its timing (`verify_ms`, `session_ms`) and counters, and the parent reads the job's `PeakProcessMemoryUsed`, the peak commit the gate decides on. On Linux each load is a process too and the peak is `VmHWM`, but the run only reports. It needs Windows to decide, a release build and the real model, which `gate` downloads (about 470 MB; `CLAWG_HF_BASE_URL` names a mirror) into a `load-eval-<uuid>` directory of the system temp dir that is removed when it ends, failed or not; `--model-dir` only accepts such a directory, so a data profile is never read. `verdict` (pure) holds an arm to the `vec` arm of the same run: the median peak commit drops at least 300 MiB, its worst load stays under the best `vec` load, and the median verify-plus-session time rises no more than max(150 ms, 15 %). It decides `View` when `view` passes (alone or with `file`), `File` when only `file` does and `Revert` when neither does; where the peak is not a commit it decides nothing. The result goes to stdout and to `docs/eval/results/{date}-real-load-eval[-T].json`, never over a file that is already there and outside git: `cargo run -p clawg-eval --release --target-dir target-test --bin load-eval -- gate`.

`agent-eval` measures agent sessions, a task under an arm, from what the client prints; it never calls a model by itself. A task is a JSON file in `crates/clawg-eval/data/agent-tasks/tasks/` (`task.rs`): an id, a category (`K1` to `K5`, `S`, `C`, `N`, `Q`, `D`, `R`, `E`), a fixture under `fixtures/` copied as the session's working directory, the prompt (or `sessions`, a list of sessions played in order on one working directory, home, store and native memory, each with its `prompt`, its `tracers`, facts born in that prompt and told nowhere else, its `checks`, which read only its stream, and its `untouched`, a list of `{"path", "text"}` that the working directory must not hold when that session ends (the run reads them right after the session into `untouched-K.json`; they decide nothing, and a session that holds one has done what it was asked not to do yet, which is an artifact); a task has a `prompt` or `sessions`, never both, and one with a `prompt` is a task of one session), the memories the arms with memory are seeded with (text, type, importance, age in days, accesses, `topic_key`, `user_stated`, which seeds the row as the person's, and `rule`, which makes it a rule of every session with `{}` or of the files its globs name with `{"paths": [...]}`), tracers (strings only those memories hold) and checks that decide success without a judge (`answer_contains`, `answer_lacks`, `file_contains`, `file_lacks`, `tool_called`, `tool_failed_count`, which passes when at most `max` calls to the tool `name` failed, those that came back marked as an error or, given `text`, those whose result holds it whatever their mark, since a command that is missing behind a `|` comes back unmarked, and `command_runs`, which passes when at most `max` calls to `Bash`, whatever came back, invoke `command`, one of the task's `shell`: a call invokes it when a part of its line, split at `|`, `||`, `&&`, `;`, `&` or a newline and opened by `$(`, a backtick or `(`, has as its first word, after any `NAME=value`, `command` or a path that ends in `/command` (`score::invocations`; forms such as `sh -c 'eza'` or `xargs eza` count as 0); a check written in a session is evaluated on that session, and one of the task at the end, on the last answer, the calls of every session and the files as they were left; the file checks read CRLF as LF, in the file and in the text, since a checkout with `core.autocrlf` leaves CRLF in the fixtures). Tasks with `"example": true` exercise the harness and measure nothing. A category says what a task measures: `K1` a preference of the person, `K2` a fact of the project or the team that the code does not hold, `K3` a decision with its reason, `S` an old memory the code already contradicts, `C` two live memories that contradict each other, `N` a control that needs no memory, `E` an error of the environment that a later session can avoid, such as a command that does not exist (`K4` and `K5` have no meaning or task yet), `R` a fact told in one session that a later one needs after a relay, and `D` a decision revised between sessions; without memory a `K` task fails, and an `S` or `C` task passes, so what those measure is the harm `success(a0) − success(arm)`. A task or fixture taken from another project names its source, commit, license and what the task wrote itself in `data/agent-tasks/SOURCES.md`, and its fixture is copied unchanged. The arms (`arm.rs`) are `a0` (no memory), `a2` (clawg's MCP server alone, seeded), `a3` (what `clawg setup claude-code` installs, its hooks and protocol block taken from `setup::plan` in the run's language, seeded), `a3-eager` (`a3` with `ENABLE_TOOL_SEARCH=false`), `a3-short` (`a3` with the short block `setup::plan` writes with `--protocol short`: the title, one line saying that the tools' rules come with the server's instructions, and the sections on the session summary and on a compaction; its `CLAUDE.md` stamp says `protocol=short`, and everything else is `a3`'s), `a4` (the client's native memory holding the same texts in `MEMORY.md`, without clawg), `b` (`a3` without `search_memory`, `read_memory` and `list_memories`), `l0` (`a3` without the protocol block), `l1` (`l0` with the seeded rules added at startup by a `SessionStart` hook that runs `agent-eval hook-context` on the run's `startup-rules.md`) and `l2` (`l1` with each rule that has globs moved out of the startup into `work/.claude/rules/clawg/rules-N.md`, one file per set of globs in its `paths:`, which the client loads when the agent reads, writes or edits a matching file). A delivered rule is one line with its age, its subject line and the rest of its text joined with ` — `, under a header that says an old rule can be out of date (`rules.rs`). Every arm with memory is also seeded with a noise, rules on other topics that no check reads, which must be rules and hold no tracer of any task, including those born in a session (`agent-eval tasks` and every run refuse them otherwise): `data/agent-tasks/noise.json` unless the run names another with `--noise NAME`, `noise-NAME.json` of the same directory, such as `noise-300.json` with its 300 rules; an `l1` or `l2` run refuses a noise whose rules at startup pass the 10000 characters the client injects from a hook (`ArmError::StartupTooLong`). The noise and the task's memories go from the newest to the oldest in the seed and in the delivered rules, and from the oldest to the newest in `MEMORY.md`, the order in which an agent that appends its notes leaves it. Every arm writes `settings.json` with an `InstructionsLoaded` hook that runs `agent-eval hook-log` into the run's `instructions.jsonl`, added to the hooks of `setup` in the arms that have them. The seed is a `clawg-memories` export (`seed.rs`) dated by each memory's age, with the tier the store would give it (`eval_api::earned_tier`) and `created_by_type` `user` for a memory with `user_stated`, loaded by `clawg import`. Every run has its own home, which every process it starts gets in `HOME`, `USERPROFILE` and `CLAWG_TEST_HOME`, its own `CLAUDE_CONFIG_DIR`, `--mcp-config` with `--strict-mcp-config` and `stream-json` output with hook events. Nothing can approve a prompt in `-p`, which denies edits and MCP calls without a mode, so every arm gets `--permission-mode acceptEdits` (edits inside the working directory only) and `--disallowedTools Bash` (it is the only way an unattended session could act outside its directory; arm `b` lists its three read tools in the same comma-joined value; a task with `shell`, a list of command names that must be read-only, lifts the denial and allows each as `--allowedTools Bash(<command>:*)`, so every other command stays denied, and its `missing_commands`, each of them in `shell`, are commands that must not exist where the session runs: a paid run refuses to start when one is on the `PATH`), and the arms with clawg `--allowedTools mcp__<server>`, all the tools of the profile's server. Every arm's `settings.json` also carries `permissions.blockReadsOutsideWorkingDirectories: true`, with which the client denies `Read`, `Grep`, `Glob` and `LSP` outside its working directories (the run keeps beside `work/` its `run.json`, with the task and its checks, the streams of the sessions before and the other branch of a fork), and `a4` lists its native memory directory in `permissions.additionalDirectories`, so the block does not deny it its own notes; the key needs Claude Code 2.1.257 or later, and a paid run refuses an earlier `--claude-version` before anything else (`check_read_block`). The client's flag and variable names (`--include-hook-events`, `--effort`, `--max-budget-usd`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY`, `ENABLE_TOOL_SEARCH`, `permissions.blockReadsOutsideWorkingDirectories`), the place of its native memory and the fields of its stream are written as the client documents them and are confirmed by the first session that runs with a real client. `stream.rs` reads a stream leniently: a line of an unknown kind is counted, one that is not JSON is reported by number. The score (`score.rs`) is the checks plus where each tracer went: `used` (written by the agent), `retrieved_but_ignored` (in a tool result or a hook, not written, or in what reached the context without the stream showing it: the `MEMORY.md` of `a4`, and each file of the plan that `instructions.jsonl` names, paths compared whatever their separators and case) or `never_reached`; each session is scored on its own, with every tracer of the task and each one born in an earlier session followed with what brought it (the name of each tool whose result showed it, `hook`, or `context` for what reached the session without the stream: in a continued session the prompts of the sessions before it, and in an arm with native memory the `MEMORY.md` the session began with, cut as the client loads it, the first 200 lines or 25000 bytes), and a fact born in a session is classified over the last one as `not_saved` (no session from its own to the one before the last wrote it in a `save_memory` or `update_memory` or in a `Write` or `Edit` to the native memory directory: what the last session saves at the end brought nothing to it), `saved_not_reached`, `reached_not_used` or `used`. A run of two sessions carries `rereads`, what the second session reads again, in tokens at 4 bytes a token and in two parts: `again`, the results of the `Read` of a file the first session read or wrote, except a file the second one edits (`Edit`, `MultiEdit`, `Write` or `NotebookEdit`, before or after reading it) that the first did not write, of the tools that read a memory (`search_memory`, `recall_context`, `read_memory`, `list_memories`) and of the `Read` of the native memory; and `to_edit`, the `Read` that `again` leaves out, because the client asks for a `Read` in the same session before an `Edit`, so any new session pays it, with a memory or without it. Paths are compared resolved from the working directory. When the second session is new, the relay overhead is what its first request has over the first of the first session (never below 0) plus `again`; when it continues the conversation there is none, since its first request is the whole conversation. The record of each session lists its `outside_reads`: the calls, a subagent's included, that read outside the working directory and the directories the plan adds (`Read` by its `file_path`; `Grep` and `Glob` by `path`, and by `pattern` when it is an absolute path; `LSP` by its file; `Bash` by each word of its command that is an absolute path or has `..`, all resolved), each with its tool, its path and whether the client denied it (its result came back marked as an error); the files the client writes for the session, which hold its `session_id` in their path, are not listed. A run carries `artifacts`, what makes it unfit to be counted, each with its session and decided by `run::artifacts` from the records: `session_failed` (no result, or an error), `server_not_connected` (an arm with clawg whose server was not `connected` in the `init`), `not_continued` (a continued session whose first request has less context than the last one of the session before), `read_outside` (an outside read the client did not deny), `compacted_early` (a compaction in a session that is not the last: in the last it is what a session that goes on does) and `applied_early` (an `untouched` entry whose text was there). The rubric (`rubric.rs`) judges each `save_memory` by the protocol's rules that need no judge: stored, known type, importance in range, size, a subject line, text after it, an identifier, the profile's language (`language::detect`), a key for a decision or a preference, the key's shape, a conclusion without `user_stated` and the six sections of a summary.

- `agent-eval tasks [--data DIR]` checks every task and that no tracer is in a file of its fixture, lists them (with `sessions=N` for a task of several) and checks and counts each noise.
- `agent-eval prepare --task ID --arm ARM --out DIR --clawg PATH --model M [--effort E] [--max-budget-usd N] [--claude-version V] [--profile dev|prod] [--lang en|es] [--sessions split|joined|both] [--noise NAME]` lays one run out in DIR, which must be missing or empty: `work/`, `home/`, `claude-config/` (with its `settings.json`), `mcp.json`, `seed.jsonl`, the `startup-rules.md` of `l1` and `l2` and `run.json` with the client that plays the session, the client's command line, its variables, the daemon of the run (`clawg serve --profile P --port 0` and the `daemon.json` it publishes) and the `clawg import` and `clawg stop` around the session. It starts nothing.
- `agent-eval run … (--replay STREAM | --max-budget-usd N --claude-version V)` prepares the run and runs the session its `run.json` plans (`execute`, `run.rs`). An arm with clawg starts `clawg serve` with the run's home on an ephemeral port, its output in `serve.log`, waits until the `daemon.json` it writes once it listens names its pid (at most 60 s) and then until `clawg status` says that daemon's model is ready (at most 15 minutes, since a first start in a run's home downloads the model, and a real import or search before is a `503 embedder_not_ready`), loads the seed with `clawg import` and ends with `clawg stop`, which also runs when the seed or the client failed, then waits for the daemon to go and ends it through its own handle if it stays; a seed that does not load starts no client, and each clawg command's output goes to `clawg.log` after its command line, with the `clawg status` that found the model ready; a command that fails is named with the last line it printed. An arm without clawg starts none. The client runs in the working directory with the plan's variables, its stdout in `stream.jsonl` and its stderr in `client.log`, and `result.json` is scored from what the sessions left, also when one failed. A task of several sessions plays them in order in one run, on one working directory, home, configuration and, with clawg, one daemon that loads the seed once and stops after the last: each session leaves `stream-K.jsonl` and `client-K.log`, the native memory it began with in `memory-before-K.md` and its instruction files in `instructions-K.jsonl`; a session that does not exit 0, or whose result is an error or is missing, lets no other begin, the commands after the sessions still run, and the sessions that ran are scored and the run does not end. `--sessions` says how: `split` (the default) starts a conversation for each session, `joined` continues the conversation of the one before with `--continue`, and `both`, only for a task of two sessions, plays the first once and the second twice from the same state: with the daemon stopped, the working directory, the client's configuration and the whole home, without the `models/` of clawg's data directory, are copied to `fork/`, the second session is played continued, everything is put back in the same paths and it is played again as a new one; each branch is left in `joined/` or `split/` with its `stream-2.jsonl`, its instruction log, its working directory and a `result.json` of its own, marked as the pair of the other, and the run has none. A branch whose second session fails keeps its files in its directory all the same and is scored as a run of two sessions that did not end, and a fork whose first session fails leaves the result of that session in its root, with no pair. A task of one session takes only `split`. With `--replay` the client is `agent-eval replay-client STREAM`: it applies the `Write` and `Edit` calls of a hand-written or recorded stream (paths inside the working directory only) and prints it, and no Claude model is called. A replay is a stream, or for several sessions a directory with `session-1.jsonl` to `session-N.jsonl` (for a fork, `session-1.jsonl`, `joined-2.jsonl` and `split-2.jsonl`; one that lacks or holds another is refused before anything is laid out). In an arm with clawg the client given the run's `mcp.json` sends each call of the stream to a tool of the run's server to that server, by stdio, and prints what it answered in place of the recorded result, so a second session can find what the first saved; a call it cannot answer fails the client naming the tool, the other calls and the arms without clawg stay as recorded, and the hooks of the client are not run. With a fake model a search finds what a session saved only by an identifier they share (with letters, such as `STAGING_PORT`) or by the same text. Without it the client is `claude`, a paid session: the run needs `--max-budget-usd`, its hard cap, and `--claude-version`, and refuses before laying anything out a `--claude-version` earlier than 2.1.257, the first with the read block, and a `claude` whose `--version` reports another version, and then (`RunError::PaidRun`, each problem named) an environment with `ANTHROPIC_API_KEY` missing or empty (in `-p` the key pays; the run's config directory has no login) or with `ANTHROPIC_AUTH_TOKEN` (outranks the key) or `CLAUDE_CODE_EFFORT_LEVEL` (overrides `--effort`) set, an `--out` that or any ancestor of which holds `.git`, `CLAUDE.md`, `CLAUDE.local.md` or `.claude/CLAUDE.md`, which the client would read as instructions or take as the project and its native memory, and a working directory whose path holds, ignoring case, the task's id or one of its tracers: the client tells the agent where it works, so a run directory named after its task can hand the agent the fact the task measures. The spending cap, the model (`--model`), the language (`--lang`) and the Claude Code version are parameters of each run, recorded in `run.json`. A run inherits the environment, so a real run's daemon downloads the model into the run's home unless `CLAWG_HF_BASE_URL` names a mirror. On Windows clawg finds its home through the system and not `HOME` (`paths::home_dir`), so a run of an arm with clawg refuses, before laying anything out, a binary that does not carry `CLAWG_TEST_HOME`, the mark of a `testing` build (`check_isolation`).
- `crates/clawg-eval/tests/agent_eval.rs` replays the example tasks with the streams of `data/agent-tasks/replays/`, the `clawg` that `cargo test --workspace` builds beside `agent-eval` (a `testing` build, which the test checks) and the fake model: the daemon of each run, its seed, a client that fails and still stops the daemon, a daemon that never listens and starts no client, a `claude` of another version refused before the run is laid out, the relay example in two sessions on one daemon and, forked, with a branch that does not see what the other did, a session that fails, the example with a command that does not exist, a session that must leave a file untouched and does or does not, a run and a branch that fail and are scored all the same, a paid run refused for a client without the read block, the noises and the tasks listed with their sessions. CI runs it on Linux and Windows; run alone, `cargo test -p clawg-eval --test agent_eval` needs that build already in the target directory.
- `agent-eval score --run DIR` scores a run again from the streams of its sessions, as played by the client its `run.json` names; a run that forked is scored in each of its branches. `result.json` records, in `session`, the credential that paid (`apiKeySource` of the stream's `init` line) and when the session started and ended in UTC, taken from the creation and last write of `stream.jsonl` (a platform that gives no creation time leaves the start out). Its `outcome` holds the main loop's tokens (`usage`, with the cache writes for 5 minutes and for 1 hour apart) and each model's tokens and estimated cost (`modelUsage`, which also counts subagents and the response that crossed `--max-budget-usd`). `session` is the record of the last session, `score` the score of the run (it succeeds only when every session ended and every check of the sessions and of the task passed), `sessions` the record and score of each session that ran, with its followed tracers, what it wrote to a memory and how many `Write` and `Edit` went to the native memory, and `shape`, `noise_rules`, `facts`, `overhead`, `rereads`, `artifacts` and `paired` complete it; a result without them reads as a run of one session. `session` also holds the context of every request and the tokens of the first request (input, cache written and cache read of the first message of the main loop: what the context costs before the agent acts) and each instruction file the client reported loading, with its `load_reason`, read from `instructions.jsonl` (a run without it loaded none). It also lists its `untouched` entries, each with its path, its text and whether the file held it, and its `outside_reads`.
- `agent-eval report --runs DIR` reads the `result.json` of the directories up to 3 levels below DIR (one that holds it is not searched further) and prints a Markdown table by task, then arm, then shape (`split` or `joined`), then noise (the rules the runs were seeded with): category, runs, the runs an artifact left out, successes as `k/n`, runs that did not end (an error or no result), the means of cost, turns, seconds and clawg calls per run (a figure a run does not report is left out of its mean), the tracer fates summed, the median of the first request's tokens over the runs that give it, the mean of the instruction files loaded for a path the agent worked on (`load_reason` `path_glob_match`), and a totals line with the sum of the costs and the runs without one, then the tokens summed (every model's, or the main loop's of a run that gives none by model), with the first session of a fork counted once. A run with an artifact is left out of its row, counted in the `excluded` column and listed below the table with its path and each cause and session; the totals count every run, since each cost what it cost. The table also gives the sessions per run, the median context of every request, the median relay overhead (empty in a `joined` row) and the median of what the second session reads again (`again`) and the facts summed by their class, and cost and turns are those of the whole run, the sum of its sessions. For the runs that forked a second table, by task and arm, gives the pairs: of all of them, how many have an artifact in a branch, how many did not continue and how many have a compaction in a session of a branch; of those without an artifact, how many each branch passed, how many the continued one passed and the new one failed, the median context at the fork, the median saving of the cost of the new session's second session over the continued one's, of the pairs whose continuation read at least 80 % of its first request from the cache, and the medians of the avoidable relay overhead of the new branch, of its reads to edit and of what the continued branch reads again. Example tasks are included and marked.
- `agent-eval costs --runs DIR` reads the same results and prints a CSV with a line per session and model: the run's path below DIR, task, arm, start and end in UTC, the credential, the model, input, output, cache read and cache write tokens, the main loop's cache writes for 5 minutes and for 1 hour (on the line of the session's model only), the client's estimated cost and the table it priced it with (`costBasis`), and the number of the session and the shape of its run (the first session of the new branch of a fork is the continued branch's and is listed once). A session without a breakdown by model has one line with its main loop and total cost, and one that printed no result a line without figures. It prices a session by its tokens and finds it by its time in the console's usage, which knows no session.
- `agent-eval calls --runs DIR` reads the stream of every session below DIR and prints a table by tool: its calls, those that carry tokens of their own (a call alone in its message and followed by another request: the context grew by what it added) the median and p90 of those tokens and the median of the size of its results at 4 bytes a token; a tool of a server whose two medians, what its calls add and its results, pass 1500 is noted as a candidate for a diet, since what a call adds holds the words the model wrote in that message.
- `agent-eval hook-context FILE` and `agent-eval hook-log FILE` are the hooks the harness adds to a session, with the absolute path of the `agent-eval` that prepared the run: the first prints FILE as the `additionalContext` of `SessionStart`, the second appends the input the client gives an `InstructionsLoaded` hook to FILE, one line each (an input that is not JSON is kept as text). `tests/agent_eval.rs` runs both, and prepares an `l2` run of `madr-0011-asterisk-list-marker` to check its rules files.

## Build directories

Cargo never removes an old artifact from a target directory. Every version bump, branch or worktree with other sources, feature set or toolchain leaves a new set of the workspace's test binaries beside the previous ones, so a directory that is only ever reused grows past 100 GB. Most of that weight is the workspace's own crates, not its dependencies.

- Tests and clippy use one directory: `target`, or `target-test` on Windows. Never create another one (`target-apply`, `target/verify-win`, a directory outside the repository).
- Before testing a new version (another branch or openspec change, a version bump, another worktree's sources), remove the workspace's old artifacts and keep the dependencies: `cargo clean --workspace --target-dir target-test`. After `rustup update` or a dependency change in `Cargo.lock`, empty it: `cargo clean --target-dir target-test`. Within one change's TDD loop the directory is reused, not cleaned.
- On Windows, `target` is cleaned only when no `clawg.exe` built there is running; never stop one to clean it.
- A directory a one-off comparison needs (a worktree arm, a baseline build) is deleted, with its worktree, by the task that made it.
- A task ends with no build directory other than `target` and `target-test`.
