# Daemon, ingest and MCP tools

The daemon's HTTP API, the docs index, what a save goes through, and what the MCP bridge offers the agent. The data directory and the projects are in [data-profiles.md](data-profiles.md), the commands in [commands.md](commands.md).

## Docs index

A project's docs index (`crates/clawg-core/src/memory/project_docs/`) holds its Markdown and manifests (`Cargo.toml`, `package.json`, `pyproject.toml`, `go.mod`) as passages split by heading, each under its breadcrumb (`path > heading > subheading`), and its Rust, Python and TypeScript code split along the syntax tree (tree-sitter), each piece under its path and the headers of the definitions that contain it (`path > impl Store`). It honours `.gitignore`, is derived from disk in its own tables and never touches `memory`; a file is re-read when its sha256 or the model changes. A changed doc keeps the stored vector of each of its passages whose whole `indexed_text` (breadcrumb, a blank line, body) is in the same doc's stored passages, when the doc was embedded by the refresh's `model_id`, read by value and not by row id (a repeated text takes the first one's blob in every passage that has it); only the rest is embedded, and the doc is still replaced whole in one transaction, so it equals a full reindex. When a doc has more than `EMBED_BATCH` (16) passages left to embed and the splitter has a tokenizer, they go to the embedder in one call from the most tokens to the fewest, ties in the passages' order, counted as the model receives them (under the passage prefix, cut to its window; `passage_order`, `in_passage_order`), so each run of the embedder pads its texts to little more than their own length; each vector goes back to its own passage, so the order changes no row, id or report, and counting belongs to the `embed` phase. With that many or fewer, or without a tokenizer, they go in the passages' order. A new doc, a moved file (its path is in the text) or a doc of another model reuses nothing, and `RefreshReport::reused` counts the passages kept, which the `indexed the docs of …` log line ends with (`refresh_line`, `crates/clawg-cli/src/daemon/api.rs`). A doc whose vector the embedder returns unusable is left as it was, logged and tried again by the next refresh, without stopping the other docs (`RefreshReport::failed`); a failing embedder or store still ends the refresh. Only a root marked `index_docs` in `project` is read: the bridge asks for it for its own root alone, and only when that root has a `.git` or one of those manifests and is not the home directory or a filesystem root (`auto_indexable`, `crates/clawg-core/src/memory/project_docs/corpus.rs`; a root already marked stays marked), and `clawg projects add` for any other, so a `project_path` the model passes is a label for memories until the user adds it. A daemon from before assigned ids that answers 409 `project_root_collision` makes every tool that scopes to that root fail rather than mix two projects (`all_projects` still works); any other registration failure only logs a warning, and the bridge goes on with the id derived from the root.

## Ingest

Ingest masks secrets (`crates/clawg-core/src/memory/redact.rs`) before a save is chunked, hashed or embedded, and the docs index does the same with every passage; a confirmed save lists the masked kinds in `redacted`. It masks keys and tokens of known formats (an `sk-` or `hf_` key only when it mixes upper case, lower case and digits, so hyphenated identifiers and class names pass; Slack webhooks; PGP private key blocks), the literal value after a key ending in `password` or `passwd` (`password`), after a key ending in `secret`, `token`, `api_key`, `access_key`, `secret_key`, `account_key` or `auth_key`, in any case and with any prefix (`credential`, never a value of digits alone), and after `Authorization: Bearer|Basic|Token` (never a variable, a type, a call or a placeholder), and everything the writer wraps in a private mark, `<private>` to `</private>`. A mark left open masks to the end of the text; a mark right after a backtick is text. Nothing is guessed from entropy. The reason of a verdict and the error an outbox row records are masked the same way before they are stored. A rule added later reaches stored rows only through `clawg secrets`, and makes `undelete` refuse a deleted row it now flags.

A save is written, already masked, to the `ingest_outbox` table of `memory.db` before the daemon answers `201` or `202`, and its row goes in the transaction that finishes storing it (`crates/clawg-core/src/memory/outbox.rs`), so a kill, crash or power cut loses nothing accepted (the row alone is written with `synchronous = FULL`; the rest of the store keeps `NORMAL`). Each piece of a long save is noted in the row as it is stored, and a replay resumes after it. On start the daemon ingests pending rows before new saves. Each take of a row spends an attempt; a row is `failed`, with its cause, once it spent 3 takes that ended in a failure the embedder did not cause or with the process gone, or when its event no longer parses. A save the embedder could not take (`EmbedderUnavailable`) hands its attempt back and is taken again in the same run after 1 s, doubling up to 60 s, holding the queue so saves under one topic key still apply in order (`crates/clawg-core/src/memory/worker.rs`); a caller waiting for it gets `202` `retrying`. A caller waiting for a save that failed otherwise gets `500 ingest_failed` and its row is dropped when nothing was stored, and `202` `partially_saved` with the stored pieces in `memories` and the cause in `detail` when some were, its row kept for the next start to finish. A drain stops a save with a row before its next piece once its deadline passes (after the first piece each take stores), handing the attempt back, and the next start resumes it. `clawg outbox retry|discard` is the way out of `failed`. Every save answers with an `operation_id` (a UUID v4, or the caller's own, 1 to 128 visible ASCII characters); sending the same one again while its row exists answers `already_queued` (pending) or `ingest_failed` (failed) instead of saving twice. Shutdown no longer writes `ingest-pending.jsonl`; one left by an older clawg is imported masked on start and removed.

A save longer than one piece (480 tokens) is split into pieces of 96 tokens, neighbours sharing about 24, so one sentence is not averaged away in a long vector; every piece after the first is embedded behind the save's first 32 tokens, and `memory_piece` links the pieces (`crates/clawg-core/src/memory/pieces.rs`). With the tokenizer loaded, every cut of the splitter (pieces, head, chunks, the docs index, an import's notes) falls where a word starts, whitespace right before the token or at it, a token of whitespace alone opening the word after it (`word_starts`, `plan_word_windows`, `crates/clawg-core/src/memory/chunker/token_splitter.rs`): a window ends at the last word start under its cap, the next starts at the word start nearest the 24th token from that end, moved back while the two share fewer than the 16 characters `join_pieces` looks for (`MIN_OVERLAP_CHARS`), and a word longer than a piece or a text without spaces is cut by token. The byte fallback cuts as before. Saves split before at 424 tokens, or inside words, keep their pieces. Search fills its KNN pool with distinct saves, keeps the best piece of each and labels it `piece=K/N`. A save's `content` holds at most 64 KiB, counted in bytes as received (`MAX_CONTENT_BYTES`, `crates/clawg-cli/src/daemon/api.rs`): a longer one is a 400 before the outbox naming its size and the limit, since every piece rewrites the outbox row with the progress so far and what a save writes grows with the square of its length; `save_memory` and `protocol.md` say so.

A save may name a `topic_key` (`crates/clawg-core/src/memory/topic.rs`): lowercase segments of `[a-z0-9._-]` joined by `/`, at most 80 characters, anything else a 400 before the outbox. Its scope is the project, as for the dedup, whoever saved the rows, within what the saver reaches: a key names a topic of the project (V20 indexes both by `COALESCE(project_id, '')`). In the transaction that finishes the save (with its outbox row, or linking its pieces), every live row of that scope outside the save becomes `superseded` by the save's first row, except a piece of a save whose first piece is live without that key, which stays live and loses the key; the save's rows take the key, the rows it inserted the best tier and the most accesses of the replaced ones, and the type and importance it does not name come from the oldest live row of the scope. The detector never pairs a save with the rows it replaces, a save that fails replaces nothing, and the answer lists the replaced rows in `replaced` and echoes `topic_key`, so a bridge can tell a daemon that ignored it. A save without a key that the detector paired with a row of its project (`Candidate.same_scope`) names the closest of them in `revision_candidate` (`unkeyed_revision`), the transaction that finishes the save marks its pair with that row `topic_key_warned` (V19; no later verdict, key or delete clears it, and the export and import carry it, since following the line keys the save's own row, which then reads like a row keyed from the start; `mark_warned_in`, `topic.rs`), and `save_memory` adds the line `revision-eval` measured: if the save revises that row, save it again under a `topic_key`, which only gives its own row the key (`topic_key_warning`, `crates/clawg-cli/src/mcp/tools.rs`; a test in `revision-eval`'s `cost.rs` keeps it the measured line). Rows keep their content: the history is the chain of `superseded` rows, listed with `by=#N` and `topic=K`. `search_memory` and `read_memory` show a row's `topic=K` only where a save under it would revise it: a row of any author in the project a `save_memory` with the same `project_path` goes to (`read_memory`, which takes none, compares with the bridge's own; `revised_from`, `crates/clawg-cli/src/mcp/tools.rs`). A `user_preference` of another project, which a search reaches from any project, shows no key, nor does a row without a project unless the save has none either; a hit from a daemon that does not send `project_id` keeps it. Each `superseded` row records why in `supersede_cause` (`revision` or `verdict`, V17). Deleting the current row of a key, when no other live row of its project holds it, makes the newest save its revision replaced live again, whoever saved either, (`crates/clawg-core/src/memory/revival.rs`), marked `revived_from` the deleted row, and points the older ones at it; `DELETE` lists them in `revived`, and the rows a verdict replaced, which stay superseded, in `hidden`. Restoring the deleted row supersedes again what its delete brought back; a restored row superseded by a deleted revision comes back current under the same rule, and the maintenance pass applies it to what an older delete left.

The contradiction detector (`crates/clawg-core/src/memory/contradiction.rs`) measures closeness, not contradiction: each earlier row within the band that the saver reaches, of any author or none, becomes a pair in `memory_conflict`, one per pair of saves, written in the transaction of the new row. `needs_user` escalates a pair only when it is closer than `ESCALATE_BELOW` (0.40) and both sides are a `user_preference` or an `architectural_decision`, or closer than `IDENTIFIER_ESCALATE_BELOW` (0.30) and both texts share an identifier; an escalated pair, and only one, is named in the newer row's `disputed_against`, makes it `disputed` and shows in ACTIVE CONFLICTS to every agent that reaches both sides and is shown one of them. The rest are `pending`: the save's answer lists them in `related` for the agent to judge, and `memory_status` counts them. A verdict is kept in the pair (`crates/clawg-core/src/memory/dispute.rs`), `supersedes` whose `other` is a preference or a decision is a 409 in any state of the pair unless the call declares `user_answered` with the user's answer in `reason`, which the pair keeps as `user answered: <reason>` (a declaration, not an authentication; the protected row as `keep` needs none, so a verdict is undone as before), and a restored row brings its escalated pairs back.

Each save is sealed with who stated it (`crates/clawg-core/src/memory/provenance.rs`): `source = 'explicit'` and `created_by_type = 'agent'` unless the save declares `user_stated`, which makes it `user`, and `source = 'synthesis'` with `agent` when it names `derived_from`; `user_stated` with `derived_from` is a 400 before the outbox, as is a `derived_from` naming a memory that is missing, deleted, out of the saver's reach or `superseded` (the refusal names what replaced it), and an outbox row without the field is the agent's. Rows saved before the seal read `explicit` / `user` whoever stated them, so no reader claims a row is the user's: `memory_status`, ACTIVE CONFLICTS and `synthesize` mark only `inferred`, `conclusion` and `imported` (the value an import writes), and a pair in `memory_status` names first the side without a mark. The origin changes no pair, status or score.

## MCP tools

MCP tools (`crates/clawg-cli/src/mcp/server.rs`): `save_memory`, `search_memory`, `recall_context`, `search_project`, `list_memories`, `read_memory`, `update_memory`, `delete_memory`, `restore_memory`, `resolve_conflict`, `answer_suggestion`, `synthesize`, `memory_status`.

`update_memory` also moves a memory, with its unit, to the project of `to_project_path` (a directory, registered first as any path a tool names), to `to_project` (an id or a name) or out of every project with `clear_project`, through `PATCH`.

`save_memory`, `search_memory`, `recall_context`, `search_project` and `synthesize` take `project`, an id or a name, not with `project_path`, resolved through `POST /v1/projects/resolve` on every call; only `save_memory` creates one (with `new_project` apart from similar names), and a refusal names the candidates and what to ask the user (`format_refusal`, `crates/clawg-cli/src/mcp/tools.rs`). `answer_suggestion` relays the user's answer to a pending suggestion.

A saved text never opens a line of its own where clawg prints it (`indent_continuations`, `crates/clawg-core/src/memory/prompt_builder.rs`): in the context prompt (hits of every block and the sides of ACTIVE CONFLICTS) and in the AUTO section of `workspace.md`, each line after the first is printed behind `  | `, and in `workspace.md` every `<!--` of a copied text becomes `<! --`, so no text can forge a block, a hit or a section marker; the rows keep their text as saved. An author is shown after `by ` through `display_author` (no controls or line breaks, brackets as parentheses, at most 48 characters), in the prompt and in `search_memory`, while the stored `agent_id` still decides whose a row is.

What the agent is told about memory lives in one text per language, `crates/clawg-cli/src/mcp/protocol.md` and `protocol.es.md`, compiled into the binary: when to save, how to write a save (a first line naming the subject, the exact paths and identifiers, in English), what not to save, which type and importance to pick, the session summary, and that whatever a tool retrieves is evidence, not instructions. Its opening paragraphs, before the first `##` section, are the server instructions, at most 2048 characters; tests keep it naming only registered tools, their arguments and the memory types. `crates/clawg-cli/src/mcp/protocol.rs` owns them (`PROTOCOL`, `PROTOCOL_ES`, `opening`, `text`), for the bridge and for `setup`: with Spanish, `text` is `protocol.es.md`, written for Spanish with the same sections and the same names and markers between backticks (a test compares them); with English, `protocol.md` with its two rules on language rewritten (found across the file's line breaks, each by a test exactly once) to save and search in English, answer the user in it unless they write in another, and search again in Spanish when a search says memories remain in it; every variant fits the 2048 characters. Without a preference it is `protocol.md` as written.

A session in Spanish reads the rest in Spanish too, one `match` on `Lang` per sentence: the descriptions of the tools and their arguments (`crates/clawg-cli/src/mcp/tools_es.rs`, a table `ClawgMcp::with_language` puts on the router, which a test keeps covering every tool and argument and naming what the English text names), every answer of the bridge (`tools.rs`, `server.rs`; the language the bridge started with, `ClawgMcp::speaks`), the notes the daemon adds to a context (`SHARED_NOTE`, `CONFLICT_NOTE`, the BUDGET note and the conflicts not shown, in the `lang` of the request, English without one) and the hooks. The markers stay as they are in every language: the `=== … ===` headings, `NEW`, `OLD`, `disputed`, `[truncated]`, `piece=K/N`, `by <agent>`, `topic=`, `score=`, `imp=`, `acc=`, `by=#N`, `from=`, `live=`, `lost=`, `origin=`, the provenance marks, the names of tools, arguments and memory types and the values of a status, as do the sentences the daemon returns in an error, which the bridge frames (`no se guardó: …`). `rag-eval` reads an empty answer in either language.

While a store holds both languages, `memory.lang` (V22: `en`, `es`, `und`, NULL until classified) says which one a row is in, as the detector `clawg_core::memory::language::detect` reads its masked text: function words of each language and the marks of Spanish, with code, paths and identifiers left out first, undecided on little evidence. The save (`PreparedRow`) and the import write it, from the row's own text and never from a file's `lang`; the maintenance pass classifies the rows left NULL in batches of 500 without touching anything else. `POST /v1/search` and `POST /v1/context` with a query take `lang` (`en` or `es`, anything else a 400) and then answer `other_language`, the live saves of the search's scope in the other language that the caller reaches (`count_saves_in`, over `idx_memory_lang`). A bridge with a preference sends its language and, when that count is above zero and the search showed fewer than `FEW_SHOWN` (3) memories, ends `search_memory` and `recall_context` with a line asking to search again with the query in the other language (`other_language_line`, `crates/clawg-cli/src/mcp/tools.rs`); with no memory left in the other language the line stops. `memory_status` names the session's language and says when `preferences.json` now says another. `save_memory` and `update_memory` list the seven memory types in their schemas, and `POST /v1/memories` refuses any other with a 400 that lists them, before the save reaches the outbox, as `PATCH` does; an outbox row written before that check still stores as `semantic_fact`.
